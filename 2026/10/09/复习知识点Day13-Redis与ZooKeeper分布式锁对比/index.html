复习知识点Day13：Redis与ZooKeeper分布式锁对比

一句话记住今天：Redis 锁 = 性能优先的”到期自动释放”锁（SET NX EX + Lua + 看门狗），ZK 锁 = 一致优先的”临时顺序节点选举”锁（会话消失自动释放）。面试抓四块：① 分布式锁要满足什么（互斥 / 防死锁 / 防误删 / 可重入 / 高可用）；② Redis 实现与三大坑（死锁、误删别人锁、忘了续期）；③ ZK 实现（临时有序节点 + watch 前一个节点）；④ 对比结论：高并发抢锁用 Redis，严格互斥 / 强一致用 ZooKeeper。

先说结论：两把锁的本质区别

都是”多台机器抢同一份资源”，但底层思路完全不同：

  • Redis 锁：用一条原子命令”写成功就赢”，靠过期时间兜底防死锁；性能高、实现轻，但主从切换时可能短暂出现”两把锁”；
  • ZooKeeper 锁：用临时有序节点 + 序号排队，客户端会话断开节点自动消失；公平、强一致，但性能和吞吐不如 Redis。

面试开场白：”Redis 锁是’先到先得 + 过期兜底’，适合高并发抢锁；ZooKeeper 锁是’临时节点 + 序号选举’，适合强一致、需要公平排队的场景。大多数业务选 Redis，但面试要能讲清楚 Redis 锁的坑，以及 ZK 为什么能避免这些坑。”

一、分布式锁要满足的五个条件

不管用谁实现，分布式锁首先要满足：

  1. （互斥）：任意时刻只有一个客户端持有锁；
  2. （防死锁）：客户端崩溃后锁能被自动释放，不能永久卡死；
  3. （防误删）：只能释放自己持有的锁，不能把别人的锁删掉；
  4. （可重入，可选）：同一线程重复加锁不被自己阻塞；
  5. （高可用 & 性能）：锁服务本身不能是单点，加锁释放要快。

下面看 Redis 和 ZooKeeper 分别怎么满足、各自在哪一条上翻车。

2.3 自动续期：Redisson 看门狗（watchdog）

锁有 30 秒过期，但业务要跑 5 秒，第二个 30 秒时锁就提前释放了——别人的请求会进入临界区。解法是续期：

  • Redisson 默认锁 30 秒；
  • 锁持有期间，看门狗每过 1/3 时长（10 秒） 自动续期一遍；
  • 客户端挂了，看门狗跟着停，锁到期自动释放，不产生死锁；
  • 所以口诀：“业务没跑完，锁不能先到期；客户端挂了，锁一定要到期。”

2.4 Redis 锁的缺点（必考）

问题 现象 缓解
主从切换丢锁 A 在主节点加上锁，主节点挂了，从节点还没同步到该 key，新主上位后 B 又能加上锁 → 同一时刻两把锁 RedLock 多数派 + ≥3 独立 Redis，但工程上争议大；或接受概率 / 换 ZK
过期时间与业务时长冲突 业务跑超时，锁提前过期，并发进入 看门狗续期，但不能 100% 杜绝极端情况
不公平 锁不排队，后来者抢到就插队 一般业务可接受

面试加分：RedLock（向 N/2+1 个独立 Redis 实例都加锁成功才算拿锁）能降低丢锁概率，但”时钟跳跃 / GC 暂停”仍可能打破互斥，Martin Kleppmann 与 Redisson 作者有著名的论战——结论是不推荐红锁，能用 ZK 就换 ZK。

三、ZooKeeper 分布式锁

3.1 原理：临时有序节点 + watch

ZK 里节点有几种类型，锁只用到两个特性：

特性 作用
临时节点（EPHEMERAL） 客户端会话结束自动删除 → 挂了不死锁
有序节点（SEQUENTIAL） 自动追加自增序号 → 天然排队，最公平

3.2 为什么没有”羊群效应（惊群）”

如果所有等待者都 watch 整个 /locks 目录，一个节点释放会唤醒所有等待者，大家全部去抢，只有一个成功，其余全白醒——这就是羊群效应。

ZK 锁的正确姿势是每个人都只 watch 自己前一个节点：锁释放只通知一个人，唤醒谁谁就是下一个持有者，O(1) 唤醒、无惊群。

3.3 ZK 锁的优缺点

优点：

  • 不会死锁：临时节点随客户端会话消失，客户端崩溃锁自动释放；
  • 公平排队：有序节点天然 FIFO，后来的不可能插到前面；
  • 无主从丢锁：ZK 自己靠 ZAB 多数派保证一致性，不存在”写到主机没同步到从机”丢锁问题；
  • 不需要过期时间：用会话心跳管理，没”业务超时锁提前释放”的续期难题。

缺点：

  • 性能低于 Redis：一次加锁要 create + getChildren + exists/watch 多次 RPC；
  • 怕会话超时：客户端 GC 停顿超过 sessionTimeout，临时节点被删，锁被别人拿走，而旧客户端还以为是自己的锁（与 Redis 过期同理）；
  • 运维成本高：ZK 集群本身要 3/5 台机器维护；
  • 锁删除、释放有事件传播延迟，要求极低延迟的场景不如 Redis 直接。

维度 Redis（SET NX + Lua） ZooKeeper（临时有序节点）
实现原理 原子 SET 抢占 + 过期时间 序号排队 + watch 前一个节点
一致性 最终一致，主从切换可能丢锁 强一致（ZAB 多数派）
性能 高，单次 RTT 多次 RPC，吞吐低于 Redis
公平性 不公平（先到先抢） 公平（FIFO 排队）
羊群 / 惊群 不存在 只 watch 前一节点，可避免
死锁防护 过期时间 + 看门狗续期 临时节点随会话清理
释放锁 Lua 校验 requestId 后 DEL 删除自己的节点
可重入 需要计数维护 需要计数维护
可用性 主从 / 集群，存在丢锁窗口 依赖 ZK 集群本身可用
运维成本 低（通常已有 Redis） 高（独立 ZK 集群）
适用场景 秒杀、订单防重、短临界区抢锁 分布式任务调度、分布式事务协调、需要强一致 / 公平的锁

五、面试常考点（背这组）

面试题 一句话答案
为什么并发锁不能用 synchronized？ 锁只在单个 JVM 内生效，多实例 / 多进程就不互斥了
setnx 有什么坑？ 和 expire 分开执行不原子，中间崩溃会永久死锁；用 SET key val NX PX milliseconds
为什么释放锁要用 Lua？ 保证”判断是自己” + “删除”两个操作原子，避免误删别人的锁
锁过期但业务还没执行完？ 看门狗自动续期（业务设超长过期时间有死锁风险，不推荐）
Redis 主从切换为什么不安全？ 锁写主成功但主挂，从节点没同步到该 key，新主上位后别的客户端又拿到锁 → 双锁
怎么防主从丢锁？ RedLock 多数派 + 多个节点；但工程上有争议，强一致场景直接考虑 ZK
ZK 怎么防死锁？ 临时节点随客户端会话消失，会话结束自动释放
ZK 怎么实现互斥和有序？ 全部抢建有序节点，序号最小的拿到锁，其余等前面的
惊群（羊群）效应是什么？ 释放时唤醒所有等待者去抢，只有 1 个能成功；ZK 只 watch 前一个节点避免
Redis 和 ZK 怎么选？ 高频抢锁 / 已用 Redis / 秒杀类选 Redis；强一致、公平排队、不能接受丢锁选 ZK
ZK 会不会也有双执行风险？ 客户端 GC 停顿超过 sessionTimeout 会被判定掉线，锁被转移，仍有理论窗口
可重入怎么实现？ 同线程计数器 + 持有者标识；Redis 里用 INCR 计数，ZK 里用线程持有者判断

六、面试加分：选型决策流程

7. 自测三问

  1. 业务在持锁过程中执行了 2 分钟，Redis 锁 30 秒就过期了，另一台机器拿到了锁开始执行同样的业务——画出时间线，说出你能做的三层补救（续期 / 版本号校验 / 幂等）。
  2. 为什么 Redis 主从切换会出现”两个客户端同时持锁”？ZK 用临时顺序节点为什么没有这个问题？
  3. 10 台机器同时在 /locks 下创建节点抢锁，最小的前 3 个节点被删除时，ZK 分别会唤醒几个人？为什么说是”无惊群”？
