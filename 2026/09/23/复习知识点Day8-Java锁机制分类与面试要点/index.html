一句话记住今天：Java 锁 = 「悲观/乐观」「公平/非公平」「可重入」「独占/共享」「JVM 内置 vs JUC」几个维度的组合。面试抓四条主线：① 两大类实现（synchronized（JVM 内置） 与 ReentrantLock（AQS + CAS））；② 锁升级（无锁 → 偏向 → 轻量 → 重量）与 CAS 乐观锁；③ 选择要点（能否中断、能否超时、是否 fair、自动释放）；④ 高频坑（死锁、锁对象选错、锁粒度、DCL 与 volatile）。

1. 为什么需要锁：临界区与三大特性

多线程并发访问共享变量时，会发生”读到一半被修改”的竞态问题：

锁的本质：把「检查 + 修改」合并成一个不可分割的临界区，同一时刻只允许一个（或多个）线程进入，从而保证并发三性：

  • 原子性：操作不可分割（锁 / CAS）；
  • 可见性：释放锁把最新值刷到主存（volatile 也有）；
  • 有序性：防止指令重排带来的意外结果。

2. 锁的分层分类：一张表看懂全局

锁其实不是”一种东西”，而是多个维度的组合（面试一开口就要先分层）：

分类维度 分类 典型实现 一句话区别
竞争策略 悲观锁 / 乐观锁 synchronized、Lock / CAS 悲观”先锁再做”；乐观”先做，冲突了 CAS 重试”
是否公平 公平锁 / 非公平锁 new ReentrantLock(true/false) 公平按排队顺序；非公平允许插队，吞吐更高
可否重入 可重入 / 不可重入 synchronized、ReentrantLock 同一线程可重复拿同一把锁
读写关系 独占 / 共享 ReentrantLock / ReentrantReadWriteLock 写写互斥、读写互斥、读读共享
实现层面 JVM 锁 / JUC 锁 synchronized / Lock 接口 虚拟机自动管理 vs 类库代码实现
获取失败 阻塞 / 非阻塞 lock() / tryLock() 拿不到就等着 vs 立刻失败返回

记忆口诀：「悲观乐观分策略、公平看排队、重入看线程、共享看读写、实现看 JVM 还是 JUC」。

3. synchronized：JVM 内置锁（最常用）

3.1 三种用法

重要陷阱：

  • 实例锁 ≠ 类锁：同一个类的 m1()（实例锁）和 m2()（类锁）可以同时执行，因为锁对象不同；
  • 锁对象必须稳定：别用 String、Integer、Long 等被常量池/缓存池复用的对象做锁，容易”误锁”。

3.2 锁升级（JDK 6 起的性能优化，面试高频）

状态 适用 代价
偏向锁 只有一个线程访问 几乎零开销（不用 CAS）
轻量级锁 少量线程交替/竞争 CAS 自旋，忙等待
重量级锁 竞争激烈 线程挂起/唤醒，涉及内核态切换，代价最高

注意：JDK 15 起默认禁用偏向锁（JEP 374），面试可以说”锁会自适应升级/降级，重量级锁也不是特别慢”。

4. ReentrantLock：JUC 锁体系（AQS 家族）

4.1 synchronized 没有的能力

能力 代码 价值
可重入 同上 同一线程重复 lock 不阻塞
获取中断 lock.lockInterruptibly() 等待时能被 interrupt 打断
超时获取 lock.tryLock(3, TimeUnit.SECONDS) 超时返回失败，不死等
多个条件队列 newCondition() 比 wait/notify 更精确唤醒
公平锁 构造参数 true 避免线程饥饿

4.2 synchronized vs ReentrantLock（面试必问对比）

对比项 synchronized ReentrantLock
实现 JVM 内置（Monitor） AQS + CAS（类库）
释放 自动释放（异常也释放） 必须 finally unlock
中断/超时获取 不支持 支持
公平锁 仅非公平 可公平/非公平
条件变量 1 个 wait/notify 多个 Condition
性能 JDK 6 后与 Lock 相当 相当

结论：大多数场景直接 synchronized；需要超时、中断、多条件唤醒、公平锁时换 ReentrantLock。

5. 乐观锁与 CAS：无锁并发

  • 悲观锁：先加锁（synchronized/Lock），独占访问；
  • 乐观锁：不加锁直接改，提交时用 CAS 检查”值还是旧值吗？是→改成功；不是→重试/失败”。

CAS 三大问题（面试点）：

  1. ABA 问题：值被 A→B→A，CAS 会误判为空闲 → AtomicStampedReference（加版本号）
  2. 自旋空转：竞争激烈时 CPU 忙等；
  3. 单一变量：CAS 只能原子操作一个变量（多个变量需要锁或不可变对象）。

6. 注意点：高频踩坑清单

坑 现象/原因 正确做法
死锁 线程互相拿着对方要的锁，互相等待 固定加锁顺序；tryLock 加超时
忘释放 Lock 漏 unlock 引起线程卡死 一律 try/finally 包住
锁对象选错 String/Integer 并发复用，误锁 用 private final Object lock = new Object()
锁粒度太大 整个方法加锁，性能下降 只锁临界区；读多用读写锁
volatile 当锁用 volatile 只保证可见性，不保证原子性 计数用 AtomicInteger 或锁
DCL 双重检查 Singleton 不加 volatile 会返回”半构造”对象 静态 volatile 单例（见下）
实例锁/类锁混淆 静态方法不阻塞实例方法 明确要锁的对象是实例还是类

7. 死锁：条件与实战修复

死锁四大必要条件（背出来就赢了）：互斥 + 持有并等待 + 不可剥夺 + 循环等待。

修复三板斧：

  1. 固定加锁顺序（都倒序拿锁，切断循环等待）；
  2. tryLock(timeout) 拿不到就释放已有锁并重试；
  3. 锁粒度最小化，别在持锁时搞耗时的 IO/网络。

8. 面试题速查表（锁相关高频）

面试题 一句话要点
synchronized 和 Lock 区别 自动/手动释放；能否中断/超时；公平策略；多条件
锁升级过程 无锁→偏向→轻量（CAS 自旋）→重量（内核）；JDK6 起自适应、JDK15 默认关偏向锁
synchronized 底层 对象头 + Monitor，退出临界区自动释放；JIT 优化（锁消除/锁粗化）
什么是 CAS 比较并交换：先比对旧值再写新值，原子指令完成
CAS 有什么坑 ABA（加版本号）、自旋空转、多变量不支持
volatile 与 synchronized 区别 volatile=可见性+禁止重排；synchronized=原子+可见+有序
为什么 double-check 加 volatile 防止把”半初始化”的对象给别的线程读
公平锁与非公平锁 公平排队，非公平插队；后者吞吐更高
读写锁有什么用 读多写少场景，读读并行、写写/读写互斥
解决死锁什么时候 tryLock？ 拿不到锁直接返回，配合重试/降级，避免无限等待
