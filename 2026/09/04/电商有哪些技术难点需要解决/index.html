电商有哪些技术难点需要解决

很多人觉得电商系统无非就是商品、订单、购物车、支付那几个 CRUD。可真到线上，订单重复提交、库存超卖、支付回调丢失、优惠券被刷……每一个问题都直接跟“钱”相关，处理不好就是事故。这篇文章把电商开发中最核心的技术难点梳理一遍，重点讲讲订单幂等、库存设计、支付体系、优惠券和购物车这几个方向。

先说结论：电商的技术难点可以收敛成几件事

一张订单从提交到履约，系统在并发、失败随时发生的网络环境下，要保证三件事：

  1. 状态只变一次 —— 幂等性
  2. 资源不能被多卖 —— 并发控制
  3. 跨系统数据最后能对上 —— 最终一致 + 对账兜底

一句话概括：电商的难点，不是功能做不出来，而是在高并发、会失败的分布式环境下，把状态和钱管对。

一、订单：幂等处理是底线中的底线

为什么订单必须幂等

用户端或系统端的“重复请求”防不胜防：

  • 用户连点“提交订单”
  • 前端网络重试、网关重试
  • RPC 超时后服务方自动重试
  • MQ 消息重复投递

如果不做幂等，一次下单可能变成：重复下单、重复扣库存、重复锁定优惠券，甚至重复扣钱，每一件都是事故。

1. 幂等键 + 唯一索引兜底

下单接口要求客户端携带一个 idempotentToken（前端生成 UUID，防重令牌）。服务端先查后插，数据库唯一索引做最后防线：

2. 用状态机管住订单

只做幂等还不够，订单的状态流转也要设计成“单向”的：

  • 任何状态更新都附带 WHERE status = 前一个状态 条件，防止并发把状态“翻转”回去。
  • 支付回调、退款回调都必须先过状态机：只有“待支付”的订单允许变成“已支付”，其他情况一律忽略。

状态机 + 幂等我行，基本能挡住订单环节 90% 的重复问题。

库存的设计：不超卖、更不能少卖

超卖是怎么发生的

经典场景：库存只剩 1 件，两个请求同时读到 stock = 1，都判断“库存够”，都执行 stock - 1，最后库存变 -1，或者两张订单都“抢”到了同一件。

根因就一句话：检查与扣减不是原子的。

分布式锁能解超卖，但锁粒度大、超时释放有边界问题，高并发下性能也差，一般只做入口限流或兜底，真正的扣减还是要靠数据库条件更新或 Redis 原子操作。

预占库存 vs 直接扣减

  • 下单即扣库存：实现简单，但用户超时未支付，库存一直被占着，影响真实销售。
  • 支付成功才扣：体验好，但容易“下单成功、支付时库存没了”。
  • 主流做法是“预占/冻结”：下单时冻结库存，支付成功彻底扣减，订单超时未支付自动解冻（回补）。

注意：回补库存和扣减都必须“幂等”，否则对账时库存对不上。建议用订单号做库存流水主键，保证同一笔订单的扣减/回补只生效一次。

支付：和钱打交道，唯一的要求是“不能错”

支付体系是电商里最严谨、也最容易“掉单”的地方。常见问题：回调丢失、回调重复、回调顺序错乱、退款重复、对账不平。

1. 支付回调必须幂等

微信/支付宝在支付成功后，回调可能重试多次、顺序不保证。处理流程固定三步：

  1. 验签：用平台证书校验签名，防止伪造回调。
  2. 幂等：以支付流水号（交易号）做幂等，同一笔支付结果只处理一次。
  3. 状态机：只有“待支付”的订单才允许变为“已支付”。

2. 掉单处理：不能只等回调

回调可能丢了（网络问题、回调写挂），结果用户付了钱、系统还是“未支付”。必须主动兜底：

  • 主动查单：定时任务扫描“待支付且超时”的订单，调用支付平台查单接口，同步真实状态。
  • 前端轮询：支付页轮询后端状态，回调与查单一起更新。
  • 对账兜底：每日与支付平台账单逐笔核对。

3. 对账，是分布式系统的最后防线

支付平台账单和本地交易流水，每天逐笔比对：金额、状态、订单号一一对应。对不上的差异（短款/长款、状态不一致）进入差异明细，用程序修复或人工确认。

再完美的链路也会出错，对账就是为了兜住“错了也能发现、能纠正”。

4. 退款

退款要当作“下单的反向订单”来对待：

  • 以退款单号做幂等，同一笔订单不能退两次；
  • 退款金额要与支付单、优惠分摊对齐（优惠券按比例分摊、退款后退回/回收）；
  • 退款成功后要回滚库存、回滚优惠券状态，同样是最终一致。

5. 分布式事务：直接放弃“强一致”

下单链路：扣库存 + 建订单 + 核销优惠券 + 支付，往往跨多个服务、多个系统，用全局强事务（如 XA）会很慢，也不现实。行业主流方案：

  • 本地消息表 / 可靠消息（MQ 事务消息）：本地事务记录消息，异步投递；
  • 状态机 + 定时任务：数据消费补偿推进；
  • 对账兜底：无论如何，最后用对账拉平。

一句话：下单链路用“最终一致 + 对账兜底”，而不是被分布式事务锁死。

优惠券与购物车：最容易埋雷的细节

1. 优惠券的难点

  • 领取：要防并发防刷、每用户只能领 N 张（用户+券模板唯一索引 / Redis 计数）、余额与用户账户扣减保持一致；
  • 核销：从“未使用”到“已使用”要原子更新：
  • 退款回滚：订单退款后优惠券要么退回（仍在有效期），要么按比例返还金额；
  • 计算引擎：满减、折扣、叠加规则、互斥规则，规则越来越多，必须把计算抽成独立的“优惠计算/决策模块”，按规则树逐条执行，并给最终金额留痕（优惠明细快照）。

2. 购物车的难点

  • 未登录/已登录购物车合并：本地购物车与账号购物车需合并去重；
  • 数量控制：加购超库存限制、重复加购、用户下单时购物车被清空；
  • 结算时的“商品快照”：用户结算后商品下架、改价、库存变化，不影响已下单的订单——所以订单要保存“下单时的商品快照”（名称、单价、规格），而不是实时拉 SKU；
  • 价格重算：结算页展示的价格，要和订单提交时实时校验，防止“页面标的钱和订单实付的钱不一致”。

总结：电商的难点可以收敛成四个词

问题 解法
幂等 幂等键 + 唯一索引 + 状态机
并发 条件更新 SQL / Redis 原子扣减 / 预占库存
一致性 本地消息 + MQ + 定时任务 + 对账兜底
正确性 价格快照 + 优惠规则引擎 + 支付验签/对账

给做电商的同学一句朴素建议：下单前先把幂等键和状态机画出来，上线前先把对账和补偿机制想好，这能帮你挡住 80% 的线上事故。 电商的“难”不在于代码多复杂，而在于——所有东西都经不起“重复”和“不一致”，而这两点，恰好需要我们最认真地去设计。
