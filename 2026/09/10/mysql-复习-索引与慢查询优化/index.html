MySQL 复习：索引与慢查询优化（从 EXPLAIN 到索引失效）

无论是线上排查问题还是面试，MySQL 的索引与 SQL 优化都是高频主题。这篇文章把「慢 SQL 定位 → EXPLAIN 分析执行计划 → 索引原理 → 建索引的原则 → 索引失效的坑」串成一条完整的复习链路，每部分都给出可直接套用的判断依据。

1. 慢 SQL 先定位：从哪里发现慢查询

优化之前，先要知道慢 SQL 在哪。三个常用入口：

  1. 慢查询日志（slow_query_log）：开启后超过 long_query_time 的 SQL 都会被记录。
  1. EXPLAIN 直接”体检”：拿到一条 SQL 立即看执行计划（第 2 节重点讲）。
  2. 性能监控 / 巡检脚本：定期导出慢日志，按 rows_examined 排序，扫出”扫描行数巨大”的 SQL。

定位慢 SQL 的核心思路是：先找出”扫描行数多、执行时间长”的少数语句，而不是靠感觉猜。

2. 分析执行 SQL：看懂 EXPLAIN

EXPLAIN SELECT ... 不真正执行，只展示优化器选择的执行计划。几个最关键的列：

列 含义 关注点
type 访问类型 从小到好：ALL → index → range → ref → eq_ref → const
key 实际使用的索引 为 NULL 说明没用上索引
rows 预估扫描行数 数量级越小越好，是优化的”温度计”
Extra 额外信息 出现 Using temporary、Using filesort 通常说明有优化空间

type 从上到下逐级解读

  • ALL：全表扫描，最差。表不大可以接受，大表就要警惕了。
  • index：扫描了整棵二级索引树，比 ALL 好一点，但仍不是精确查找。
  • range：索引范围扫描（>、<、BETWEEN、LIKE 'abc%' 等），走了索引且限定范围，比较好。
  • ref：非唯一索引等值匹配，如 WHERE dept_id = 3 且 dept_id 是非唯一索引。
  • eq_ref：唯一索引等值匹配，通常出现在 JOIN、且被驱动表用主键/唯一键关联时。
  • const：主键或唯一索引等值查询且值确定，最多一行，最快。

Extra 里最值得注意的两个

  • Using filesort：排序没有用到索引，MySQL 会额外建临时排序。出现它优先考虑给排序字段建索引（或放到联合索引最后）。
  • Using temporary：GROUP BY、DISTINCT、ORDER BY 时用了临时表，大结果集下很伤，需要检查是否有覆盖的联合索引。

高阶：MySQL 8.0 可以用 EXPLAIN ANALYZE 拿到真实执行耗时和实际扫描行数，比 EXPLAIN 的估值更能说明问题。

3. 索引原理速通：B+ 树、聚簇索引、覆盖索引

  • 索引底层是 B+ 树：非叶子节点只存键值 + 指针，叶子节点存数据/主键并有序串联，天然有序、支持范围查询，磁盘 IO 少。
  • 聚簇索引（主键索引）：叶子节点直接存储整行数据，一张表只有一个。
  • 二级索引（普通索引）：叶子节点存”索引列 + 主键”，查询需要回表去主键索引拿整行。
  • 覆盖索引：查询列的需要的字段全部都在二级索引里，Extra 里出现 Using index，无需回表，最快。所以 SELECT 尽量只查需要字段，有机会走覆盖索引。
  • 联合索引的最左前缀原则：(a, b, c) 这个联合索引，能命中 a、a+b、a+b+c，但不能单独用 b 或 c。

4. 索引创建的原则

  1. 频繁出现在 WHERE 的条件：优先建索引。
  2. JOIN 的关联字段：两边类型必须一致才能走索引，否则索引失效。
  3. GROUP BY / ORDER BY 字段：建联合索引且列顺序和查询一致，能避免 filesort / temporary。
  4. 区分度高的列：比如用户ID、订单号效果好；性别这种只有几个值的列建索引意义不大。
  5. 联合索引按”选择度从高到低”排列（最左前缀的延伸），把优先级最高的放在最左。
  6. 尽量覆盖查询：把查询常用到的列放进联合索引，实现”索引覆盖”，省掉回表。
  7. 索引不是越多越好：每个索引都会拖慢 INSERT/UPDATE/DELETE（维护成本），只造真正被频繁查询的。
  8. 前缀索引：长文本、URL、手机号这类长列，只索引前 N 个字符，减小索引体积，比如 CREATE INDEX idx_name ON t(name(20))。
  9. 避免冗余索引：已有 (a, b) 时，再单独建 (a) 就是冗余的。

5. 什么情况下索引会失效（高频面试题）

建了索引但写法不对，一样会全表扫描。常见失效场景：

1. 违反最左前缀原则

2. 模糊匹配以 % 开头

3. 对索引列做了运算或函数

4. 隐式类型转换

  • 字符串列用数字查询，如 WHERE phone = 13800000000（phone 是 VARCHAR），隐式转换导致索引失效。

5. OR 两边不是同一索引可用的列

6. 优化器认为”全表更划算”

  • 数据量很小，或者命中行数占表比例很大（比如条件命中率超过约 20%~30%），优化器会主动放弃索引直接全表表扫。

7. NULL 判断

  • IS NULL / IS NOT NULL 在部分情况下不能走索引（尤其复合索引）；另外列设计尽量 NOT NULL + 默认值，能避免很多意料之外的问题。

提问：为什么 LIKE ‘%abc’ 不能用索引？

因为 B+ 树是根据完整键值排序的，前缀未知时无法定位起始位置，只能整树扫描。

6. 优化方法论：一条 SQL 的完整优化路径

  1. 抓出 SQL：慢日志里挑频率高、耗时高的语句；
  2. EXPLAIN 体检：看 type 是不是 ALL、rows 是不是巨大、Extra 有没有 filesort/temp；
  3. 有针对地加索引（不重复加），或改写 SQL（改不了索引就改查询写法）；
  4. 重新 EXPLAIN 对比：rows 大幅下降，type 从 ALL → range/ref，优化基本完成；
  5. 复位压测/观察线上：确认耗时下降，监控不反弹。

记住一个判断标准：扫描行数就是最大的耗时来源，大部分 SQL 优化其实都在减扫描行数。

7. 全文复习速查

主题 一句话结论
发现慢 SQL 慢查询日志 + EXPLAIN 体检
EXPLAIN 重点 type / rows / Extra 三列最有价值
索引原理 B+ 树，二级索引要回表，覆盖索引最优
建索引原则 WHERE 高频、区分度高、联合索引最左、别冗余
失效场景 最左前缀破坏、LIKE %、函数运算、隐式转换、OR 无索引、优化器自动放弃
优化流程 抓慢 SQL → EXPLAIN → 加/改 → 复测

面试时被问”数据库优化”，先答看执行计划 → 找全表扫描 / filesort → 基于索引解决，再展开细节，基本就是这个题目的正确打开方式。
