关于RAG你需要了解的东西

模型不知道你公司内部的知识，模型的记忆有截止日期，模型还会一本正经地胡说八道。RAG（Retrieval-Augmented Generation，检索增强生成）就是针对这三个问题最实用、落地最快的解法：与其逼模型“记住”所有知识，不如在回答前去“查一下资料”。这篇文章用尽量短的话讲清楚 RAG 是什么、向量数据库在里面扮演什么角色、有哪些真实应用场景，以及为什么这套设计是合理的。

一、RAG 是什么：一句话版

RAG = 先检索 + 再生成。

具体来说：把知识（文档、FAQ、商品库、代码）提前切碎并向量化存进向量数据库；用户提问时，先从库里检索出与问题最相关的几段内容；再把这些内容拼进提示词交给大模型，让大模型“带着资料”作答。

RAG 这个词最早来自 2020 年 Lewis 等人的论文《Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks》，核心思想一直没变：不要试图把知识塞进模型的“脑子”里，而是让模型在推理时自己去“查资料”。

二、为什么需要 RAG：纯大模型有四个硬伤

问题 表现 RAG 的解法
幻觉 回答得头头是道，但事实是编的 强制模型只依据检索片段回答，可溯源
知识截止 不知道最新事件、最新政策 知识放外部库，随时增量更新，不用重训
私有数据 看不到企业的文档、合同、客服话术 私有文档进向量库，模型看不到但能查到
更新成本 微调一次贵且慢 更新文档 = 重新切片入向量库

微调（Fine-tuning）解决的是“风格、格式、能力”问题；RAG 解决的才是“知识从哪来”的问题。

三、标准流程：离线索引 + 在线问答

1. 离线阶段（建索引）

  1. 文档清洗：去掉页眉页脚、广告、乱码；
  2. 切分（Chunking）：把大文档切成 200～800 字左右的小片段，按标题/段落/语义边界切；
  3. 向量化（Embedding）：用嵌入模型把每个片段变成一个高维向量（几百到几千维）；
  4. 入库：向量 + 原文 + 元数据（来源、标题、时间）一起存进向量数据库，并建好索引。

2. 在线阶段（问答）

  1. 用户问题同样向量化；
  2. 向量库按相似度召回 top-k 片段（如 3~8 段）；
  3. 常用优化：混合检索（向量 + BM25 关键词，兼顾语义与精确匹配）、Rerank（用重排模型把召回结果细排）；
  4. 把片段拼进提示词，让模型生成答案并给出引用来源。

四、为什么要这么设计（重点）

理解了“为什么”，比背流程重要得多。

1. 为什么不把全部资料直接塞给模型？

  • 长度限制：上下文有限，几千页手册塞不进去；
  • 噪声伤害效果：不该相关内容越多，模型越容易“迷失在中间”，答案反而更差（“Lost in the Middle”是实证现象）；
  • 成本：Token 按量计费，喂越多越贵、越慢。

所以只检索“最相关的几段”而不是全量喂——这是 RAG 整个设计的出发点。

2. 为什么用向量检索而不是关键词搜索？

用户问的往往和文档写的“字面上不一样”：

  • 用户问“这个能退吗”，文档写的是“退货政策”；
  • 用户问“认证怎么搞”，文档可能通篇没有“认证”二字。

向量检索比的是“语义”而不是“字面”：嵌入模型把文本映射到向量空间后，语义接近的文本距离近，不同语言的相似意思也会比较小。专有名词、型号、编号等精确匹配场景，再加入 BM25 关键词，这就是“混合检索”连用的原因。

3. 为什么把知识放外部库，而不是微进模型？

对比项 微调 RAG
知识更新 重新训练，周期按周/月 换文档重索引，分钟级
可溯源 模型记忆，说不出来源 直接定位到哪篇文档哪一段
成本门槛 高，需要算力+数据工程 低，接入相对便宜
幻觉控制 有限，编出来的还是出不了 严格限“只依据资料回答”
数据安全 知识进了模型参数，难以剥离 私有文档不出自己系统

结论：知识是高频变动、需要溯源的，放外部；能力/风格这类稳定的、难用文本表达的，才值得微调。

4. 为什么需要“向量数据库”？普通数据库不行吗？

关系型数据库擅长精确查找和范围查找，但无法高效做“高维向量相似度排序”——几百万条 1536 维向量线性扫描太慢。

向量数据库解决的问题：

  • 近似最近邻（ANN）检索：用 HNSW、IVF+PQ 等索引，把“全量扫描”变成“顺藤摸瓜”，十亿级数据也能在毫秒级返回；
  • 相似度计算：内置余弦相似度、内积、欧氏距离等；
  • 元数据过滤 + 混合检索：支持 WHERE 部门 = '财务' 且相似度 > 0.7，向量和过滤条件一起做；
  • 增量更新、备份、水平扩展：这些是把它当“数据库”而不是“工具库”用的原因。

四、向量数据库是什么（简述）

一句话：专门用来存“向量”并做“相似度搜索”的数据库。

  • 向量：文本/图片/音视频经过嵌入模型，变成几百维的浮点数数组，语义相近 → 向量距离近；
  • 距离度量（距离越小越相似）：
    • 余弦相似度：看方向是否一致，文本检索最常用；
    • 内积：常用于向量已归一化的场景；
    • 欧氏距离：看重绝对距离，图像类场景常用。
  • 索引：HNSW（图索引，性能树稳定优先）、IVF（先聚类再就近搜）、PQ（量化压缩省内存），各有取舍；
  • 常见产品：
类型 代表
独立向量库 Milvus、Qdrant、Weaviate、Pinecone(云)
数据库内置 pgvector（PostgreSQL）、Redis Stack、Elasticsearch 8.x
轻量/本地 Chroma、LanceDB、Faiss（算法库）

选型原则：团队已有 PG 就用 pgvector 起步；数据量过亿、并发高再上独立向量库；本地原型直接 Chroma。先在流程里跑通，别一上来就选型。

五、具体应用实例：怎么做 + 为什么能这么设计

1. 企业知识库问答（最典型）

  • 怎么做：把 Wiki、SOP、员工手册、合同模板切分入向量库；员工问“报销上限多少”，系统检索到相关条款，回答并标注“出自《差旅报销制度》第 x 章”。
  • 为什么这么设计：知识是私有的、每天都在变，微调不现实；答案需要可溯源（合规要求），RAG 天然满足“出处可查”。

2. 客服 FAQ 与在线客服辅助

  • 怎么做：FAQ、历史工单、售后政策入库；用户问题先命中售后知识库，自动回复或给客服提供速答建议；
  • 为什么：答复种类有限但量大，检索能覆盖 80% 长尾问题；让 LLM 只负责那 20% 的复杂话术，成本低、兜底到人工也顺滑——难度高的部分留给人工才是系统的关键。

3. 电商 / 商品语义搜索

  • 怎么做：商品标题、详情、卖点向量化；用户搜“通勤穿的外套”——语义召回黑色西装外套、正式夹克；
  • 为什么：电商查询天然口语化，关键词匹配会漏掉同义词、意图（“穿”隐含场景），向量能召回字面不匹配但语义相近的商品。

4. 论文 / 文档研究助手

  • 怎么做：把一批论文压成向量库，问“这篇论文的消融实验结论是什么”，回答会附上对应段落。
  • 为什么：学术对正确性和出处要求极高，幻觉不可接受；RAG 把“不知道”的成本变成“查不到就是没库存”，答案可控。

5. 代码问答 / 代码库助手

  • 怎么做：把公司代码文档、历史解决过的 Issues 检索给模型，回答“登录接口为什么超时”这类问题，并可顺手给出相关代码段。
  • 为什么：私有代码模型没学过，但语义检索能定位到相似代码块和文档，让模型基于现场代码回答而不是凭记忆猜。

6. Agent / 机器人的长期记忆

  • 怎么做：把多轮对话历史、用户偏好向量化当长期记忆，下次会话先检索“这个用户之前说过什么”。
  • 为什么：Agent 上下文有长度上限，而“记忆中重要的部分”可以用语义检索动态捞回来，相当于给 Agent 配了一个“外接大脑”，比全量叠上下文更省、更聚焦。

7. 图片/多模态检索（顺带一提）

向量化图片，用文字或图片搜“相近商品”“相似款式”，原理与文本一致，只是 embedding 模型换成多模态模型。

六、正确使用 RAG：几个常见坑

  1. 切分决定上限：切碎了丢语义，切大了检索不准，按语义边界切分 + 适量重叠；
  2. 检索不到就是答案乱：先看召回率，召回不好就做混合检索 + Rerank，而不是换更聪明的大模型；
  3. 提示词要约束：“只能依据给定资料回答”写在系统提示里，防止模型用记忆补全；
  4. 必须给引用：让答案带上来源，既能溯源又减少幻觉；
  5. RAG 不是万能的：强实时（如股价秒级波动）、强计算（数学推导、复杂逻辑推理）场景，RAG 帮助有限，需要接实时数据源或换 Agent + 工具。

七、总结：为什么这套设计合理

一句话：把“记忆”从模型参数里搬出来，放到一个可以秒级更新、逐条追溯、任意扩容的数据库里；模型只负责理解问题和组织语言，数据库负责回到“哪份资料、哪一段”。

  • 知识静态、模型静态 → 微调；
  • 知识动态、要溯源、要低成本 → RAG；
  • 高并发、上亿级向量、复杂过滤 → 交给向量数据库。

这就是为什么 RAG 现在是企业接入大模型时最优先考虑的方案：不是因为它“聪明”，而是因为它把最贵的部分（知识）与最灵活的部分（生成）解耦了。
