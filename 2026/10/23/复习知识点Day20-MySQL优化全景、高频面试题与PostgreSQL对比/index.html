一句话记住今天：MySQL 优化不是”加索引”，而是一条六层漏斗：SQL 写法 → 索引 → 表结构 → 事务与锁 → 实例参数 → 架构。先用慢日志和 EXPLAIN 找到证据，再从代价最小的一层开始改。面试对比 PostgreSQL 只需记住：MySQL 胜在简单、成熟、互联网生态；PG 胜在标准、复杂查询、扩展能力。

先说结论：优化是一层层往下漏的

层级 典型手段 收益 风险/代价
1. SQL 写法 只查必要列、改写深分页、去掉函数运算、拆 OR 高，改动小 需要理解执行计划
2. 索引 联合索引、覆盖索引、前缀索引、删冗余索引 高 写放大、维护成本
3. 表结构 合适类型、自增主键、大字段拆表、分区 中高 改表有锁与迁移成本
4. 事务与锁 缩短事务、统一加锁顺序、降隔离级别、批量提交 中高 一致性语义变化
5. 实例参数 Buffer Pool、连接数、redo/binlog 刷盘 中 参数耦合，乱调会翻车
6. 架构 读写分离、缓存、归档、分库分表 高 复杂度、一致性、运维成本

优化顺序反了会怎样？ 一条 SQL 只是忘了走索引，却先去分库分表——复杂度上去了，问题还在。正确顺序是：先测量 → 再改写 SQL/补索引 → 最后才动架构。

01 优化从证据开始：先定位，再动手

1.1 四个入口

入口 用途 关键点
慢查询日志 找执行慢的 SQL long_query_time 按业务定，别设 10 秒自欺欺人
performance_schema 按 SQL 摘要聚合 看总耗时、平均耗时、扫描行数
SHOW PROCESSLIST / innodb_trx 看当前谁在跑、谁在锁 定位长事务、锁等待
EXPLAIN / EXPLAIN ANALYZE 看执行计划和真实耗时 估值 vs 实际值

1.2 EXPLAIN 只盯五个字段

字段 看什么 危险信号
type 访问方式 ALL（全表）、index（全索引扫描）
key 实际用的索引 NULL
rows 预估扫描行数 远大于最终返回行数
filtered 过滤后剩余比例 很低说明扫了很多无用行
Extra 额外动作 Using filesort、Using temporary、Using join buffer (hash join) 视场景

EXPLAIN 是估算，EXPLAIN ANALYZE（MySQL 8.0.18+）会真正执行并给出实际耗时和实际行数。优化器估错时，优先怀疑统计信息过期，而不是马上 FORCE INDEX。

1.3 一条 SQL 变慢的四种常见根因

  1. 没走索引或走错索引：扫描行数暴涨；
  2. 回表太多：二级索引找到大量主键，再逐行回聚簇索引；
  3. 排序/临时表：filesort、temporary 落磁盘；
  4. 锁等待/长事务：SQL 本身不慢，是在等锁。

排查时先分清”执行慢”还是”等待慢”：SHOW PROCESSLIST 里 State 是 Sending data 还是 Waiting for ... lock，方向完全不同。

02 SQL 层：改写往往比加索引更便宜

2.1 只取需要的列

SELECT * 的代价：破坏覆盖索引、增加网络传输、表加字段后行为变化、可能把大字段一起拉出来。

2.2 六个索引失效高频写法

写法 示例 原因/改法
列上做函数/运算 WHERE DATE(create_time) = '2026-10-23' 改成范围：create_time >= '2026-10-23' AND create_time < '2026-10-24'
隐式类型转换 phone 是 varchar，却写 WHERE phone = 13800000000 列被转成数字，索引失效；参数加引号
前导模糊 LIKE '%abc' 无法利用 B+ 树有序性；改 LIKE 'abc%' 或全文/ES
联合索引跳过最左列 索引 (a,b)，查询 WHERE b = 1 遵守最左前缀，或补 a 条件
OR 一侧无索引 WHERE a = 1 OR b = 2，b 无索引 全表扫描；改 UNION ALL 或给 b 建索引
字符集/排序规则不一致 两表 JOIN，一边 utf8mb4 一边 utf8mb3 JOIN 列字符集统一，避免隐式转换

补充两个容易忽略的点：NOT IN 遇到 NULL 会返回空结果；LEFT JOIN 后把右表条件写在 WHERE 里，会退化成 INNER JOIN。这两条既是 SQL 坑，也是面试题。

2.3 深分页：三种解法

解法一：游标（keyset）分页，最优

要求排序字段稳定且唯一（通常是主键），不能随机跳页，适合”下一页/下拉加载”。

解法二：延迟关联（deferred join）

子查询只查主键，能走覆盖索引；再按 20 个主键回表，避免把 10 万行的整行数据都读出来。

解法三：交给搜索引擎

搜索、复杂排序、多条件筛选的场景，别硬扛 MySQL，同步到 ES/ClickHouse，MySQL 只按 ID 取详情。

2.4 JOIN 优化

  • 关联列必须有索引且类型/字符集一致，否则被驱动表全表扫描；
  • 小表驱动大表是优化器的选择，不是 SQL 书写顺序决定的；MySQL 8 有 hash join，但索引嵌套循环仍是 OLTP 主力；
  • 避免在 JOIN 列上做函数、运算、隐式转换；
  • 控制 JOIN 表数量，超过 3~4 张要考虑冗余字段或宽表；
  • LEFT JOIN 的过滤条件放在 ON 还是 WHERE，语义不同：放 WHERE 会过滤掉右表为 NULL 的行。

2.5 ORDER BY / GROUP BY

  • 排序字段与索引顺序一致，才能避免 filesort；
  • 联合索引 (a, b) 下 ORDER BY a, b 可走索引，ORDER BY b, a 不行；
  • ORDER BY 与 WHERE 的列组合要满足最左前缀；
  • GROUP BY 可能产生临时表，尽量用索引列分组，或先过滤再分组；
  • ORDER BY RAND() 会生成随机数排序，大表禁用。

2.6 COUNT 的真相

写法 行为
COUNT(*) InnoDB 会选最小的二级索引扫描，统计行数，不取具体值
COUNT(1) 与 COUNT(*) 基本等价，优化器处理相同
COUNT(col) 只统计 col IS NOT NULL，且可能无法用覆盖索引
COUNT(DISTINCT col) 需要去重，成本更高

InnoDB 不像 MyISAM 那样保存精确行数（MVCC 下每行可见性不同），所以 COUNT(*) 大表必然慢。实时性要求不高的总数用缓存/计数表；分页总数能省就省。

2.7 OR、IN、UNION

  • OR 可能触发 index merge，但更常见的是全表扫描；能拆 UNION ALL 就拆；
  • IN 列表很大时，优化器可能从 index dive 退化为统计估算，执行计划会变；超大列表考虑临时表/JOIN；
  • UNION 会去重排序，确定无重复时用 UNION ALL；
  • NOT IN 子查询含 NULL 会返回空集，改 NOT EXISTS 或过滤 NULL。

2.8 批量与长事务

Java 侧使用 JDBC 批量时，MySQL Connector/J 需要开启 rewriteBatchedStatements=true，否则 addBatch() 可能仍是一条条发。

03 索引层：设计比数量重要

索引原理、B+ 树、索引失效完整清单在旧文《MySQL 复习：索引与慢查询优化》里已经展开，这里只讲面试最常追问的设计与优化器问题。

3.1 联合索引的列顺序

假设联合索引 (a, b, c)：

查询条件 能否用索引 说明
a = 1 是 最左前缀
a = 1 AND b = 2 是 前两列
a = 1 AND b = 2 AND c = 3 是 全部命中
b = 2 否 跳过最左列
a = 1 AND c = 3 部分 只能用 a，c 不能用于定位
a > 1 AND b = 2 部分 a 是范围，b 不能继续用于索引定位
a = 1 AND b > 2 AND c = 3 部分 a、b 可用；c 通常只能靠索引下推过滤

设计口诀：等值列在前，范围列在后，排序/分组列跟着等值列。

3.2 覆盖索引与索引下推

  • 覆盖索引：查询需要的列全在索引里，Extra: Using index，不用回表；
  • 索引下推（ICP）：Extra: Using index condition，把 WHERE 中能在索引上判断的条件下推到存储引擎，减少回表次数；
  • 两者都不是银弹：覆盖索引会让索引变宽，ICP 只减少回表、不减少索引扫描。

3.3 选择性与基数

  • 性别、状态这类低区分度列单独建索引意义不大；
  • 但低区分度列放在联合索引里可能有价值（配合高区分度列过滤）；
  • SHOW INDEX FROM t 里的 Cardinality 是估算值，统计信息不准会导致选错索引。

3.4 优化器选错索引怎么办

  1. ANALYZE TABLE t; 更新统计信息；
  2. 检查是否因为回表成本估算而放弃索引（覆盖索引可解）；
  3. 检查隐式转换、字符集、函数导致索引不可用；
  4. 用 FORCE INDEX 只是临时止血，版本升级/数据变化后可能再次翻车；
  5. 用 optimizer_trace 看优化器为什么选它：

3.5 索引不是越多越好

每个二级索引都要维护：INSERT 多写一棵树、UPDATE 改索引列多一次维护、DELETE 多一次清理，还会占 Buffer Pool。经验规则：

  • 单表索引控制在 5~6 个以内（视业务而定）；
  • 删除冗余索引：有 (a,b) 就不需要单独的 (a)；
  • 定期用 sys.schema_unused_indexes / sys.schema_redundant_indexes 排查（MySQL 8 自带 sys 库）。

04 表结构层：一开始就设计对，后面少改表

4.1 数据类型

场景 推荐 避免
金额 DECIMAL(18,2) 或整数分 FLOAT/DOUBLE（精度丢失）
主键 BIGINT UNSIGNED AUTO_INCREMENT 有符号 INT 可能不够、业务字段做主键
字符串 按实际长度 VARCHAR(n) 一律 VARCHAR(255)
时间 DATETIME（范围大）或 TIMESTAMP（带时区，2038 问题） 字符串存时间
布尔 TINYINT(1) CHAR(1) 存 Y/N
大文本 TEXT 拆到扩展表 主表放 TEXT/BLOB 还频繁 SELECT *
字符集 utf8mb4 + utf8mb4_0900_ai_ci 已废弃的 utf8（实际是 utf8mb3）

4.2 主键：为什么推荐自增

InnoDB 是聚簇索引，主键顺序决定数据页的物理顺序：

  • 自增主键：新数据总在最后一页追加，页分裂少、缓存友好；
  • 随机主键（UUID）：插入位置随机，频繁页分裂、索引碎片、写放大；
  • 必须用 UUID 时，选有序 UUID（如 UUID v7）或用 BINARY(16) 存储，别用 36 字符的字符串。

4.3 大字段与宽表

  • TEXT/BLOB 可能溢出页存储，读取成本高；详情、富文本、图片 URL 列表拆到扩展表；
  • 宽表拆成”主表（热字段）+ 扩展表（冷字段）”，减少主表行宽和 Buffer Pool 占用；
  • 但这属于垂直拆分，会带来一次额外查询，按访问频率决定。

4.4 分区表：能做，但别当分库分表

  • 优点：按分区裁剪、历史分区可快速 DROP；
  • 限制：所有唯一索引必须包含分区键、不支持外键、跨分区查询仍可能扫描多分区；
  • 它解决的是单实例内的数据管理，不解决单机容量/写入瓶颈，不能替代分库分表。

4.5 大表 DDL 怎么做

方式 说明 风险
ALGORITHM=INSTANT MySQL 8.0 部分操作秒级加列 不是所有 DDL 都支持
Online DDL ALGORITHM=INPLACE, LOCK=NONE 仍可能耗 IO、复制延迟
gh-ost / pt-osc 影子表 + binlog 同步 + 切换 需要额外磁盘、触发器/ binlog 权限
低峰期 + 主从切换 先在从库执行再切换 流程复杂

原则：大表 DDL 永远不要在业务高峰直接跑，先评估锁级别、执行时间、复制延迟和回滚方案。

05 事务与锁层：很多”慢 SQL”其实是等锁

5.1 隔离级别与 MVCC

隔离级别 脏读 不可重复读 幻读 MySQL 默认 PG 默认
READ UNCOMMITTED 可能 可能 可能 否 否
READ COMMITTED 否 可能 可能 常用（互联网） 是
REPEATABLE READ 否 否 InnoDB 快照读基本避免 是 否（PG 的 RR 是快照隔离）
SERIALIZABLE 否 否 否 否 否

InnoDB 的 MVCC：

  • 每行有隐藏的 DB_TRX_ID、DB_ROLL_PTR；
  • 快照读（普通 SELECT）根据 Read View 判断版本可见性，通过 undo log 构造历史版本；
  • 当前读（SELECT ... FOR UPDATE、UPDATE、DELETE）读最新版本并加锁。

5.2 为什么 MySQL 默认 RR，而 PG 默认 RC

  • MySQL 早期默认 statement 格式 binlog，RR 能减少主从不一致；现在互联网团队普遍用 ROW 格式 binlog + RC，因为 RC 减少间隙锁、提升并发；
  • RR 下当前读使用 next-key lock（记录锁 + 间隙锁）防幻读，代价是更容易死锁；
  • PG 的 MVCC 用元组版本 + 快照，RR 是事务级快照（快照隔离），不靠间隙锁；写冲突用 SSI 在 SERIALIZABLE 下检测。

面试答法：“隔离级别不是越高越好，要看一致性需求和并发成本。MySQL 互联网业务常用 RC + ROW binlog；金融强一致场景才考虑 RR/SERIALIZABLE 并接受锁代价。”

5.3 锁与死锁

InnoDB 行锁是加在索引上的。如果 UPDATE 没走索引：

表现为”更新一行，锁了一片”，并发一高就锁等待甚至死锁。

死锁排查：

避免死锁的四条：

  1. 统一加锁顺序：所有事务按相同顺序更新多行/多表；
  2. 缩短事务：不要在事务里做 RPC、发消息、等用户输入；
  3. 让更新走索引：减少锁范围；
  4. 冲突高时降级重试：捕获死锁异常，退避重试；业务允许时用 RC 减少间隙锁。

5.4 长事务的五宗罪

  • undo log 无法 purge，历史版本链膨胀；
  • 持有锁时间长，阻塞其他事务；
  • 主从延迟（大事务提交后 binlog 集中传输）；
  • 回滚极慢，故障恢复时间长；
  • 连接占用，连接池被拖垮。

监控 information_schema.innodb_trx 的 trx_started，超过阈值告警；业务代码用”短事务 + 批量提交”。

5.5 redo log、undo log、binlog

日志 所属层 作用 关键点
redo log InnoDB 崩溃恢复，保证持久性 循环写，innodb_flush_log_at_trx_commit
undo log InnoDB MVCC 历史版本 + 回滚 长事务会导致 undo 膨胀
binlog MySQL Server 主从复制、数据恢复 ROW 格式推荐，sync_binlog 控制刷盘

事务提交时，InnoDB 与 Server 层通过 两阶段提交协调 redo 与 binlog，保证崩溃后两者一致。

5.6 持久性与性能的取舍

参数 最安全 性能模式 风险
innodb_flush_log_at_trx_commit 1（每次提交刷盘） 0/2 崩溃可能丢 1 秒事务
sync_binlog 1（每次提交刷 binlog） 0/N 崩溃可能丢 binlog
innodb_flush_method O_DIRECT（避免双缓冲） 视文件系统 需压测验证

金融场景用”双 1”；普通业务可以在压测后适度放宽，但必须清楚丢数据的边界。

06 实例与架构层：最后的放大器

6.1 Buffer Pool

  • innodb_buffer_pool_size 通常设为物理内存的 50%~70%（专用 DB 机器）；
  • 命中率低不一定是池小，可能是大查询/全表扫描污染了缓存；
  • 大表扫全表会挤掉热数据，考虑 innodb_old_blocks_time、只读从库或归档。

6.2 连接与线程

  • MySQL 是 thread-per-connection，连接数过高会导致上下文切换和内存压力；
  • max_connections 不是越大越好，配合应用侧 HikariCP 控制总连接；
  • 关注 Threads_running、Threads_connected、Aborted_connects。

6.3 读写分离与延迟

  • 主库写、从库读，解决读多写少；
  • 复制延迟是最大坑：写后立刻读可能读不到；
  • 解法：关键读强制主库、按 GTID 等待、会话粘性、缓存双删/延迟双删；
  • 半同步复制能降低丢数据风险，但会增加写延迟。

6.4 缓存

  • Cache Aside：读缓存 → 未命中查库回填；写库后删缓存；
  • 先更新库再删缓存，比先删缓存更稳；
  • 热点 Key、缓存击穿/穿透/雪崩的处理见 Day18；
  • 缓存不是数据库的替代品，一致性要求高的余额/库存要谨慎。

6.5 分库分表与归档

  • 单表千万级、单库到瓶颈才考虑；
  • 分片键、跨分片查询、分布式事务、迁移方案见 Day18；
  • 历史数据先归档（冷热分离），往往比直接分库分表更划算。

6.6 高可用

  • 主从 + MHA/Orchestrator 自动切换；
  • MySQL InnoDB Cluster / MGR 提供组复制；
  • 代理层（ProxySQL、MySQL Router）做读写分离和故障转移；
  • 高可用不仅是”切得快”，还要保证切换后数据不丢、应用能重连、脑裂有仲裁。

07 高频面试题（15 问）

Q1：一条 SQL 很慢，你怎么排查？
A：先确认是执行慢还是等锁（SHOW PROCESSLIST、innodb_trx）；再看慢日志和 performance_schema 找 TOP SQL；用 EXPLAIN 看 type/key/rows/Extra；判断是索引缺失、回表过多、排序临时表还是统计信息问题；最后改写 SQL、补索引、更新统计信息；仍不够再考虑表结构/架构。

Q2：索引为什么会失效？
A：常见六类：列上做函数/运算、隐式类型转换、前导 % 模糊、违反最左前缀、OR 一侧无索引、JOIN 列字符集/类型不一致。根因都是”优化器无法用索引的有序性定位”。

Q3：联合索引 (a,b,c)，WHERE a=1 AND b>2 AND c=3 能用到哪些列？
A：a 用于等值定位，b 用于范围扫描；c 一般不能继续用于索引定位，但可能通过索引下推在存储引擎层过滤，减少回表。

Q4：什么是回表？怎么避免？
A：二级索引叶子存的是索引列 + 主键，查其他列要回聚簇索引取整行。把查询需要的列放进联合索引形成覆盖索引（Using index）即可避免回表。

Q5：深分页怎么优化？
A：优先游标分页 WHERE id > last_id ORDER BY id LIMIT n；不能改接口就用延迟关联，子查询只取主键再回表；搜索类场景交给 ES。

Q6：COUNT(*)、COUNT(1)、COUNT(col) 区别？
A：COUNT(*) 和 COUNT(1) 基本等价，统计行数；COUNT(col) 只统计非 NULL 值。InnoDB 因 MVCC 不保存精确行数，大表 COUNT(*) 仍然要扫描，实时总数应缓存或异步统计。

Q7：事务隔离级别有哪些？MySQL 默认哪个？
A：RU、RC、RR、Serializable；MySQL InnoDB 默认 RR，互联网业务常用 RC + ROW binlog 来减少间隙锁；PG 默认 RC。

Q8：MVCC 怎么实现的？
A：InnoDB 通过隐藏事务 ID、undo log 版本链和 Read View 判断可见性；快照读不加锁，当前读读最新版本并加锁。PG 则是元组上的 xmin/xmax 可见性判断 + vacuum 清理旧版本。

Q9：幻读是什么？MySQL 怎么解决？
A：同一事务两次查询，第二次多出第一次没看到的行。InnoDB 在 RR 下用 next-key lock（记录锁 + 间隙锁）解决当前读的幻读；快照读靠一致性视图。PG 的 RR 是快照隔离，不加间隙锁，写冲突用 SSI 检测。

Q10：死锁怎么排查和避免？
A：看 SHOW ENGINE INNODB STATUS 的 LATEST DETECTED DEADLOCK，或 performance_schema.data_locks/data_lock_waits；避免方法是统一加锁顺序、缩短事务、更新走索引、降低隔离级别、失败重试。

Q11：为什么推荐自增主键，不推荐 UUID？
A：InnoDB 聚簇索引按主键组织数据，自增主键顺序追加，页分裂少；UUID 随机插入导致页分裂、碎片和写放大。必须用 UUID 就用有序 UUID v7 或 BINARY(16)。

Q12：redo log、undo log、binlog 有什么区别？
A：redo 是 InnoDB 的物理日志，用于崩溃恢复；undo 是逻辑旧版本，用于 MVCC 和回滚；binlog 是 Server 层逻辑日志，用于复制和恢复。提交时两阶段提交保证 redo 与 binlog 一致。

Q13：大表加字段/加索引怎么做？
A：先确认 MySQL 8 是否支持 INSTANT/Online DDL；评估锁级别和复制延迟；大表用 gh-ost/pt-osc 影子表迁移；低峰执行，准备回滚和监控。

Q14：优化器选错索引怎么办？
A：先 ANALYZE TABLE 更新统计信息，检查隐式转换/字符集/回表成本；必要时改写 SQL 或补覆盖索引；FORCE INDEX 只做临时止血，最后用 optimizer_trace 定位原因。

Q15：读写分离后写后读不一致怎么办？
A：关键读强制走主库；或按 GTID/位点等待从库追平；会话粘性；缓存延迟双删；业务上接受最终一致。根因是主从复制延迟，不能假装它不存在。

8.2 五个关键差异展开

1）MVCC 与清理机制

  • MySQL：undo log 保存旧版本，purge 线程清理；长事务会阻止 purge，导致 undo 膨胀；
  • PG：堆表里保留多版本元组，autovacuum 清理死元组；长事务/长查询会导致表膨胀（bloat），需要监控 pg_stat_user_tables 的 dead tuples。

2）索引能力

  • MySQL 以 B+Tree 为主，覆盖索引、联合索引、前缀索引是核心；全文和空间索引能力有限；
  • PG 索引类型更丰富：GIN 适合 JSONB/数组/全文，GiST 适合几何/范围，BRIN 适合超大有序表（如时间序列），表达式索引和部分索引也很常用。

3）SQL 能力

  • PG 对 SQL 标准支持更好，复杂查询、窗口函数、CTE、LATERAL、RETURNING、事务性 DDL 更完整；
  • MySQL 8.0 已经补上 CTE、窗口函数、公共表表达式，但复杂分析仍不如 PG；OLAP 场景两者都常让位给 ClickHouse/Doris。

4）JSON 与扩展

  • MySQL JSON 适合简单存取和函数查询；PG jsonb 支持 GIN 索引，适合在 JSON 上做复杂检索；
  • PG 扩展生态是护城河：PostGIS、pgvector、TimescaleDB、pg_cron、Citus 等；MySQL 生态胜在云厂商托管和周边工具成熟。

5）运维与生态

  • MySQL 在互联网公司积累深，分库分表中间件、监控、备份、云服务非常成熟；
  • PG 的 VACUUM、连接进程模型、参数调优需要专门经验；但事务性 DDL、复制和扩展能力更强。

8.3 选型怎么答（面试标准答案）

“选型不是站队，先看 workload 和团队。简单高并发 OLTP、读多写少、需要成熟云托管和分库分表生态，优先 MySQL；复杂查询、JSON/GIS、分析混合负载、需要丰富扩展和事务性 DDL，优先 PostgreSQL。迁移成本、团队熟悉度、运维能力、云厂商支持同样重要，不能只看 benchmark。”

10 60 秒面试话术

问题：”MySQL 怎么做优化？”

参考回答：

我按六层来做。第一层先定位：慢日志和 performance_schema 找 TOP SQL，EXPLAIN 看 type、key、rows、Extra，同时排除锁等待和长事务。第二层改 SQL：只查必要列、去掉列上的函数和隐式转换、深分页改游标、OR 拆 UNION ALL、LEFT JOIN 条件放对位置。第三层看索引：按等值在前、范围在后、排序字段跟上的原则建联合索引，尽量覆盖查询，删掉冗余索引。第四层看表结构：金额用 DECIMAL、主键自增、大字段拆表、大表 DDL 用 Online DDL 或 gh-ost。第五层看事务和锁：缩短事务、统一加锁顺序、更新走索引，必要时 RC + ROW binlog。第六层才是架构：读写分离、缓存、归档、分库分表。最后用 P99、扫描行数、慢 SQL 数、锁等待时长和复制延迟验证效果。

最后记住三句话：

  1. 优化从证据开始：先 EXPLAIN 和慢日志，再动手；没有测量就没有优化。
  2. 索引是成本最低的杠杆，但不是越多越好：设计联合索引和覆盖索引，比盲目加索引有效得多。
  3. MySQL 与 PG 没有绝对优劣：MySQL 把简单 OLTP 做到极致，PostgreSQL 把标准、复杂查询和扩展做到极致，选型看业务、团队和成本。
