复习知识点Day12：法律文书检索系统ES与MySQL混合架构

一句话记住今天：法律文书检索 = ES 只管搜（返回 id 列表），MySQL 只负责存（拿 id 回表查全量）。面试抓四块：① 为什么不用 MySQL LIKE；② 索引设计（mapping 类型、IK 法律词库、分片与别名）；③ 数据同步（binlog → Canal → Kafka → ES，保证顺序、幂等、能对账）；④ 查询链路（id 回表、filter 与 must、search_after 深分页、BM25 相关性）。

先说结论：整个方案就是一组权衡

法律文书的核心需求是全文检索：按关键词、案由、法院、裁判日期去搜海量文书。最朴素的 MySQL LIKE '%关键词%' 走不了索引，数据量一上来就是全表扫描，延迟完全不可接受，所以引入 ES。

整体架构一句话：ES 只负责检索，MySQL 只负责存储。查询链路是先在 ES 里搜出符合条件的 id 列表，再拿这批 id 回 MySQL 查完整数据，最后组装返回。

为什么要这样折中？三个核心权衡：

权衡 怎么做 换来什么
数据源 MySQL 是唯一真实数据源，ES 只存检索字段 强一致、可事务，ES 挂了可降级
写入方式 binlog 异步同步到 ES 检索性能从秒级降到毫秒级，业务无侵入
存储 ES 不存全量文书，回表取正文 索引体积小、存储成本可控，代价是一次回表

面试开场白：”我们采用 ES + MySQL 混合架构：ES 建倒排索引做毫秒级全文检索，MySQL 做唯一数据源保证强一致，通过 Canal 监听 binlog 异步同步到 ES，接受秒级最终一致；查询两阶段，先拿 id 再批量回表，用最终一致换检索性能。”

一、背景：为什么不能只靠 MySQL 检索

早期直接用 MySQL 的 LIKE '%关键词%' 搜文书：

问题很明显：

  • 无法走索引：前导通配符 % 让 B+ 树索引失效，只能全表扫描；
  • 数据量大就崩：文书数据量是百万、千万级，扫描一次几十秒甚至分钟级；
  • 没有相关性：LIKE 只能判断”有没有”，不能按相关度排序，也不能做高亮、聚合。

为什么不干脆全存 ES

法律文书是强一致、高价值、要落库的数据：

ES 的短板 为什么不能接受
不是事务型数据库 单文档更新原子性没问题，但没有跨文档事务、没有外键约束
更新代价高 分词重算 + 倒排索引重建，频繁更新成本高
存储成本高 副本 + 倒排索引翻倍膨胀，整篇存正文非常贵
数据可靠性 集群抖动、刷新窗口内数据可能不一致，不能当唯一数据源

所以 ES 里只存需要检索的字段：标题、案由、正文（索引字段）、法院、文书类型、裁判日期。真实全量数据永远在 MySQL。代价是最终一致——数据通过 binlog 异步同步到 ES，有秒级延迟，这种场景业务上完全可接受。

二、索引设计：三大块

2.1 mapping：text 还是 keyword

这是面试手写 mapping 的基础：

字段 类型 理由
标题、案由、正文 text 需要分词、全文检索
案号、法院、文书类型 keyword 精确匹配、聚合（terms）、排序（date）
法院（既要分词又要精确） multi-fields 主字段 text + 子字段 .raw 为 keyword
大字段只存不检索 index: false 不建倒排索引，省空间、省写入
  • court.raw：按法院名做 terms 聚合、精确筛选；
  • full_text 只存不索引：作为冗余存一份，避免回表取全文（或按业务取舍）。

2.2 分词器：法律领域的重点

默认 standard 分词器对中文是按单个汉字切，搜”表见代利”会碎成四段，检索基本报废。所以：

  • 建索引时用 ik_max_word：细粒度、穷举切分，保证召回；
  • 查询时用 ik_smart：粗粒度、尽量切成词，保证精度；
  • 自定义法律词典：表见代理、善意取得、不可抗力 这种术语不配词典会被切碎；
  • 同义词配置：如”原告 / 起诉人””被告 / 被上诉人”，提升召回。

面试加分：remote_ext_dict 远程词典可以热更新业务词（新法条、简称），不用重启节点。

2.3 分片与索引策略

策略 做法 原因
单分片大小 控制在 10~50G 太大迁移慢，太小分片碎片化
副本数 至少 1 高可用 + 读扩展
索引滚动 按时间（如 judgments-2026-10） 结合 ILM 冷热分离，旧索引降副本、转冷存储
别名 读写一律走 alias 重建索引时切换 alias 实现零停机

三、数据同步：binlog → Canal → Kafka → ES

同步链路是这套架构最关键的环节：

必须解决的四个问题：

3.1 顺序性

同一行多次变更（insert → update → delete）必须有序执行，否则 ES 数据错乱。
做法：按主键 hash 选 partition，保证同一行的所有变更落在同一个 Kafka partition，partition 内天然有序。

3.2 幂等

Kafka at-least-once 场景下消息可能重复投递。做法是写 ES 时用 mysql_id 作为文档 _id 做 upsert——同一 id 重复写，结果一样，天然幂等：

3.3 全量 + 增量

系统初始化时先做一次全量导入，再把同步位点切到某个 binlog position 开始跑增量。位点必须持久化（DB 或 Redis），挂了重启能从断点续传，不能从当前最新消费导致丢失。

3.4 对账补偿 + 监控

异步同步一定有短暂不一致：

  • 定时对账：比对 MySQL 与 ES 的文档数量，抽样校验内容，发现不一致补偿重推；
  • lag 监控：binlog 消费位点与 MySQL 当前位点差超过阈值就告警；
  • 删除处理：走逻辑删除，ES 里标记 is_deleted，查询时过滤。

四、查询链路：两阶段检索 + 回表

链路：ES 搜索（只返回 id 列表）→ MySQL WHERE id IN (...) 批量查全量 → 按 ES 顺序组装返回。

4.1 避免 N+1

不能拿到 id 后一条一条查 MySQL（N 次网络 RTT）。正确做法：

注意：ES 返回顺序就是相关度排序，回表后必须用 map 按 ES 顺序重排，否则排序就丢了。

4.2 filter 和 query 分开

  • 不需要算分的条件（法院、日期范围、文书类型、is_deleted 过滤），放 filter：不参与打分，可缓存，性能高；
  • 需要算相关性的关键词匹配，放 must。

4.3 深分页：search_after 代替 from + size

ES 默认 from + size 上限 1 万条，再深就报错或内存爆炸。解决：

  • 分页深打 from + size 到一定深度直接限制（如第 100 页封顶）；
  • 更平滑的是 search_after + 排序游标，像翻页书签一样往后翻，不依赖 from；
  • 产品上也可引导用户加筛选条件，减少总命中量。

面试一句话：search_after 本质是”游标”+ 排序值，每次把上次最后一条的排序值带进来继续翻，天然避免横向跳过大量文档。

4.4 相关性排序

  • BM25 打底（ES7+ 默认，词频、文档长度归一化内置）；
  • multi_match 给字段 boost：标题权重 > 案由 > 正文；
  • function_score 结合裁判时间：gauss 让新文书轻微靠前；
  • highlight 返回命中片段给前端标红。

五、兜底与监控

可靠性问题 方案
ES 挂掉 / 集群不可用 降级：按案号走 MySQL = 精确查询，保证核心入口不挂
索引结构要改（换 mapping） 新索引 + _reindex + 切换别名，零停机
mapping 字段类型不可改 新索引重建，别名对用户透明
同步延后 lag 告警 + 对账补偿，补偿重推
ES 慢查询 慢查询日志、监控耗时分布、大分页拦截
集群健康 监控红黄状态、分片未分配、段数量

六、总结：三句话背下来

  1. 索引设计要贴合业务分词——text/keyword 选对、IK + 法律词典、分片副本与别名；
  2. 数据同步保顺序、保幂等、能对账——hash 分区 + _id upsert + binlog 位点持久化 + 定时对账；
  3. 查询链路控好回表和深分页——批量 IN 回表、filter 缓存、search_after、BM25 + 字段 boost。

这套”ES 只搜、MySQL 只存”的思路，不只适用于法律文书，法院案例库、合同库、知识库全文检索都可以直接复用。

7. 常见面试题（背这组）

问题 一句话答案
为什么用 MySQL + ES 两套？ MySQL 保强一致/事务/低成本存储，ES 提高全文检索性能，职责拆分
为什么不全存 ES？ ES 非事务、更新贵、存储贵，法律文书强一致必须落 MySQL
ES 只存哪些字段？ 检索相关字段：title、cause、content、court、judgment_date
数据怎么进 ES？ Canal 伪装 slave 消费 binlog → Kafka → 消费写入 ES，秒级最终一致
同步乱序怎么办？ 主键 hash 分区，同一 id 一行落同一 partition，天然有序
重复消费怎么办？ mysql_id 作为 _id upsert，重复投递不产生脏数据
全量 + 增量怎么写？ 先全量，再持化 binlog 位点增量，断点续传
异步同步不一致怎么办？ 定时对账（数量 + 内容）+ lag 告警 + 补偿
LIKE '%x%' 为什么慢？ 无法走索引，全表扫描；ES 倒排索引是搜索的正解
回表 N+1 怎么避免？ 拿 id 后 WHERE id IN 一次批量查，map 重排保顺序
filter vs must？ 都要求命中；filter 不算分、可缓存，must 参与算分
深分页超 1 万的解法？ search_after + 排序游标；页面限制 / 加筛选
排序怎么让新的靠前 function_score 配日期 gauss 衰减
文书关键词被拆碎？ 配 IK 法律词典 / 同义词；ik_smart 查询、ik_max_word 索引
删除怎么做？ 逻辑删除 is_deleted，同步与查询过滤统一处理
ES 挂了大影响？ 降级 MySQL = 精确查案号，保证可用性

8. 自测三问

  1. 检索”北京法院近三年的民事判决书中包含’善意取得’”，从 ES 两阶段查询到 MySQL 回表的完整链路应该怎么走？
  2. binlog → Kafka → ES 在”同一行 update 了 3 次、消费进程中途重启”的情况下，怎么保证 ES 最终一致且不重复不丢？
  3. 线上 ES 里查出的标题排序和 MySQL 回表后顺序乱了，可能是什么原因？怎么修复？

下一篇预告：可以复习「缓存与数据库一致性（双写 / 延迟双删）」或「Redis 分布式锁」，都是检索类系统最容易连环考的点。
