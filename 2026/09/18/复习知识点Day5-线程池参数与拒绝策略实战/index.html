复习知识点Day5：线程池参数与拒绝策略实战

一句话记住今天：线程池 = 「核心线程 + 任务队列 + 非核心线程 + 拒绝策略」的调度器。面试抓三条主线：① 七大参数（core / max / 存活时间 / 队列 / 线程工厂 / 拒绝策略）；② 任务提交流程（先核心线程 → 再入队 → 队列满才扩容 → 全满拒绝）；③ Executors 四种内置池的区别与坑（无界队列 / 无上限线程数，生产建议手写 ThreadPoolExecutor + 有界队列）。

1. 线程池是什么，为什么离不开它

  • 线程是稀缺资源：每次 new Thread 都有创建开销（内核线程 + 栈内存），并发一高，上下文切换和内存都会被拖垮，甚至 OOM。
  • 线程池 = 一组可复用的线程 + 一个任务队列 + 一套调度规则：任务来了不用反复创建线程，而是交给已有线程按流程接单。
  • 三大价值：复用线程（省创建/销毁）、限制并发（防止打爆机器）、统一管理（排队、超时、拒绝、监控、优雅关闭）。

一句话面试开场：”线程池把『提交任务』和『执行线程』解耦，用一组复用线程干活，通过 核心线程数 + 队列 + 最大线程数 控制并发上限。”

2. ThreadPoolExecutor 七大参数（背熟这张表）

参数 含义 例子
corePoolSize 核心线程数 平时保留、优先创建执行的线程数 8
maximumPoolSize 最大线程数 队列满后最多能扩容到的线程数 16
keepAliveTime + unit 非核心线程空闲多久被回收 60, TimeUnit.SECONDS
workQueue 工作队列 任务排队容器（建议有界） new ArrayBlockingQueue<>(64)
threadFactory 线程工厂 创建线程的工厂，可设线程名/守护 命名 order-pool-%d
handler 拒绝策略 队列满且线程满时怎么兜底 CallerRunsPolicy

实际上 ThreadPoolExecutor 构造器里 7 个参数（核心数、最大数、存活时间、时间单位、队列、工厂、拒绝策略），面试把这张表列全就够用。

任务提交完整流程（必背）

三个反直觉的细节（面试最爱挖坑）：

  1. 先入队，后扩容：只要队列没满，即使线程数是 core，也不会新建 max 线程——很多新手以为”任务多就直接扩到 max”，错。
  2. 核心线程默认不回收：keepAliveTime 只对非核心线程生效；想让核心线程也闲时回收要开 allowCoreThreadTimeOut(true)。
  3. FixedThreadPool 的 max 形同虚设：core = max，队列一满就直接走拒绝策略，永远轮不到”扩容”环节。

3. 四种拒绝策略（面试必考）

策略 行为 适用场景
AbortPolicy（默认） 抛 RejectedExecutionException 想立刻暴露问题、不丢任务
CallerRunsPolicy 让提交任务的调用线程自己执行该任务 慢任务天然背压、绝不能丢数据
DiscardPolicy 静默丢弃新任务 可容忍丢弃的次要数据/日志
DiscardOldestPolicy 丢弃队列中最旧的等待任务，再重试新任务 实时性要求高、旧任务已过期

生产推荐 自定义 handler：记录拒绝次数 + 告警 + 把任务塞回 MQ/落库重试，而不是用默认 AbortPolicy 在高峰直接抛异常把调用方打挂。CallerRunsPolicy 虽然”不丢数据”，但会把任务压力反压给提交方线程，要评估提交方能不能扛。

4. Executors 内置四种线程池区别（高频对比表）

线程池 核心线程 最大线程 队列 特点 风险
newFixedThreadPool(n) n n LinkedBlockingQueue（无界） 固定 n 个线程，排队执行 任务无限制进入 → 队列积压 OOM
newCachedThreadPool() 0 很大（Integer.MAX） SynchronousQueue（不存任务） 来任务即来即用，空 60s 回收 峰值任务多个 → 线程爆炸 OOM
newSingleThreadExecutor() 1 1 无界队列 单线程顺序执行 同无界队列积压 OOM
newScheduledThreadPool(n) n n DelayedWorkQueue（无界延迟队列） 定时/周期任务 延迟队列同样无界，周期任务异常吞掉

一句话总结：Fixed/Single 的问题是”无界队列任务积压”，Cached 的问题是”无上限线程”，Scheduled 是无界延迟队列——生产都不建议直接用 Executors。
官方文档也强调：更推荐用 ThreadPoolExecutor 手动指定有界队列、明确拒绝策略、自定义线程名（不然线上 jstack/Arthas 看线程全是 pool-1-thread-1，不知道是哪业务）。

5. 线程数怎么定 + 生产配置模板

估算口诀：

  • CPU 密集型（大量计算/循环）：core ≈ CPU核数 + 1。
  • IO 密集型（大量 DB/RPC/网络等待）：core ≈ CPU核数 × 2 或更准 N × (1 + W/C)（W=等待时间，C=计算时间）。
  • 无论哪类核心：队列必须有界（如 64~2000），否则拒绝策略形同虚设。

拿来即用的模板：

  • ThreadFactoryBuilder 来自 Guava；不引 Guava 就自写一个 ThreadFactory 设置 name。
  • 可以覆写 beforeExecute / afterExecute 钩子埋点（耗时、成功/失败、异常）。
  • 提交量大时先看 orderPool.getQueue().size() / getActiveCount() 判断积压，再决定是否扩容。

6. 使用注意点与线上排查

场景 要点
execute vs submit execute 异常由线程池异常处理器兜住；submit 异常包进 Future，不 get() 就永远”没动静”，很多”任务丢了”的真相就是 submit 后没人 get
优雅关闭 shutdown() → awaitTermination() 等待 → 超时再 shutdownNow() 打断
监控指标 getQueue().size()（积压）、getActiveCount()（活跃）、getLargestPoolSize()（历史峰值）、getCompletedTaskCount()（累计完成）
拒绝告警 自定义 handler 里计数 + 告警，别让拒绝发生在静默里
动态调参 setCorePoolSize / setMaximumPoolSize / setRejectedExecutionHandler 都可在运行期改，应对流量突增
线上坑 接口变慢 + 活跃线程持续 = max → 多半是下游 DB/RPC 慢或任务卡死；堆里对象暴涨 → 先怀疑队列里的任务对象

7. 常见面试题（背这组）

面试题 一句话要点
线程池有哪些参数？ 7 个：core / max / keepAlive+unit / queue / threadFactory / handler
提交任务执行流程？ 先核心线程 → 再尝试入队 → 队列满才扩到 max → 全满才拒绝
四种拒绝策略？ Abort(抛异常) / CallerRuns(调用者线程跑) / Discard(丢新) / DiscardOldest(丢最旧)
Fixed 和 Cached 区别？ 线程数固定 & 无界队列 vs 线程数无上限 & 不存任务
为什么生产不用 Executors？ 无界队列 / 无上限线程 → OOM，且线程不可见，推荐手写 ThreadPoolExecutor
核心线程能回收吗？ 默认不能，allowCoreThreadTimeOut(true) 才行
CPU/IO 密集线程数？ CPU 密集 N+1，IO 密集 2N 或 N×(1+W（等待）/C（计算）)
队列为什么要有限？ 防止任务积压无限吃内存，配拒绝策略做兜底
execute vs submit？ submit 返回 Future 并吞异常，必须 get() 才能看到
线程池排满怎么办？ 动态提升 core/max、换有界队列、自定义拒绝（告警+重投），最后还是冲掉调用方
怎么优雅关闭？ shutdown → awaitTermination → 超时 shutdownNow 兜底

8. 自测三问

  1. 任务提交时队列没满、线程数等于 core，会新建线程还是入队等待？根本原因是什么？
  2. CallerRunsPolicy 真能无条件”不丢任务”吗？它把任务扔给谁，副作用是什么？
  3. 一个 FixedThreadPool 线上突然 OOM，第一反应应该查任务队列还是线程数？哪条命令验证？
