一句话记住今天：50 万在线 = 50 万条长连接，真正的难点不是”连上”，而是”怎么找到他、把消息准确送过去、并且不丢不重不乱序”。 所以架构一定是四件事：Netty 网关扛连接（保持极轻）、MQ 解耦削峰（业务与推送分离）、Redis 存路由（uid → 网关节点）、ACK + seq 兜底可靠性。面试抓五块：① 容量估算；② Netty 接入层调优；③ 跨节点路由与精准推送；④ MQ 消息模型与可靠性；⑤ 断线重连与优雅发布。

先说结论：一张图看懂

三条链路记牢，面试时先说这个：

链路 路径 关键点
上行（发消息） 用户 → 网关 → MQ → 业务服务 网关只做转发，快速回 ACK
下行（收消息） 业务服务 → 查路由表 → RPC 直投网关 → 用户 精准投递，避免 MQ 广播放大 N 倍
广播（公告） 业务服务 → MQ 广播 topic → 各网关本地过滤 只有广播场景才用广播

一、容量估算：先把数字算出来

面试最忌一上来就画架构，先把量级算清楚（数量级对就行）：

指标 估算 依据
在线连接 50 万 用户端为主，客服端只有几千
单机连接 5 万（留 50% 余量） 8C16G + Netty，Linux 调优后单机可到 10 万+
网关台数 12 台 50万 ÷ 5万 = 10 台，再加 2 台用于滚动发布
心跳 QPS 约 1.7 万 50 万 ÷ 30s
消息 QPS 约 800，峰值 ×10 ≈ 8000 人均每 10 分钟 1 条：50万 ÷ 600s
单机内存 约 3~5 GB 每连接 20~50 KB（含堆外读缓冲）
坐席规模 3000~5000 人 1 坐席同时服务 100~150 个会话

结论：连接数是线性成本，消息量其实很小。50 万在线的真实压力是”50 万个 TCP 连接 + 1.7 万 QPS 心跳”，不是聊天内容本身。所以优化重点是连接成本（内存、fd、心跳），而不是消息吞吐。

二、接入层：Netty 怎么扛住单机 5 万连接

2.1 线程模型：EventLoop 绝对不能阻塞

Netty 默认 worker 线程数 = CPU 核数 × 2，一个 EventLoop 会绑定很多连接。只要有一个业务操作（查库、调 RPC、抢锁）卡在 IO 线程里，它绑定的几千条连接会一起卡住。所以铁律：

2.2 系统参数：不调参，1 万连接就崩

层面 参数 建议值 不调的后果
OS ulimit -n 100 万 fd 不够，第 1024 个连接就报 Too many open files
OS net.core.somaxconn 32768 accept 队列溢出，握手被丢
OS net.ipv4.tcp_max_syn_backlog 65535 SYN 队列满，连接超时
OS net.ipv4.tcp_tw_reuse 1 频繁重连时 TIME_WAIT 堆积
JVM -XX:MaxDirectMemorySize 显式设置（如 4g） 堆外内存无上限，被 Netty 吃光后 OOM
JVM GC G1 / ZGC 堆大对象多，Full GC 一次卡几秒，连接集体超时
Netty PooledByteBufAllocator 默认池化 频繁申请释放直接内存，GC 压力大

2.3 心跳：1.7 万 QPS 的隐形开销

心跳是长连接系统里最容易被低估的成本：

做法：

  • 服务端用 IdleStateHandler 做空闲检测，客户端定时发 ping，服务端只回 pong（不落库、不走 MQ、不进业务线程池）。
  • 间隔取 30~60s：移动网络 NAT 超时一般 5 分钟，30s 足够及时发现死连接，又不至于把 CPU 烧在心跳上。
  • 读空闲超过 2 × 心跳间隔 直接 ctx.close()，立刻释放连接与路由表。

2.5 接入层骨架代码

为什么不用 Spring WebSocket / Tomcat？Tomcat 的 NIO 连接器撑万级没问题，但几十万长连接下线程模型、内存占用、pipeline 可控性都不够：Netty 能自定义编解码、控制写缓冲水位、复用直接内存池，这些正是长连接系统的保命手段。

三、连接路由：整个系统最难的一块

网关是有状态节点——用户的连接只存在于某一台网关上。别人要给他发消息，必须先知道”他在哪台机器上”。

3.1 路由表：Redis 存 uid → gatewayId

数据 存储 说明
route:u:{uid} → gatewayId Redis String + TTL 心跳续约，天然容错宕机
route:s:{sessionId} → {agentId, uid} Redis Hash 会话绑定关系
agent:status:{agentId} Redis Hash 坐席在线 / 忙碌 / 小休
seq:{sessionId} Redis INCR 会话内消息序号
本地连接表 ConcurrentHashMap<uid, Channel> 只存本机连接，进程内 O(1)

3.2 跨节点投递：三种方案怎么选

这是面试最爱问的点：给用户推一条消息，怎么送到”持有他连接的那台网关”？

方案 原理 优点 缺点 适用
MQ 广播 + 本地过滤 每台网关独立消费组收全量消息，本地查表命中才推 完全解耦、容灾简单 消息放大 N 倍（12 台 → 12 倍投递），网络与 CPU 浪费大 小规模、广播场景
RPC 精准直投（推荐） 推送服务消费 MQ，查 Redis 路由表，gRPC 直投目标网关 无放大、延迟低、可控 需自研可靠投递（重试/超时/幂等）+ 服务发现 点对点聊天
Redis Pub/Sub 按 gateway 订阅频道 简单、够快 不可靠、无持久化，宕机丢消息 实时性高的轻量通知

生产做法是混合：点对点消息走”MQ 持久化 + RPC 精准直投”；全员公告、系统广播走 MQ 广播 topic，网关本地过滤。

四、MQ 在客服系统里到底干什么

4.1 四个作用，别只会说”削峰”

作用 说明
解耦 消息服务不需要知道谁在线、在哪台网关；网关不需要知道业务规则
削峰 活动瞬时 10 倍流量先进 MQ 排队，业务服务按自己的速度消费
广播 公告、系统通知、坐席状态变更一次投递、多方消费
可靠 + 有序 持久化 + 分区有序 + 重试，是”不丢不乱序”的基础

4.2 topic 设计

topic 分区键 消费者 用途
chat_msg sessionId 消息服务、质检服务 聊天消息（同一会话有序）
chat_broadcast 随机 各网关（广播模式） 公告、系统通知
session_event sessionId 会话服务 会话创建 / 关闭 / 转接
agent_event agentId 坐席服务 坐席上下线、状态变更
chat_delay sessionId 会话服务 延迟消息：会话超时关闭、满意度评价

4.4 顺序、幂等、重试、死信

问题 方案
同一会话消息乱序 分区键 = sessionId（RocketMQ 顺序消息 / Kafka 同 key 同分区）+ 服务端 seq 递增
重复消费 msgId 唯一索引 / Redis SETNX msg:{msgId} 去重，消费逻辑幂等
消费失败 有限次重试（指数退避）→ 超过阈值进死信队列 → 定时任务补偿
消息堆积 监控 lag；扩容消费者（分区数 ≥ 消费者数）；网关侧降级为”只推关键消息”
消息体过大 图片/文件只传 URL，消息体控制在 1KB 内

五、消息可靠性：不丢、不重、不乱序

IM 的行业标准答案是：至少一次投递 + 客户端 ACK + 服务端幂等去重 + 客户端按 seq 排序，而不是硬追”精确一次”。

5.3 断线重连：靠 seq 做补偿

关键点：可靠性的兜底不在长连接上，而在”重连后按 seq 补拉”这条链路上。长连接只保证”大部分时候快”，seq 保证”最终一定全”。

六、客服业务侧的设计

6.1 坐席状态机

6.2 会话分配算法

算法 规则 优点 缺点
轮询 按坐席列表顺序 实现简单 不考虑负载，可能忙死一个
最少会话优先 取当前会话数最少的坐席 负载均衡好 热门坐席被冷落、体验不均
技能组匹配 按问题类型 + 技能标签筛选后取最少会话 转化率高、专业对口 需要技能标签体系
权重 / 优先级 VIP 用户优先分给金牌坐席 商业价值高 规则复杂

生产上一般是技能组匹配 + 最少会话优先 + 兜底轮询三层，坐席状态、会话数都放 Redis（INCR/DECR + Lua 保证原子）。

6.3 排队、转接与超时

场景 处理
无空闲坐席 进排队队列（Redis ZSet，按进入时间排序），前端展示排位与预计等待
用户等太久 超时阈值（如 60s）→ 触发兜底：留言、机器人接待、转其他技能组
客服转接 更新 route:s:{sessionId}，通知双方；历史消息随会话走
会话超时 延迟消息（30 分钟无消息）→ 关闭会话 + 推送满意度评价
坐席突然离线 监听 agent_event，把其会话批量重新入队或转接

6.4 客服端的特殊性

  • 坐席人少（几千）但消息集中：一个坐席同时 100+ 会话，下行量是普通用户的几十倍，网关推送要按坐席维度做聚合与限流。
  • 客服端通常要多端在线（PC + 移动端）：同一 uid 对应多个 Channel，路由表要存 List<gatewayId>，推送时全部投递。
  • 坐席侧对延迟更敏感（要秒回客户），对可靠性要求也更高（漏一条 = 客户投诉）。

七、优雅上下线：发版不断连

50 万连接最怕”发布重启”，一步没做好就是重连风暴：

同理，网关宕机时它的 5 万连接会瞬间重连到其他节点，所以：

  • 客户端重连要 指数退避 + 随机抖动（1s、2s、4s…上限 30s）；
  • 接入层对新建连接做限流（按 IP / 全局令牌桶），把”重连风暴”削平；
  • 至少预留 20% 冗余容量，防止一个节点挂了把其他节点压垮。

八、难点清单（面试重点）

# 难点 为什么难 解法
1 单机连接数瓶颈 fd、内存、心跳三重限制 Linux 调参 + 池化内存 + 单机 5 万留余量 + 水平扩展
2 跨节点消息投递 网关有状态，连接不共享 Redis 路由表 + RPC 精准直投（或 MQ 广播 + 本地过滤）
3 广播风暴 / 消息放大 N 台网关 × 全量消息 点对点用直投，只有广播用广播 topic + tag 过滤
4 消息不丢不重不乱序 网络不可靠 + 重试 + 多分区 分区键 = sessionId、seq 递增、ACK、msgId 幂等去重
5 断线重连补偿 断线期间消息可能丢 lastSeq + 上线补拉 + 客户端去重排序
6 慢客户端拖垮网关 写缓冲无限增长 → OOM WriteBufferWaterMark + isWritable() 降级
7 心跳成本 50 万 × 频繁心跳 = 巨量 QPS 心跳 30~60s、只回 pong、不进业务线程池
8 优雅发布 重启导致重连风暴 摘流量 + 通知重连 + 抖动 + drain + 冗余容量
9 安全 WS 无同源限制、易被刷 握手阶段 token 鉴权、单连接限流、消息大小限制、内容审计
10 可观测性 长连接问题难复现 连接数、心跳超时率、推送 P99、MQ lag、堆外内存监控

九、参数与设计速查表

项 建议值 备注
单机连接数 5 万（上限 10 万） 8C16G，留 50% 余量
心跳间隔 30~60s 读空闲 90~120s 踢连接
消息体大小 ≤ 1KB 图片/文件只传 URL
WriteBufferWaterMark 32KB / 64KB 高水位后不再写
WS 最大帧 64KB maxFramePayloadLength
路由表 TTL 心跳间隔 × 2~4 如 120s
MQ 分区键 sessionId 保证会话内有序
重连退避 1s→30s 指数退避 + 抖动 防惊群
发布 drain 30~60s 分批摘除
离线消息保留 7 天热 + 冷存储 超期转 ES / 对象存储

十、面试问答

Q1：为什么用 Netty，不用 Spring WebSocket？
Tomcat 的 NIO 能撑万级连接，但几十万连接下线程模型和内存不可控。Netty 的主从 Reactor、可定制 pipeline、池化直接内存、写缓冲水位控制，是长连接系统必需的。

Q2：怎么知道用户在哪个节点？
Redis 路由表 route:u:{uid} → gatewayId，连接建立时写入、心跳续约（TTL 120s）、断开时删除；网关宕机靠 TTL 自动过期。

Q3：跨节点消息怎么投递？
推荐”推送服务消费 MQ → 查路由表 → gRPC 直投目标网关”；MQ 广播 + 本地过滤只适合小规模或广播场景，否则消息放大 N 倍。

Q4：消息会丢吗？会重复吗？
采用”至少一次 + 客户端 ACK + msgId 幂等去重 + 重连按 seq 补拉”，正常不会丢；重复是允许的，靠 msgId 和 seq 在客户端/服务端去重。

Q5：怎么保证同一会话消息有序？
MQ 分区键取 sessionId（同一会话进同一分区、单线程顺序消费），再叠加服务端 seq 递增，客户端按 seq 排序兜底。

Q6：50 万在线要多少机器？
网关 10 台（每台 5 万）+ 2 台冗余；业务服务按消息 QPS（约 8000 峰值）几台就够；Redis 主从 + 集群；MQ 3 主 3 从。瓶颈在连接，不在消息。

Q7：怎么做到发版不断连？
摘流量 → 推 reconnect 指令 → 客户端随机抖动重连 → 等 30~60s drain → 关服务；同时预留冗余容量，防止宕机节点把压力转移给别人。

Q8：为什么网关不做业务？
网关是 12 台 × 5 万连接的入口，任何一次查库/慢调用都会阻塞 EventLoop，连带几千条连接卡死。网关只做”鉴权、编解码、转发、写回”，业务全部下沉到 MQ 下游。

一句话总结

Netty 负责”把 50 万条连接稳稳拿住”，Redis 负责”知道人在哪”，MQ 负责”业务与推送解耦、削峰与可靠”，而 seq + ACK + 补拉负责”一条都不少、一条都不乱”。 记住这条主线，50 万在线的客服系统就是一道可以讲 20 分钟的送分题。
