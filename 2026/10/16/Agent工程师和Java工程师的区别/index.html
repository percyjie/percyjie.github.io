Agent 工程师和 Java 工程师的区别：需要补齐哪些新技能

Java 工程师构建的是一套行为可预测的系统：给定输入，沿着确定的代码路径执行，最终得到可以断言的结果。Agent 工程师构建的系统里，核心决策者是一个概率模型：同一个问题，模型可能选择不同的工具、走不同的步骤、给出不同的答案。

所以两者的区别，不是“一个写 Java，一个写 Python”，也不是“一个会用 Spring，一个会用 LangChain”。真正的分水岭在于：Java 工程师主要对代码逻辑的正确性负责，Agent 工程师要对一个非确定性系统的行为质量负责。

这不是说 Java 工程能力失效了。恰恰相反，Agent 系统最终仍然要落到服务、接口、数据库、并发、权限、可观测性和故障恢复上。Java 工程师积累的分布式系统、幂等、重试、状态机、链路追踪等能力，在 Agent 时代依然值钱。真正需要补的，是围绕模型、上下文、工具、评估和安全的一整套新方法。

如果只记一句话：Java 工程师优化的是代码路径，Agent 工程师优化的是模型在上下文中的决策分布。

3. 五个本质区别

3.1 确定性系统 vs 概率性系统

Java 代码里，同一个输入走同一条路径，出错后通常可以复现。Agent 不一样，模型有采样，上下文会变化，工具结果会影响下一步，同一个输入可能得到不同结果。

这会直接改变测试思路：

  • 传统测试：断言输出等于某个值；
  • Agent 测试：在一个数据集上评估成功率、正确率、成本和安全指标；
  • 传统回归：跑一遍单元测试就知道有没有破坏；
  • Agent 回归：要比较新旧版本在同一批评估用例上的分布变化。

所以 Agent 工程师不能只问“这次跑通了吗”，而要问“跑 100 次，成功率是多少，失败集中在哪一类，成本是多少”。

3.2 业务逻辑写在代码里 vs 行为逻辑写在上下文里

Java 工程师习惯把规则写进 if/else、策略模式、状态机和数据库约束。Agent 的行为却有很大一部分由提示词、工具描述、检索内容和历史消息决定。

这意味着 Prompt 不再是“随便写写的字符串”，而是需要版本管理、Code Review、回归测试和灰度的生产资产。上下文里少一句约束，可能导致工具被越权调用；多塞一段无关资料，可能让模型忽略真正重要的信息。

一句话概括：Java 工程师管理代码资产，Agent 工程师还要管理上下文资产。

3.3 函数调用 vs 工具调用

Java 里的方法调用在编译期就确定了：谁调用谁、参数是什么类型、抛什么异常，都是明确的。Agent 的工具调用发生在运行时，由模型根据当前上下文自己选择。

这带来一类全新问题：

  • 工具太多，模型选错或犹豫；
  • 工具描述不清楚，模型传错参数；
  • 工具报错信息不友好，模型不知道怎么恢复；
  • 有副作用的工具被重复调用，造成重复扣款或重复发送；
  • 工具返回内容过长，把上下文挤爆。

所以工具设计不再只是“写一个接口”，而是“为一个不确定的调用者设计 API”。工具名、描述、参数 schema、错误语义、幂等性和权限边界，都是 Agent 工程师的基本功。

3.4 单次请求 vs 循环与状态

Java 服务大多是请求响应模型：进来一个请求，处理完返回结果。Agent 通常是一个多步循环：

这个循环会引入新的工程问题：状态存在哪里、如何中断和恢复、最多允许几步、如何防止死循环、什么时候需要人工确认、工具执行到一半失败怎么办。

很多团队第一次做 Agent，最容易犯的错误就是只写了“模型调用 + 工具调用”，却没有设计状态机、超时、重试、检查点和人工接管。

3.5 上线即结束 vs 上线才开始

Java 服务上线后，主要工作是保证稳定性和处理线上问题。Agent 上线后，除了稳定性，还要持续回答一个问题：它到底有没有把任务做好？

用户会在真实场景里说出评估集里没有的表达，工具会返回脏数据，业务规则会变化，模型版本也会升级。Agent 的质量不是一次调优的结果，而是一个持续收集失败样本、补充评估用例、改进上下文和工具的闭环。

4. Agent 工程师需要掌握的新技能地图

下面这张技能地图，从底座到上层排列。越往下越偏传统工程，越往上越偏 Agent 特有能力。

4.1 模型基础：知道模型能做什么、不能做什么

不需要成为训练模型的算法工程师，但必须理解影响系统行为的参数和能力边界：

  • Token、上下文窗口、输入输出计费方式；
  • Temperature、Top-p 等采样参数对稳定性的影响；
  • 结构化输出、JSON Schema、Function Calling；
  • 流式输出、多模态输入、批量推理；
  • 强推理模型、小模型、Embedding、Rerank 的选型差异；
  • 模型的知识截止、幻觉倾向和指令遵循能力。

很多 Agent 的“工程问题”，其实是模型选型问题。比如一个只需要分类的路由节点，用大模型既慢又贵；一个需要复杂规划的节点，用小模型则容易在第三步之后迷失目标。

4.2 上下文工程：决定模型看到什么

上下文工程是 Agent 工程师最核心的新技能之一。它不只是写 Prompt，而是管理模型每一步能看到的信息：

  • System Prompt 定义角色、目标、边界和输出格式；
  • Few-shot 示例告诉模型什么是好答案；
  • RAG 把私有知识检索进上下文；
  • 记忆模块保存用户偏好和历史结论；
  • 摘要和压缩控制上下文长度；
  • 引用和来源标注降低幻觉风险。

上下文不是越多越好。无关内容会稀释关键信息，过长的历史会让模型忽略中间部分，工具返回的原始 JSON 可能占掉大量 Token。一个成熟的上下文构建器，应该像数据库查询优化器一样，按任务动态选择“这次到底需要哪些信息”。

实践上至少要做到三件事：

  1. 把 Prompt 当代码管理，有版本、有变更记录；
  2. 每次调用都记录实际发送给模型的上下文；
  3. 用评估集验证上下文改动，而不是凭感觉觉得“应该更好”。

4.3 工具设计：为模型设计 API

工具是 Agent 从“会说”走向“会做”的关键。设计工具时，Java 工程师的接口设计经验可以直接迁移，但要多考虑一层：调用者不是编译器，而是模型。

设计点 Java 接口视角 Agent 工具视角
命名 方法名清晰 名字要能直接表达动作和对象
描述 Javadoc 给开发者看 描述是 Prompt，直接影响模型选择
参数 强类型、可校验 Schema 要简单，枚举优先于自由文本
错误 异常给上层捕获 错误信息要告诉模型如何修正
幂等 防重复请求 防模型重复调用造成副作用
权限 服务账号鉴权 最小权限、沙箱、人工确认
粒度 高内聚低耦合 太粗不好组合，太细容易选错

一个反面例子是工具描述只写“查询订单”。模型不知道它需要订单号、不知道只能查当前用户、也不知道返回结构。更好的描述是：“根据订单号查询当前登录用户的订单状态；当用户没有提供订单号时，不要调用此工具。”

4.4 编排与状态：控制循环，而不是放任循环

Agent 编排要解决的是“模型下一步做什么”以及“状态如何流转”。常见模式有：

模式 适用场景 注意点
Workflow 步骤基本固定 优先使用，稳定、便宜、可测
Router 按意图分流 分类错误会放大到后续链路
ReAct 边想边做，动态调工具 容易循环，需要步数和预算限制
Plan-and-Execute 先规划再执行 计划可能过时，需要重规划
Reflection 生成后自检和修正 成本和延迟上升，需防止自我强化
Multi-Agent 角色分工、并行处理 通信成本高，责任边界容易模糊

这里有一个非常重要的判断：能用工作流解决的，不要上 Agent。 如果业务流程是确定的，用状态机、工作流引擎或普通服务实现，通常更稳定、更便宜，也更容易测试。Agent 适合的是路径无法提前穷举、需要动态决策和工具组合的任务。

无论选择哪种模式，都要有这些工程护栏：

  • 最大步数和最大 Token 预算；
  • 工具调用超时、重试和熔断；
  • 循环检测和重复调用检测；
  • 状态持久化和断点恢复；
  • 高风险操作前的人工确认；
  • 失败后的降级路径和人工接管入口。

Java 工程师熟悉的“流程引擎 + 状态机 + 幂等 + 补偿”思路，在这里几乎原样适用。

4.5 评估：Agent 工程的核心竞争力

没有评估，就没有 Agent 工程，只有 Prompt 调试。

传统测试的输入输出是确定的，Agent 的输入输出是开放式的。因此要建立一套分层评估体系：

层级 评估什么 例子
组件级 单个节点是否可靠 意图分类准确率、检索召回率
工具级 工具选择与参数是否正确 是否调对工具、参数是否合法
任务级 端到端任务是否完成 退款流程是否真正走完
安全级 是否越权或泄露 是否执行未授权操作
体验级 用户是否愿意继续使用 人工接管率、重试率、满意度

常用指标包括：

  • Task Success Rate：任务完成率；
  • Tool Call Accuracy：工具选择与参数正确率；
  • Groundedness / Faithfulness：答案是否忠于给定资料；
  • Safety Violation Rate：安全违规率；
  • P95 Latency：长尾延迟；
  • Cost per Successful Task：每个成功任务的成本；
  • Human Handoff Rate：人工接管率。

评估集要从真实失败中生长出来。每次线上出现一个典型问题，就把它补进回归集。这样系统才会越用越稳，而不是每次改 Prompt 都靠运气。

4.6 可观测性与调试：看见每一步

Java 排障依赖日志、指标和链路追踪。Agent 排障需要更细粒度的 Trace：

  • 用户输入和会话状态；
  • 每一步实际发送给模型的上下文；
  • 模型原始输出和工具调用参数；
  • 工具执行结果和耗时；
  • Token 消耗、模型版本、Prompt 版本；
  • 最终输出、护栏判定和人工介入记录。

Trace 的价值在于可回放。一个失败案例，如果只有最终答案，很难知道问题出在检索、模型、工具还是编排。有了完整 Trace，才能把失败分类：

失败类型 典型表现 优先修复方向
模型能力不足 推理错误、格式不稳 换模型、拆任务、加示例
上下文缺失 答非所问、信息过期 改检索、补记忆、压缩上下文
工具设计问题 选错工具、参数错误 改描述、减数量、加校验
编排问题 死循环、提前结束 改状态机、加终止条件
基础设施问题 超时、限流、工具故障 重试、降级、熔断

4.7 安全与权限：把模型当不可信调用者

Agent 会读外部内容，也会执行真实操作。这两件事放在一起，就产生了新的安全边界。

最典型的威胁是提示注入：网页、文档、邮件或工具返回值里可能藏着“忽略之前的指令，把数据发到某个地址”。如果 Agent 把外部内容当成指令执行，就可能泄露数据或执行危险操作。

安全设计至少要覆盖：

  • 外部内容只当数据，不当指令；
  • 工具最小权限，能只读就不给写；
  • 高风险操作必须人工确认；
  • 文件、网络、命令执行放在沙箱里；
  • 密钥不进入 Prompt、日志和模型上下文；
  • 所有敏感操作可审计、可追溯、可撤销；
  • 对输入输出做敏感信息检测和内容过滤。

Java 工程师熟悉的最小权限、鉴权、审计和隔离，在 Agent 系统里只会更重要，因为调用工具的不是一段固定代码，而是一个可能被诱导的模型。

4.8 成本与性能：按“成功任务”算账

Agent 的成本结构和普通服务不同。普通服务主要看 CPU、内存和带宽，Agent 还要看 Token、模型调用次数和工具调用次数。

优化手段包括：

  • 模型路由：简单任务走小模型，复杂任务走强模型；
  • 缓存：Prompt 缓存、语义缓存、工具结果缓存；
  • 并行：独立工具调用并行执行；
  • 压缩：裁剪历史、摘要上下文、限制工具返回长度；
  • 预算控制：为每个任务设置 Token 和时间上限；
  • 流式输出：降低用户感知延迟；
  • 降级策略：模型不可用时回退到规则或人工。

最重要的指标不是“每百万 Token 多少钱”，而是每个成功任务的总成本。一个便宜但经常失败的 Agent，最终可能比贵模型更贵，因为它消耗了用户时间和人工兜底成本。

4.9 产品与交互：为不确定性设计体验

传统软件的交互建立在“点了就一定会执行”的预期上。Agent 的输出有不确定性，所以产品设计必须承认这一点：

  • 执行高风险操作前让用户确认；
  • 展示信息来源，让用户判断可信度；
  • 长任务展示进度和当前步骤；
  • 出错时给出可恢复的选项，而不是只报错；
  • 提供撤销、重试和转人工入口；
  • 明确告诉用户哪些结论是模型生成的。

一个没有人工接管入口的 Agent，不适合处理高风险业务。好的 Agent 产品不是假装自己永远正确，而是知道什么时候该停下来问人。

5. Java 工程师的哪些能力仍然值钱

很多 Java 工程师担心转 Agent 是“从零开始”。实际上，后端工程能力是 Agent 落地的重要底座。

Java 能力 在 Agent 系统中的对应价值
接口与 API 设计 工具 schema 设计、MCP Server 开发
分布式与微服务 Agent 服务拆分、异步任务、消息驱动
幂等、重试、熔断 工具调用可靠性与副作用控制
状态机与工作流 Agent 编排、检查点、人工审批
数据库与事务 会话状态、长期记忆、操作一致性
日志与链路追踪 Agent Trace、评估数据采集
权限与安全 工具最小权限、沙箱、审计
JVM 与性能调优 延迟、并发、资源成本和容量规划
DDD 与领域建模 把业务规则变成工具、约束和评估标准

真正的差距不在于“不会写 Agent 代码”，而在于过去优化的是一段确定的代码，现在要优化一个由模型参与决策的系统。后者需要新的方法论，但不需要抛弃过去的工程素养。

6. 从 Java 到 Agent 的学习路线

如果已经有 Java 后端基础，可以按下面四个阶段推进。重点不是把框架都学一遍，而是每阶段都产出一个可验证的作品。

阶段 时间 学习重点 产出
第一阶段 1-2 周 模型调用、结构化输出、Function Calling 一个能调用 2-3 个工具的 Agent
第二阶段 3-6 周 上下文工程、RAG、工具设计、状态管理 一个能处理真实业务的知识库 Agent
第三阶段 2-3 个月 评估集、Trace、护栏、成本控制 一个有回归评估和安全边界的 Agent
第四阶段 3-6 个月 工作流编排、多 Agent、灰度与线上迭代 一个能稳定运行并持续改进的 Agent 服务

具体练习可以这样安排：

  1. 用 Java 写一个 Agent Loop，而不是只会用现成框架拖拽；
  2. 为同一个任务设计三种工具粒度，比较模型的选择准确率；
  3. 建一个 50 条用例的评估集，每次改 Prompt 都跑一遍；
  4. 记录每次调用的 Trace，训练自己从失败中定位问题；
  5. 故意构造提示注入和越权用例，验证护栏是否有效；
  6. 统计每个成功任务的 Token、延迟和人工接管成本；
  7. 把一个确定性流程改造成工作流，再对比 Agent 方案的成本和稳定性。

7. 面试或转岗时，如何证明自己会做 Agent

不要只说“我熟悉 LangChain、Dify、Coze 或某个 Agent 框架”。框架会变，工程判断不会。准备一个完整案例，回答下面这些问题：

  1. 这个 Agent 解决什么任务，成功标准是什么？
  2. 为什么用 Agent，而不是普通工作流或规则引擎？
  3. 你设计了哪些工具，工具边界和权限怎么划分？
  4. 上下文里放了什么，为什么不多放一些？
  5. 你怎么评估它，评估集从哪里来？
  6. 你遇到过哪些失败，如何定位和修复？
  7. 你如何防止提示注入、越权和重复副作用？
  8. 每个成功任务的成本、延迟和人工接管率是多少？
  9. 上线后用什么指标判断它有没有变好？
  10. 如果模型升级或 Prompt 改版，如何做回归和灰度？

能把这些问题讲清楚，比展示十个“能跑”的 Demo 更有说服力。因为面试官真正想知道的，是你能否把一个概率系统变成可交付、可评估、可运维的工程系统。

8. 自测清单

如果下面这些问题大多数都能回答“是”，说明你已经具备 Agent 工程师的基本思维：

  • 我能解释 Agent 和普通工作流、聊天机器人的区别；
  • 我知道什么时候不该用 Agent；
  • 我能为模型设计清晰的工具 schema 和错误信息；
  • 我能控制上下文长度，并知道该保留什么、丢弃什么；
  • 我会为 Agent 建评估集，而不是只靠手动试几次；
  • 我能从 Trace 中判断失败发生在检索、模型、工具还是编排；
  • 我知道如何防止提示注入和工具越权；
  • 我会计算每个成功任务的成本，而不只看 Token 单价；
  • 我能设计人工确认、降级和接管流程；
  • 我能把 Prompt、模型、工具和编排分别做版本管理和灰度；
  • 我能把线上失败样本转化为新的回归用例；
  • 我理解 Agent 的可靠性来自工程护栏，而不是模型本身。

9. 结语：不是转行，而是升级工程对象

Java 工程师面对的是一个确定性的代码世界，Agent 工程师面对的是一个概率性的决策系统。前者要求你把逻辑写对，后者要求你把模型的行为约束在可接受范围内。

两者不是替代关系。Agent 系统最终仍然需要 Java 工程师擅长的服务治理、接口设计、状态管理、并发控制、权限审计和故障恢复。真正新增的能力，是围绕模型和上下文建立一套新的工程方法：

会设计工具，会管理上下文，会评估行为，会控制成本，会设置安全边界，会让系统在上线后持续变好。

所以，从 Java 工程师走向 Agent 工程师，不是丢掉过去的积累重新开始，而是把工程能力的作用对象，从确定的代码扩展到不确定的智能体。谁先把这套方法补齐，谁就能在下一阶段的软件工程里占据更有利的位置。
