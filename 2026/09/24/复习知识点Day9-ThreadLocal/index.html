复习知识点Day9：ThreadLocal

一句话记住今天：ThreadLocal = 「线程私有的上下文储物柜」。复习抓三条主线：① 结构（Thread → ThreadLocalMap → Entry，key 是弱引用的 ThreadLocal、value 是强引用的对象）；② 内存泄漏（key 被回收后 value 没人清理，线程池场景必须 remove）；③ 异步获取（默认拿不到 → InheritableThreadLocal 只对 new Thread 拷贝一次 → 线程池要用 TTL/显式传参）。

1. ThreadLocal 是什么：先 5 分钟找回记忆

  • 作用：给”同一个线程”开辟一块私有变量空间，线程内随便读写，线程之间互不可见。
  • 本质：不是把值复制给每个线程，而是每个 Thread 自己持有一个 ThreadLocalMap，ThreadLocal 对象只是这个 map 的 key（第二节细讲）。
  • 典型使用场景：
    1. 每个请求/线程的独立上下文（登录用户、requestId、traceId、MDC 日志）；
    2. Spring 事务：DataSourceTransactionManager 把连接按线程存起来，保证一个事务内永远拿到同一个连接；
    3. SimpleDateFormat 等非线程安全对象的”每线程一份”；
    4. 避免层层方法传参（context 透传）。

基础 Demo：

反直觉点：变量声明是静态/全局的，但”值”属于每个线程——这就是面试最爱挖的第一个点。

关键对应关系（背下来）：

组件 是谁 引用强度 作用
Key ThreadLocal 实例本身（不是字符串） 弱引用（继承 WeakReference） 定位/区分不同的 ThreadLocal
Value 线程里存的对象 强引用 真正存的值
Entry 弱引用子类 — 把 key + value 绑在一起放进数组

2.2 设计哲学：为什么 key 用弱引用？

假设 key 用强引用：ThreadLocal 对象被业务代码丢弃后（比如局部变量用完），由于 Thread 活着 → ThreadLocalMap 活着 → Entry 强引用 key → ThreadLocal 和它的 value 全被拖住、永远无法回收。

尤其 Web 容器 + 线程池场景：每处理一个请求 set 一个局部 ThreadLocal，线程不销毁，引用链永远在；如果 value 还挂着一个 ClassLoader，整块类的元数据都无法卸载，这就是经典的”热部署/长驻线程 OOM”来源。

改成弱引用 key 后：

  • 业务代码不再引用 ThreadLocal（外部强引用消失）→ GC 时 key 被回收，Entry.get() 返回 null，该条目立刻能被识别为过期条目（stale entry）；
  • value 仍然是强引用，不会被自动回收——这正是内存泄漏（第 3 节）真正的根源；
  • 于是设计达成：key 的泄漏被设计消灭了，value 的泄漏留给”访问路径上的清理 + 显式 remove”兜底。

一句话面试回答：”Entry 复用 WeakReference 当 key，是为了让 ThreadLocal 对象本身的存亡只由业务代码决定；value 保持强引用是为了使用期间不被 GC 抢走，代价是 value 需要手动 remove 兜底。”

2.3 Hash 定位与开放寻址（了解即可）

  • 每个 ThreadLocal 创建时分配一个 threadLocalHashCode，步长是魔术数 0x61c88647（黄金分割数），让散列均匀；
  • 定位：index = hash & (len - 1)，哈希冲突时线性探测向后找空位，而不是像 HashMap 一样拉链；
  • size > 2/3 * len 触发清理 + 扩容（长度仍为 2 次幂）。

3. 内存泄漏（重点二）：到底谁漏了

3.1 泄漏的两个主角

对象 会不会漏 原因
key（ThreadLocal） 基本不会 弱引用，外部引用消失即被 GC
value（set 的值） 会漏 Entry 数组强引用 value；只有 Thread 消亡或显式 remove() 才被解除

泄漏链条（必背）：

3.2 源码里已有的”自动清理”机制

JDK 不是完全不管，而是”用的时候顺手清“（注意：不是守护线程定时清）：

触发点 清理动作
get() 撞到 key 为 null 的过期槽 expungeStaleEntry 清掉该 entry 并做局部整理
set() 撞到过期槽 replaceStaleEntry 替换旧 key 并清理、cleanSomeSlots 顺手清几个
remove() 显式删除（最可靠的清理）
扩容 / rehash() expungeStaleEntries 全表清理

关键局限：这些都是”访问路径上顺手清理”，并不会主动轮询。如果线程存活且再也不碰那个 ThreadLocal，过期 entry 就一直堆着——线程池空闲线程就是典型案例。

3.3 为什么”线程池 + 不 remove”一定会出问题

  • 每次任务都在旧任务：thread 的 map 里留下一个新 ctx（大对象）；
  • 池里只有 4 个线程 → 槽位不断被新对象顶替又留下，内存只涨不降，长期积累 = OOM；
  • 同时还有脏值问题：下一个任务没重新 set 时，get() 会拿到上一个任务留下的值。

3.4 正确姿势（面试背下来）

  1. 必用 try-finally + remove：
  1. 只在合适的地方用（请求上下文、连接绑定、事务上下文），别把大对象/池化的连接塞进长生命周期线程的 ThreadLocal。
  2. 配合线程池：任务里 remove，或直接上 TTL（第 4 节）让框架自动 restore。
  3. 线上排查：jmap -dump + MAT 看 java.lang.ThreadLocal$ThreadLocalMap 的 retained size。

错误回答：”ThreadLocal 用的是弱引用，所以不会泄漏” ❌
正确回答：”key 弱引用防的是 ThreadLocal 对象自身的泄漏；value 仍是强引用，线程池场景必须 remove，否则 value 泄漏 + 脏值。”

4. 异步任务怎么拿到 ThreadLocal（重点三）

4.1 一句话结论

异步（线程池 / 新线程）默认拿不到提交线程的 ThreadLocal，手工补传。要传就要靠：显式传参、InheritableThreadLocal（仅 new Thread）、或阿里 TTL。

4.2 默认拿不到：值绑定在”执行线程”上

因为 ThreadLocal.get() 按 Thread.currentThread() 取 map；Runnable 跑在池线程，自然拿不到提交线程的 map。

4.3 InheritableThreadLocal：只能”生孩子”，不能”借”

new Thread() 时，父线程的 inheritableThreadLocals 会被 createInheritedMap 拷给子线程：

也就是说它只在线程诞生那一刻拷贝一次：线程池线程已被池创建，第二次提交也不再拷贝 → 线程池场景直接失效，还自带”脏值”风险。

4.5 不用的常见异步场景速查

场景 推荐做法
Spring @Async 异步方法 把需要值写成参数显式传入；或自定义 TaskDecorator 配合 TTL
日志 MDC 丢 traceId 任务包装 TTL / TtlRunnable 包一层，或 MDC 配合 TTL 实现
CompletableFuture 链式异步 每一段异步任务都包 TTL（或显式传参）
新线程 new Thread InheritableThreadLocal 够用；线程池一律 TTL
跨线程大量对象共享 别用 ThreadLocal，用上下文对象显式传参 + ConcurrentHashMap 按 requestId 存

5. 高频面试题速查

问题 一句话答案
ThreadLocal 里 value 放堆还是栈 堆。ThreadLocal、ThreadLocalMap、value 都是对象
key 为什么弱引用 防止 ThreadLocal 对象本身被线程长生命周期拖住回收；value 必须强引用（使用中不能被 GC）
ThreadLocal 会内存泄漏吗 会（value）。前提：线程存活 + 不再访问 + 不 remove（线程池最典型）
线程池里不 remove 为什么会脏 线程被复用，map 里还留着上一个任务的值，新任务 get 会读到旧值
InheritableThreadLocal 能解决线程池吗 不能；它只在 new Thread 那一刻拷贝一次
异步怎么传 TTL 包装任务 / 包装线程池 / 显式传参；面试说”TTL 的 capture→replay→restore”就是亮点
ThreadLocal vs 普通共享变量 ThreadLocal 是”空间隔离”（各线程一份）；普通共享变量是”时间互斥”（加锁协调），两者用途不同

6. 速查表（背完收工）

考察点 一句话答案
数据放哪 Thread 对象的 threadLocals（堆上），ThreadLocal 只是 key
key / value 引用 key 弱引用、value 强引用
泄漏点 长驻线程 + 不 remove + 大对象 value
防御 try/finally remove；限制使用场景
异步获取 默认 null；new Thread 用 Inheritable；线程池用 TTL
排查 jmap -histo 看 ThreadLocal$ThreadLocalMap，MAT 查 stale entry
