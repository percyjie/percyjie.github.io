复习知识点Day11：MQ顺序可靠与延迟

一句话记住今天：MQ 三大保命技能 = 顺序（分区/队列 + 单一消费者串行）+ 可靠（生产端确认 + Broker 持久化 + 消费端 ack + 幂等）+ 延迟（延迟消息 / TTL+死信 / Redis 延迟队列）。面试抓三条主线：① 顺序性；② 可靠性；③ 延迟实现。

1. 为什么面试必考 MQ 的”顺序 + 可靠 + 延迟”

  • MQ 三大价值：解耦（上下游互不感知）、异步（削峰填谷）、广播（一写多读）。
  • 但引入 MQ 就引入三个”幺蛾子”：消息乱序、消息丢失、消息迟到/重复消费——它们正是生产事故高频来源，所以是面试必考。
  • 本篇用同一套”生产端 → Broker → 消费端”三段闭环把三件事讲透。

2. 消息顺序性（重点一）

2.1 先分清：全局有序 vs 局部有序

类型 含义 吞吐 适用
全局有序 所有消息严格按发送顺序消费 低（只能一个队列） 极少见，如 binlog 同步
局部有序 同一业务 key（订单/用户/设备）内有序 高（可并行分片） 生产 99% 场景

一句话：保证”同一个订单的消息有序”就够了，不用全站有序。

2.2 保证顺序的四道关口（背下）

  • RocketMQ：MessageQueueSelector 按 key 选队列 + MessageListenerOrderly 顺序消费；
  • Kafka：同一 key 用固定 partition（默认按 key hash）+ 消费端不加并行线程；
  • RabbitMQ：单队列 + 单消费实例（多 consumer 抢同一个队列就是乱序）。

2.3 各中间件的顺序支持（对比表）

中间件 支持方式 注意事项
RocketMQ 队列选择器 + 顺序消费 MessageListenerOrderly 全局顺序要 topic 只用单队列
Kafka 分区内天然有序（key 路由分区） 跨分区乱序；重试（Retries）可能乱
RabbitMQ 单队列 FIFO 多 consumer 即乱序；要用单消费者 + 串行处理

2.4 顺序易失守的坑（面试”避坑”答案）

  1. 消费失败重试跳序：队列 A 消费第 1 条失败，重试放回队尾，第 2 条先消费 → 顺序乱。顺序消费必须先成功再往下，失败阻塞重试。
  2. 并行消费：同一队列开了多个消费者/多线程，天然乱序。
  3. 生产端乱序发送：网络重试可能先发后到。同一 key 必须同步等 ack 或幂等序列号重排。
  4. 业务状态兜底：业界最终方案还是”业务侧状态机 + 幂等”，乱序消息能被识别并拒绝（如订单只能 待支付→已支付 单向流转）。

3. 消息可靠性（重点二）

3.1 三段式防线总览（核心框架）

3.2 生产端可靠性

机制 作用
同步发送 + 超时重试 等 ack 成功才算发完（RocketMQ send() 同步；Kafka acks=all + retries）
事务消息 RocketMQ 半消息 + 本地事务 + 回查，保证”库数据和发消息”原子一致
消息表 + 定时补偿扫描 落库状态”待发送”，定时任务补发 = 兜底方案
幂等生产者（Kafka） enable.idempotence=true，避免重试造成的重复写入

3.3 Broker 端：持久化 + 副本

步骤 手段
落盘 RocketMQ 同步刷盘 FlushDiskType=SYNC_FLUSH / Kafka 也异步刷盘（默认 page cache + 定时）
副本 RocketMQ 主从同步双写（SYNC_MASTER）；Kafka 多副本 min.insync.replicas=2
容灾 副本落在不同机房/机架；磁盘写满、掉电都可能丢已刷盘的少量数据

要点：同步=慢但安全，异步=快但有窗口，选型以业务容忍度为准。

3.4 消费端：先成功再 ack + 幂等

  • 消费端规则：”消费成功才提交位点/返回确认“。
    • Kafka：enable.auto.commit=false，业务成功后手动 commitSync()；
    • RocketMQ：消费成功返回 CONSUME_SUCCESS，失败返回 RECONSUME_LATER（重试 16 次后进死信 DLQ）；
    • RabbitMQ：autoAck=false 手动 basicAck，失败 basicNack 重回队列（要小心无限重试 → 配 DLX）。
  • 至少一次投递是几乎所有 MQ 的默认语义 → 消费端必须幂等：
    1. 业务唯一键 + 数据库唯一索引（[最稳]）；
    2. Redis setNx(key,1) 去重（吞吐高）；
    3. 状态机判断（已处理则直接返回）。

3.5 全链路可靠性清单（背熟）

环节 防丢动作 防重动作
生产发送 同步 ack + 重试 + 事务/消息表 幂等生产者 / 唯一消息 ID
Broker 存储 刷盘 + 同步复制 —
消费处理 成功后再 ack 业务幂等（唯一键去重）
失败兜底 重试队列 → 死信队列 + 告警人工 死信消费也幂等

4. 延迟消息怎么实现（重点三）

4.1 需求本质

“过 N 秒/到某时刻才被消费”，典型：下单 30 分钟未支付自动关单、超时未确认收货、定时提醒。

4.2 方案一：MQ 自带延迟能力

RocketMQ（延迟消息，固定分级）：

RabbitMQ（TTL + 死信队列 DLX）：消息设 expiration，到期后进入”死信交换机”，
由业务队列消费：

Kafka（原生无延迟）：需要自己实现（定时扫描/时间桶），或用 RocketMQ 替代。

4.3 方案二：Redis ZSet 延迟队列（不上 MQ 也能做）

  • score = 到期时间戳，到期后 zrangeByScore 取出处理，zrem 原子删除（推荐 Lua 防并发丢单）。

4.4 方案三：进程内时间轮 / 定时扫描

  • Netty HashedWheelTimer / 时间轮：毫秒~分钟级，内存高效，适合单机 batch 任务。
  • 定时扫库：ScheduledExecutor 每 5s 扫 execute_time <= now 的任务表，简单可靠，但实时性差、DB 压力大。

4.5 延迟实现方案对比

方案 延迟粒度 可靠性 适合
RocketMQ 延迟级别 固定 18 档 MQ 级别高 订单、任务调度最常用
RabbitMQ TTL+DLX 任意 ms MQ 级别高 已有 RabbitMQ 时
Redis ZSet 秒级 Redis 挂了丢（自做持久化） 轻量、无 MQ 场景
时间轮 ms 级 进程内存 本地定时任务
定时扫库 秒~分钟 最高（落库） 数据量大但简单方案

5. 面试高频考点速查（背题表）

问题 得分点
MQ 怎么保证顺序 同 key 同队列 + 队列 FIFO + 单消费者串行 + 顺序失败重试不跳
怎么保证不丢消息 三段式：生产 ack、Broker 持久化+副本、消费完整提交
消息重复消费怎么办 幂等：唯一键去重/状态机/Redis setnx
延迟消息怎么实现 RocketMQ 延迟级别 / RabbitMQ TTL+DLX / Redis ZSet / 时间轮 / 扫库
Kafka vs RocketMQ 顺序 Kafka 分区有序、RocketMQ 队列有序，消费端要串行
消费失败重试会乱序吗 会：顺序消费必须阻塞重试不跳消息
死信队列拿来干嘛 重试 N 次仍失败的消息放 DLQ，人工/定时补偿
落到 Redis 幂等怎么保证 SETNX + 过期时间 + 唯一业务 ID
消息时间戳做延迟 消费者按 sendTime + delay 判断，不推荐（占用消费者）

6. 生产自查清单（写代码前过一遍）

  • 每类消息明确 key（订单/用户维）并确认路由到同一队列/分区；
  • 消费组：顺序业务用单消费者 + MessageListenerOrderly；并发业务明确接受乱序；
  • 发送用同步 + 重试上限，且 enable.idempotence=true（Kafka）；
  • 消费端 auto.commit=false 手动提交，业务成功后 先幂等 再 ack；
  • 延迟需求：30 分钟内用 Redis ZSet；>分钟级/固定档用 RocketMQ 延迟级别或 RabbitMQ TTL+DLX；
  • 所有消费处理都有 DLQ/告警和人工补偿入口。

7. 自测三问

  1. 画一条完整链路：一个下单消息从发送到消费结束，哪些环节可能丢、哪些环节可能重复，分别怎么解？
  2. 同一订单的”创建→支付→取消”三消息，如何保证按顺序执行？如果支付一条消费失败怎么办？
  3. 让你们用”下单 30 分钟未支付关单”，在已有 RabbitMQ 和 Redis 两种条件下，你分别怎么实现？各有什么坑？

写完这篇，”顺序 + 可靠 + 延迟”三连题就能连成一串答。配合 Day10 Redis、Day9 ThreadLocal，缓冲与异步链路的知识成体系。
