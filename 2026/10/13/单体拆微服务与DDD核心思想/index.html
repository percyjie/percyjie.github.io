「单体拆微服务」是面试和落地都绕不开的话题。很多人第一反应是「按模块拆」，结果拆完发现：服务之间互相调用几十跳、改一个字段要一起发版、跨库事务对不上账——这就是典型的分布式单体。这篇文章把三件事串起来讲清楚：单体到底按什么思路拆、DDD 的核心思想是什么、贫血模型和充血模型该怎么取舍。

先说结论

先用一张表把全文的结论摆出来，后面再展开：

问题 结论
什么时候拆 组织上多团队互相阻塞、业务上模块的变更频率/伸缩要求差异巨大、单体已经难以构建部署——三条至少中一条
按什么拆 按业务能力/子域垂直切（即限界上下文），不要按 controller/service/dao 技术层横着切
怎么落地 绞杀者模式渐进迁移：模块化单体 → 抽接口与防腐层 → 拆读侧服务 → 拆数据 → 治理
难点在哪 不在应用代码，而在数据归属和跨服务一致性
DDD 是什么 一套「让代码结构与业务概念对齐、用边界管理复杂度」的建模方法论，核心是通用语言 + 限界上下文
贫血/充血怎么选 核心域用充血，支撑域/通用域用贫血；不要一刀切，也不要为了「纯粹」而充血

一句话概括：拆微服务的本质是拆边界，而划分边界最靠谱的工具就是 DDD；充血/贫血只是边界划好之后，模型内部要不要内聚业务规则的选择题。

01 先问自己：为什么拆？不拆行不行？

拆微服务是手段，不是目的。很多人只看到了收益，没算过成本：

你以为的收益 真实代价
独立部署、独立发版 换来分布式复杂度：链路追踪、分布式事务、跨服务排查
技术栈自由 团队维护成本、平台建设成本上升
团队自治 需要契约治理、SLA、监控告警等一整套基础设施兜底
独立扩容 大多数系统的瓶颈在数据库，拆应用并不解决

所以先做三道判断题：

  1. 组织维度：是不是有多个团队在同一个代码库里互相阻塞、排队等发版？
  2. 业务维度：是不是不同模块的变更频率、可用性等级、伸缩需求差异巨大？（比如秒杀模块和后台报表）
  3. 工程维度：单体的构建、部署、回归测试是不是已经慢到影响交付？

三条都不成立，先别拆，把单体做成「模块化单体」（Modular Monolith）往往收益更高：边界清晰、模块内高内聚，但依然是一个进程、一个数据库，没有分布式成本。

康威定律：系统架构会映射组织的沟通结构。所以拆分的粒度最终是由团队边界决定的——一个服务如果找不到一个团队对它负责，它迟早会变成没人管的孤儿服务。

02 拆分的总体思路：五步走

每一步的关键动作和产出物：

阶段 关键动作 产出物
① 现状梳理 业务能力地图、代码依赖分析、调用链、数据依赖、变更频率 依赖矩阵、候选边界清单
② 边界识别 用 DDD 找子域与限界上下文，做上下文映射 上下文地图（Context Map）
③ 拆分设计 定粒度、定优先级、定迁移方式（绞杀者/分支抽象） 拆分路线图、服务清单
④ 数据拆分 单一写入者、共享表治理、最终一致方案 数据归属表、同步方案
⑤ 治理演进 契约版本、可观测、熔断限流、一致性兜底 平台能力、治理规范

第 1 步：现状梳理（别跳过）

拆之前一定要有事实依据，而不是拍脑袋。至少收集这几类信息：

  • 业务能力地图：按价值链列出用户域、商品域、交易域、履约域、结算域……
  • 代码依赖矩阵：模块之间谁依赖谁，有没有循环依赖（循环依赖往往就是边界划错的信号）。
  • 运行时调用链：用 APM 画出服务拓扑、热点接口、慢 SQL。
  • 数据依赖：每张表被哪些模块读写——这是整个拆分里最难的部分。
  • 变更频率：用 git log 按目录统计提交频率，高频变动的模块优先隔离。

一个简化的依赖矩阵长这样（√ 表示有依赖）：

模块 用户 商品 订单 库存 支付
用户 — √
商品 — √
订单 √ √ — √ √
库存 √ √ —
支付 √ √ —

一眼就能看出：订单模块被最多模块依赖，也依赖最多模块——它天然是「交易上下文」的核心，拆的时候要格外小心事务边界。

第 2 步：识别边界——用 DDD 的限界上下文

这一步直接决定成败，原理见第 04 章。简单说：不要按「表」或「类」去切，要按「业务能力 + 模型边界」去切。

第 3 步：拆分设计与优先级

  • 从最容易切的开始试点：低耦合、低流量、边缘功能（比如消息推送、文件服务），先跑通「独立部署 + 独立发布 + 监控」这套流程。
  • 绞杀者模式（Strangler Fig）：新老逻辑并行，网关按流量比例/用户维度切流，新服务稳定后逐步放大，最后下线老逻辑。
  • 分支抽象（Branch by Abstraction）：先在单体里抽出接口，接口实现可以从「本地调用」换成「RPC 调用」，代码结构不用大改。
  • 优先拆读多写少、无事务共享的模块；写侧和强事务耦合的部分最后再拆，或者先只做「模块化」不做「服务化」。
  • 难切的先留着：不要为了「拆而拆」。一个拆不好会带来分布式事务的服务，不如继续留在单体里。

第 4 步：数据拆分（真正的难点）

应用代码拆开很容易，数据拆开才是成本大头。推荐一个渐进路径：

共享表怎么处理：核心原则是「单一写入者」（Single Writer）——一张表只允许一个服务写，其他服务要么通过 API 查询，要么订阅变更事件维护自己的只读副本。

跨服务一致性怎么保证，按优先级排序：

方案 一致性 适用场景 建议
本地事务 强一致 同一服务内 首选，能不出服务就不出
2PC / XA 强一致 极少数强约束场景 性能差、可用性差，不推荐
TCC 最终一致 资金类、可补偿的业务 成本高，核心链路才用
本地消息表 / 事务消息 最终一致 绝大多数跨服务场景 推荐默认方案
对账 + 补偿任务 最终一致兜底 所有涉及钱的场景 必须要有，是最后防线

记住一句话：分布式环境下不要追求强一致，要追求「最终一致 + 可对账 + 可补偿」。

跨服务查询：不要用「服务 A 调 B、B 调 C」拼数据，那样响应时间和故障率会指数级上升。优先用 API 组合（BFF 层聚合）、CQRS 读模型或宽表（用事件同步出一张查询专用的宽表）。

第 5 步：治理与演进

拆完之后才是真正的开始：

  • 契约治理：接口版本化、向后兼容、契约测试（Consumer-Driven Contract）。
  • 可观测性：TraceId 贯穿全链路，日志/指标/告警三件套。
  • 稳定性：熔断、限流、降级、超时、重试（重试必须配合幂等）、死信队列。
  • 一致性兜底：幂等键、状态机、定时对账、人工补偿入口。

03 按什么维度切？五个可用依据（附反例）

切分依据 说明 例子 风险
业务能力 / 子域（推荐） 按业务垂直切分 订单、库存、支付 需要一定的领域建模能力
变更频率 把高频变动的隔离出去 营销规则引擎 边界容易漂移
数据所有权 按数据归属切 用户主数据 需先理清数据依赖
团队边界（康威） 一个团队一个服务 按小组划分 组织调整会导致架构抖动
技术分层（不推荐） 按 controller/service/dao 切 用户-Controller 服务 直接产出分布式单体

反模式：分布式单体（Distributed Monolith）

拆了进程，没拆边界。判断信号：

  1. 多个服务共享同一张表或同一个数据库实例；
  2. 服务之间同步调用链很长（A→B→C→D→E），一个慢全链路慢；
  3. 改一个需求要同时发布多个服务；
  4. 服务之间共享 DTO/公共库，公共库一改全员升级；
  5. 出了故障无法定位是哪个服务的责任。

只要中了两条以上，说明这次拆分基本白拆——它只是把单体的复杂度从「代码内」搬到了「网络上」，还额外增加了运维成本。

04 DDD 的核心思想到底是什么

一句话：DDD（Domain-Driven Design，领域驱动设计）是把「业务领域知识」翻译成「软件模型」的一套方法，核心目标是让代码结构与业务概念一一对应，并用「边界」来管理复杂度。

它分三个层次，理解顺序就是从外到内：

4.1 通用语言（Ubiquitous Language）

业务方、产品、开发、测试说同一套词，代码里也用这套词命名。

  • 正例：Order.pay()、Inventory.lock()、Coupon.calculateDiscount()。
  • 反例：doProcess()、handleData()、status = 1 / 2 / 3（谁能记住 3 是已取消还是已超时？）。

通用语言是 DDD 的地基。没有它，所谓「领域模型」就是一群自己发明的类名，业务方看不懂，改需求时还是会失真。

4.2 领域与子域：把精力花在刀刃上

整个业务领域可以拆成子域，按重要程度分三类：

子域类型 含义 投入策略
核心域 公司的核心竞争力所在 自研 + 最强人力 + 充血模型 + 精雕细琢
支撑域 支撑核心业务但无差异化 自研或外包，够用就行，贫血模型
通用域 行业通用能力 直接买/用开源（认证、支付网关、短信），贫血模型

这条太重要了：不是所有模块都值得做 DDD 建模。 把通用域也拿来认真建模，就是典型的过度设计。

4.3 限界上下文（Bounded Context）—— 最重要的抓手

限界上下文 = 一个模型能成立的边界。 在边界内，术语的含义是明确且唯一的；出了边界，同一个词可能完全不是一回事。

经典例子——「商品」这个词：

上下文 「商品」的含义
商品上下文 有标题、详情、类目、上下架状态，关注展示与检索
交易上下文 有价格、优惠、库存快照，关注下单与结算
履约上下文 有重量、体积、发货地，关注物流与配送

如果在整个系统里只用一个 Product 类，就必然出现「字段越来越多、每个模块只用一部分、改一处影响一片」的局面——这正是单体腐化的根源。

所以：一个限界上下文，通常就是一个微服务的边界。 它同时是模型边界、团队边界和数据边界，三者对齐时，拆分才是健康的。

4.4 上下文映射（Context Map）：边界之间怎么协作

划好边界后，还要定义边界之间的关系，常见模式：

模式 含义 使用场景
共享内核（Shared Kernel） 两个上下文共享一小块模型 谨慎使用，共享越多耦合越重
客户-供应商（Customer-Supplier） 下游依赖上游，上游需照顾下游 上游是内部团队时
遵奉者（Conformist） 下游直接照抄上游模型 上游是强势外部系统时
防腐层（ACL） 下游加一层翻译，隔离外部模型 最常用，强烈推荐
开放主机服务（OHS） 上游提供统一对外协议 一个上游对多个下游
各行其道（Separate Ways） 干脆不集成 集成成本大于收益时

防腐层是微服务里最实用的模式：外部系统的 DTO 不要直接流进你的领域模型，中间加一层转换，外部一变只改这一层，领域模型不受污染。

4.5 战术设计的构件（写代码时用）

概念 定义 判断要点
实体 Entity 有唯一标识，生命周期内标识不变 用 ID 判等，而不是属性
值对象 Value Object 无标识，靠属性判等，不可变 金额、地址、时间区间、订单号
聚合 Aggregate / 聚合根 一致性边界，一个事务只改一个聚合 尽量小
领域事件 Domain Event 领域内发生的、业务关心的事实 用过去式命名，如 OrderPaid
仓储 Repository 聚合的持久化抽象 只为聚合根建，不要给每张表建
领域服务 Domain Service 不属于任何实体的领域逻辑 跨聚合的计算/规则
应用服务 Application Service 编排用例、控制事务边界 要薄，不写业务规则
工厂 Factory 复杂对象的创建封装 创建逻辑复杂时才需要

聚合设计三条铁律（面试常问）：

  1. 一次事务只修改一个聚合——跨聚合的一致性交给领域事件 + 最终一致；
  2. 聚合之间用 ID 引用，不要用对象引用——否则加载一个对象会牵出整个对象图；
  3. 聚合要小——小到「一个事务能保证它的一致性」就够了，聚合越大并发冲突越严重。

4.6 一个关键澄清：DDD 不等于微服务

  • DDD 也可以用在单体里（模块化单体 + 清晰的模块边界），而且先做 DDD 再拆服务才是正确顺序；
  • 微服务也可以不用 DDD，但边界会「飘」——因为没有业务依据，只能靠感觉切；
  • DDD 真正的价值在于通用语言 + 限界上下文，战术构件是附赠品。

05 贫血模型 vs 充血模型：到底怎么取舍

5.1 定义

  • 贫血模型（Anemic Domain Model）：对象只有数据和 getter/setter，业务规则全部写在 Service 里。本质是「面向过程的事务脚本」。
  • 充血模型（Rich Domain Model）：对象既有数据也有行为，业务规则内聚在领域对象内部。
  • 中间还有「失血模型」「胀血模型」等说法，但核心就是业务逻辑到底放在哪。

5.3 全面对比

维度 贫血模型 充血模型
业务规则位置 Service 里，集中但容易散落、重复 领域对象内，内聚，只写一处
上手 / 维护成本 低，符合大多数人的编程习惯 高，需要建模能力和团队共识
与 ORM 的契合度 天然契合（POJO + Mapper） 需要处理不可变、无 setter、集合封装
单元测试 常依赖 Mapper/DB，偏集成测试 纯内存对象，测试快、覆盖全
规则一致性 多个入口容易各写一遍校验 规则唯一，改一处全生效
可读性 面向过程，逻辑直白 需要理解领域概念，但更贴近业务
适合场景 CRUD、报表、支撑域/通用域 核心域、规则复杂、状态机多、涉及钱
主要风险 上帝 Service、规则漂移、贫血化回流 过度设计、为充血而充血、模型「假装充血」

5.4 取舍建议（重点，七条）

  1. 不要一刀切：核心域（订单、交易、风控、结算）用充血；支撑域/通用域（配置、字典、消息、日志）用贫血，够用就行。
  2. 用「不变式」来识别：如果一个对象上有多条互相约束的规则（状态机、金额上下限、额度校验），那就该充血——因为规则必须被守住。
  3. 别把 Service 整个搬进 Entity：跨聚合的编排、外部调用、事务边界，留在应用服务里；只有属于这个对象的规则才搬进去。
  4. 充血不等于不需要 Service：应用服务（编排 + 事务）、领域服务（跨聚合计算）依然需要，只是它们不再是业务规则的唯一容器。
  5. 领域层不要依赖框架：尽量别让 @Entity、@Autowired、Mapper 注解侵入领域对象。做不到就退一步，用独立的持久化对象 + 转换（DTO/PO 与领域对象分离）。

  7. 别在贫血模型上硬套 DDD 战术构件：贫血的 Entity + Repository + 领域事件 = 形式主义 DDD，只会增加代码量，不产生任何价值。

5.5 五个常见误区

误区 纠正
DDD 就等于充血模型 DDD 的核心是边界和语言，战术模型只是其中一环
充血 = 把 Service 方法剪切到 Entity 充血的标准是「规则由对象自己守住」，不是代码搬家
聚合越大越完整 聚合要尽量小，只圈住「必须强一致的」那部分
一个事务可以更新多个聚合 跨聚合用领域事件 + 最终一致，不要跨聚合加锁
用了 ORM 就做不了充血 可以做，只是需要额外处理不可变和集合封装，或者做对象转换

06 落地路线图：从单体到微服务的五个阶段

不要幻想一次拆完，按阶段演进，每个阶段都有明确的验收标准：

阶段 做什么 验收标准
0. 模块化单体 在单体内部按限界上下文划分模块，禁止跨模块直接访问对方的表和 Mapper 模块依赖无环，跨模块只能走公开接口
1. 抽接口 + 防腐层 给要拆的模块定义接口，外部系统加 ACL 转换 本地实现可被替换为远程实现
2. 拆服务（读侧优先） 把只读/低耦合功能独立部署，网关切流 新服务独立发布，监控告警齐全
3. 拆数据 明确单一写入者，事件同步只读副本，逐步独立库 无跨库 JOIN，无跨库事务
4. 治理平台化 契约管理、全链路追踪、熔断限流、对账补偿 故障可定位、可回滚、可补偿

关键顺序：先划边界 → 再拆服务 → 最后拆数据。反过来做（先拆库）几乎一定会返工。

07 面试速答模板

Q1：单体怎么拆微服务？

先看要不要拆——多团队互相阻塞、模块伸缩与变更频率差异大、单体交付效率低，三条中一条才值得拆。拆的思路是五步：梳理现状（依赖矩阵、调用链、数据依赖）→ 用 DDD 的限界上下文识别边界 → 用绞杀者模式渐进迁移，先拆低耦合的读侧 → 再拆数据，坚持单一写入者，用本地消息表/事务消息做最终一致 + 对账兜底 → 最后补齐契约、可观测、熔断限流等治理能力。核心原则是按业务能力垂直切，绝不按技术分层横切，否则就是分布式单体。

Q2：DDD 的核心思想是什么？

DDD 是一套把业务领域知识映射成软件模型的建模方法论，核心是三层：最底层是通用语言，让业务和代码说同一套词；中间是战略设计，用子域（核心域/支撑域/通用域）和限界上下文划清模型边界，再用上下文映射（防腐层、客户-供应商等）定义边界间的协作；最上层是战术设计，用实体、值对象、聚合、领域事件、仓储把模型落地。其中限界上下文是拆微服务时最重要的抓手，它同时是模型边界、团队边界和数据边界。DDD 不等于微服务，它也可以用在模块化单体里。

Q3：贫血模型和充血模型怎么选？

按子域的重要程度分而治之：核心域用充血，把状态流转和业务规则内聚到领域对象里，避免规则被绕过；支撑域和通用域用贫血，CRUD 够用就行，别过度设计。识别标准是「有没有需要守住的不变式」——有状态机、金额约束这类互相制约的规则就充血。同时要澄清两点：充血不等于把 Service 代码搬进 Entity，跨聚合编排和事务边界仍留在应用服务；也不要在贫血模型上硬套 Repository 和领域事件，那只是形式主义。落地建议是渐进重构：先抽值对象，再把规则搬进实体，最后引入领域事件。

08 一页速查

最后再强调一遍开头的结论：先想清楚要不要拆，再用 DDD 划边界，最后才讨论模型要不要充血。顺序错了，怎么拆都是分布式单体。
