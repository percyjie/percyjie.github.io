一句话记住今天：Java 队列 = “三套方法 + 一个家族图谱 + 一条铁律”。三套方法是”满了怎么办”（add / offer / put）和”空了怎么办”（remove / poll / take）以及”只看不动”（element / peek）；家族图谱是 ArrayDeque、PriorityQueue、ArrayBlockingQueue、LinkedBlockingQueue、SynchronousQueue、DelayQueue、ConcurrentLinkedQueue 各自的边界；铁律是生产环境必须有界 + 必须监控排队时长。绝大多数线上事故不是”队列不会用”，而是”用了无界队列”或”消费者挂了生产者还在 put”。

先说结论

高频问题 一句话答案 面试官想追问
add / offer / put 区别 满时分别：抛异常、返回 false、阻塞等待 超时版怎么写
remove / poll / take 区别 空时分别：抛异常、返回 null、阻塞等待 为什么 BlockingQueue 禁止 null
单线程用什么队列 ArrayDeque，比 LinkedList 和 Stack 都快 ArrayDeque 能不能多线程用
线程池任务队列选什么 有界 ArrayBlockingQueue 或显式容量的 LinkedBlockingQueue 无界会怎样
延时任务怎么做 JVM 内用 DelayQueue，跨进程/可靠用 MQ 延迟消息 重启丢任务怎么办
PriorityQueue 注意事项 最小堆、非线程安全、迭代器不保证有序 Top K 怎么用
高并发无锁队列 ConcurrentLinkedQueue，非阻塞、弱一致迭代器 size() 为什么是 O(n)
优雅关闭 毒丸（poison pill）或 offer(timeout) + shutdown + 排空 只用 shutdownNow 有什么后果

三句可背诵的话：

  1. 方法选错的本质是”满了/空了的行为选错”：要么该抛异常（暴露问题），要么该阻塞（背压），要么该返回 false（降级）。
  2. 队列选错的本质是”并发语义选错”：单线程用并发的浪费锁，多线程用非并发的丢数据。
  3. 线上出事的本质几乎都是”没设上界”：无界队列 = 把 OOM 延后，而不是解决问题。

02 三套核心方法：满了怎么办、空了怎么办

2.1 插入：add / offer / put

方法 队列满时行为 返回 属于哪个接口 什么时候用
add(e) 抛 IllegalStateException boolean Queue 想立刻暴露”塞不进去”
offer(e) 返回 false boolean Queue / BlockingQueue 非阻塞投递、可自行降级
offer(e, timeout, unit) 等待到超时后返回 false boolean BlockingQueue 生产推荐：既有背压又不会永久挂死
put(e) 一直阻塞到有空间 void BlockingQueue 必须保证不丢数据、且消费者健康

2.2 取出：remove / poll / take

方法 队列空时行为 返回 属于哪个接口 什么时候用
remove() 抛 NoSuchElementException E Queue 逻辑上”不该为空”，为空即 bug
poll() 返回 null E / null Queue / BlockingQueue 非阻塞轮询
poll(timeout, unit) 等超时后返回 null E / null BlockingQueue 消费者主循环，方便检查停止标志
take() 一直阻塞到拿到元素 E BlockingQueue 标准消费者，空转成本最低

不要用 isEmpty() + poll() 组合判断：多线程下”判空”和”取出”不是原子操作，会丢任务或误判。直接用 poll() 返回值判 null。

2.3 查看：element / peek

方法 队列空时 说明
element() 抛异常 强制要有队头
peek() 返回 null 只看不取，O(1)
peekFirst()/peekLast() 返回 null Deque 双端查看

PriorityQueue 的 peek() 返回的是堆顶（最小/最大）元素，不是”最后加入的元素”，这是最常见的理解错误。

2.4 Deque 的双端方法（ArrayDeque 专用）

Deque 把 Queue 和 Stack 的方法统一了：

动作 头部 尾部
插入 addFirst / offerFirst / push addLast / offerLast
移除 removeFirst / pollFirst / pop removeLast / pollLast
查看 getFirst / peekFirst getLast / peekLast

2.5 为什么 BlockingQueue 不允许 null

LinkedBlockingQueue、ArrayBlockingQueue 等都会对 null 抛 NullPointerException，原因是：

  • poll() / take() 用 null 表示”队列空或超时”；
  • 如果允许存入 null，取出 null 就分不清”拿到了一个 null 元素”还是”没拿到东西”。

所以毒丸（poison pill）不能用 null 表示，要定义一个专门的哨兵对象。

03 有界、背压与容量规划

3.1 无界队列的真实后果

任务提交速度一旦持续大于消费速度：

  1. 队列长度无限增长，maximumPoolSize 和拒绝策略永远不触发；
  2. 老年代被任务对象填满，Full GC 频繁；
  3. 最终 OOM，而且排查时看到的是”内存问题”，根源是”容量策略缺失”。

同理，PriorityBlockingQueue、DelayQueue、ConcurrentLinkedQueue 都是”事实无界”，必须有外部限流。

3.2 容量怎么定：用排队时长反推

经验公式（利特尔法则的简化版）：

场景 峰值提交 可接受排队 建议容量
实时风控（200ms 内处理） 2000/s 0.1s 200
异步日志落库 5000/s 2s 10000
订单履约任务 500/s 10s 5000
批量数据导入 1000/s 60s 60000（配合消费者扩容）

还要叠加三个约束：

  • 单个任务对象大小：10000 × 10KB = 100MB，队列本身就能吃满内存；
  • 消费者数量：容量要按”消费能力最弱时的缓冲”设计，不是按平均流量；
  • 多实例分摊：10 台机器共担流量，单机容量可除以实例数（但要考虑单台宕机）。

3.3 队列满了以后怎么办（比设容量更重要）

策略 做法 适用
快速失败 add() 抛异常 + 上层返回”系统繁忙” 用户可重试的读请求
超时降级 offer(timeout) 失败后走备用逻辑 有兜底数据源的同步场景
转持久化 失败后落库/写 Kafka，等慢速消费 不能丢的任务型数据
丢弃 + 打点 非核心指标类，计数告警 埋点、监控日志
反压上游 put() 或 CallerRunsPolicy 让调用方变慢 上游可降速且能扛
动态扩消费者 观察积压自动加线程/加实例 消费能力可弹性扩展

面试金句：“队列容量决定系统能忍多久，拒绝策略决定系统怎么死。生产必须两个都设计，而不是只设容量。”

04 生产者-消费者：四种写法

4.1 wait / notify 手写（理解原理）

三个必背细节：

  1. while 而不是 if：wait() 可能被虚假唤醒，也可能唤醒时条件已不成立；
  2. notifyAll() 而不是 notify()：多个消费者时用 notify() 可能唤醒”错的那个”，导致大家一起等待；
  3. 生产环境不要手写这套，直接用 BlockingQueue，除非你需要自定义等待条件。

4.2 BlockingQueue（标准写法）

消费者线程死掉是队列最隐蔽的故障：一旦异常穿透 while 循环，队列开始积压，生产者 put 逐渐挂死，上游线程池被占满，最后整链路超时。所以消费者循环里必须 catch 单个任务异常。

4.3 批量取出降低锁竞争：drainTo

drainTo 一次加锁取多个元素，比循环 poll() 少 N 次锁操作，还能让下游做批量 IO（批量入库、批量发消息）。

4.4 优雅关闭：毒丸 + 超时

关闭方式 效果 风险
shutdown() 不再接新任务，队列里的会跑完 队列积压时会很久才结束
shutdownNow() 中断线程 + 返回未执行任务 任务被丢弃/中断，需要自己处理返回值
毒丸 保证已入队任务被处理完 要预留投毒丸的容量，别被满队列挡住
offer(timeout) 不会永久阻塞关闭流程 关闭时可能丢新任务

shutdownNow() 返回的 List<Runnable> 一定要接住并补偿，否则等于静默丢任务。

05 PriorityQueue：最小堆的四个坑

5.1 基本用法

5.2 复杂度与坑

操作 复杂度 备注
peek() O(1) 堆顶
offer() / poll() O(log n) 上浮 / 下沉
remove(Object) O(n) 要先线性查找，别在热点路径用
迭代器遍历 不保证有序 想要有序，循环 poll()
addAll(collection) O(n) 比逐个 offer 快（一次性建堆）

四个高频坑：

  1. 迭代器不排序：for (Integer x : pq) 的顺序不是优先级顺序，面试常考。要有序就 while (!pq.isEmpty()) pq.poll()。
  2. 非线程安全：多线程用 PriorityBlockingQueue。
  3. 元素必须可比较：默认自然序要求实现 Comparable，否则 ClassCastException。
  4. 相同优先级不稳定：比较器没打破平局时出队顺序不确定，加序号字段兜底。

5.3 Top K 问题

数据流场景（不断进来新元素取前 K 大）也用这个模式，PriorityQueue 是标准答案。

06 特殊队列怎么用

6.1 SynchronousQueue：容量为 0 的”交接”

  • 没有内部存储：put 必须等到有线程 take，反之亦然；
  • offer() 在没有配对消费者时立即返回 false，不阻塞；
  • fair 模式（new SynchronousQueue<>(true)）按 FIFO 交接，默认非公平吞吐更高；
  • CachedThreadPool 用它：意味着”要么复用空闲线程，要么新建线程”，任务不会排队。

适合场景：线程间直接传递、不缓冲；不适合需要削峰的场合。

6.2 DelayQueue：延时到期才出队

元素要实现 Delayed：

特点与限制：

优点 限制
API 简单，take() 天然阻塞到到期 纯内存，进程重启任务全部丢失
单个消费者即可，无需轮询 无界，大量延时任务会占内存
适合秒级~分钟级、允许丢失的场景 多实例部署时无法共享，可能重复/漏处理

面试对比：“JVM 内 DelayQueue 适合轻量、可容忍丢失的延时任务；订单超时这种不能丢的，用延迟消息（RocketMQ 延迟等级 / Redis ZSet 轮询 / 时间轮 + 持久化）。” 海量定时任务（百万级）还应考虑时间轮（HashedWheelTimer），插入/删除 O(1)，而 DelayQueue 是 O(log n)。

6.3 LinkedTransferQueue：可等待的交接

  • 兼具 ConcurrentLinkedQueue 的高吞吐和 SynchronousQueue 的交接语义；
  • transfer(e) 会阻塞直到被消费者取走（比普通 put 更强的确认）；
  • tryTransfer(e) 只在已有消费者等待时才成功；
  • tryTransfer(e, timeout, unit) 可加超时；
  • 无界，需要自己控流。

适合”生产者希望确认任务已被处理线程接走”的场景。

6.4 ConcurrentLinkedQueue：无锁但不阻塞

特性 说明
无 put/take 它不是 BlockingQueue，只能 poll 或轮询
size() O(n) 全链遍历，别在循环或判限流里调用
迭代器弱一致 不抛 ConcurrentModificationException，但可能看到部分修改
无界 生产快消费慢就是内存泄漏
适合 高并发投递 + 消费方可容忍空轮询，或作为多生产者收集器

如果用 poll() + sleep 轮询，CPU 会白白消耗；正确做法是配 LockSupport.parkNanos，或者直接用 BlockingQueue。

6.5 ArrayDeque：单线程首选

  • 循环数组，头尾操作均摊 O(1)；
  • 比 LinkedList 缓存友好、内存连续、无逐节点对象开销；
  • 官方建议：当栈用比 Stack 快（Stack 继承自 Vector，全同步），当队列用比 LinkedList 快；
  • 非线程安全，禁止 null，迭代器 fail-fast。

07 并发语义与一致性注意

7.1 fail-fast 还是弱一致

队列 迭代器行为 影响
ArrayDeque / LinkedList / PriorityQueue fail-fast，可能抛 ConcurrentModificationException 多线程遍历时会炸
BlockingQueue 家族 弱一致 可能少看或多看，但不抛异常
ConcurrentLinkedQueue 弱一致 同上

需要”从队列里捞一批出来处理”时，优先 drainTo() 而不是遍历再删除——BlockingQueue.removeIf / removeAll 是 O(n) 且会长时间持锁。

7.2 中断处理

  • put/take/offer(带超时) 都会响应中断并抛 InterruptedException；
  • 吞掉中断等于骗过所有想要停止你的代码，Thread.interrupted() 标志被清掉后，上层线程池无法关闭工作线程。

7.3 排队时长比队列长度更该监控

只监控 size() 不够，要监控队头元素的等待时间（P99 排队时长）。1000 个轻量任务和 50 个重任务的积压含义完全不同。

建议指标：

指标 含义 告警阈值思路
队列长度 当前积压 容量的 70%、90% 两级
队头等待时长 最老任务的排队时间 按业务 SLA，如 > 2s 告警
offer 超时次数 满的次数 持续增长即容量不足
put 阻塞线程数 被背压的生产者数量 突增说明消费者出问题
拒绝/降级次数 落库/丢弃的量 必须为 0 或在预算内
消费速率 处理 TPS 与生产速率对比

7.4 内存与对象引用

  • 队列里的对象在出队前不会被 GC，放 DTO 而不是大对象（字符串、图片 byte[] 会显著放大内存）；
  • ArrayBlockingQueue 数组容量固定，即使 poll 出元素，底层数组仍是那个大小（占内存稳定，好预估）；
  • LinkedBlockingQueue 每个元素一个 Node，节点对象额外开销约 24~32 字节，海量小元素时反而更占内存；
  • 出队后及时清理 List / Map 引用（尤其 drainTo 批处理用完要 clear()）。

7.5 公平性

  • ArrayBlockingQueue(100, true) 可开启公平模式，FIFO 等待但吞吐下降明显；
  • 默认非公平，性能优先；
  • SynchronousQueue(true) 同理。生产默认非公平，除非出现明显饥饿。

08 选型速查

需求 首选 理由
单线程做队列/栈 ArrayDeque 最快、内存连续、API 完整
单线程优先级队列 PriorityQueue 堆，O(log n) 出最值
线程池工作队列 ArrayBlockingQueue（或指定容量的 LinkedBlockingQueue） 有界才能触发拒绝策略
高吞吐生产者消费者 LinkedBlockingQueue（给容量） 读写双锁，put/take 竞争小
内存可控、容量固定 ArrayBlockingQueue 预分配数组、单锁简单
线程间直接交接不缓冲 SynchronousQueue / LinkedTransferQueue 容量 0 / 可等待被取走
延时到期执行 DelayQueue（可丢）/ MQ 延迟消息（不可丢） 内存 vs 可靠性
优先级 + 多线程 PriorityBlockingQueue 线程安全的堆
高并发非阻塞投递 ConcurrentLinkedQueue CAS 无锁，吞吐最高
双端 + 工作窃取 LinkedBlockingDeque / ForkJoinPool 队列 两端阻塞、可窃取
跨进程、可回放、削峰 Kafka / RocketMQ JVM 队列不解决可靠性与分布式

一句总结：“JVM 内队列解决解耦和背压，MQ 解决可靠、广播与跨进程。别用内存队列假装消息中间件。”

09 面试高频问答

Q1：add 和 offer 到底用哪个？
A：语义区别只在”满了怎么办”——add 抛异常，offer 返回 false。生产上更推荐 offer(e, timeout, unit)，既能背压又不会让调用线程永久挂死，失败后走降级（落库/转 MQ/丢弃打点）。

Q2：put 和 offer 呢？
A：put 阻塞直到成功，适合”绝不丢数据且消费者健康”的场景，但有消费者挂掉导致生产者堆积卡死的风险；offer 立即返回结果，适合可容忍丢弃或需要自己做重试的场景。

Q3：ArrayBlockingQueue 和 LinkedBlockingQueue 的区别？
A：三点——① 有界性：前者构造必须指定容量，后者默认 Integer.MAX_VALUE（无界隐患）；② 锁：前者一把锁（put/take 互斥，可选公平），后者两把锁（put/take 可并行，吞吐更高）；③ 内存：前者预分配数组，内存可控；后者每元素一个节点对象，容易积压占内存。

Q4：为什么不建议用 Executors 创建线程池？
A：newFixedThreadPool / newSingleThreadExecutor 用无界 LinkedBlockingQueue，任务积压直接 OOM；newCachedThreadPool 最大线程数是 Integer.MAX_VALUE，峰值会创建海量线程。生产用 ThreadPoolExecutor 手动指定有界队列、线程名和拒绝策略。

Q5：BlockingQueue 为什么不能存 null？
A：poll() / take() 用 null 表示”空或超时”，如果允许存 null 就产生歧义。所以毒丸机制要用专门的哨兵对象，而不是 null。

Q6：PriorityQueue 的迭代器为什么不是有序的？
A：它底层是数组堆，只保证父节点不大于子节点，层序遍历不是排序结果。要有序就反复 poll()。另外 remove(Object) 是 O(n)，热点路径避免使用。

Q7：DelayQueue 适合做订单超时吗？
A：单机、量小、允许重启丢任务的话可以；但订单超时通常不能丢，应该用延迟消息或 Redis ZSet + 轮询，或多实例共享。海量延时（百万级）用时间轮，插入/删除 O(1)，比堆的 O(log n) 更适合。

Q8：多线程遍历队列会发生什么？
A：ArrayDeque、PriorityQueue 是 fail-fast，会抛 ConcurrentModificationException；BlockingQueue、ConcurrentLinkedQueue 是弱一致迭代器，不抛异常但视图可能不完整。要处理一批元素就用 drainTo。

Q9：消费者线程怎么优雅停止？
A：毒丸（每个消费者一颗）或 volatile running 标志 + poll(timeout) 循环 + shutdown() 后等待队列排空；shutdownNow() 返回的未执行任务列表必须补偿处理。

Q10：怎么发现队列出了问题？
A：看四个指标——队列长度、队头等待时长、offer 超时/拒绝次数、被 put 阻塞的线程数。队头等待时长比长度更能反映真实积压。

10 避坑清单（生产 12 条）

  1. 永远显式指定队列容量，不要用无界队列”先跑起来再说”。
  2. 消费者循环内 catch 单任务异常，一个任务失败不能让线程退出。
  3. 别用 isEmpty() + poll() 判空取数，直接用 poll() 返回值。
  4. 生产入口带超时：offer(e, timeout, unit)，失败有明确降级路径。
  5. 中断要恢复标志：catch (InterruptedException e) { Thread.currentThread().interrupt(); }。
  6. 毒丸不用 null，用独立哨兵对象，且关闭时确保容量够投毒丸。
  7. 别在 BlockingQueue 上遍历删除，用 drainTo 批量取。
  8. 别用 ConcurrentLinkedQueue.size() 做限流，O(n) 且并发下不准。
  9. PriorityQueue 非线程安全，并发场景换 PriorityBlockingQueue。
  10. DelayQueue 是内存态，重启即丢，不能当可靠延时方案。
  11. 队列元素尽量放 ID/轻量 DTO，别放大字符串、集合、byte[]。
  12. 监控排队时长而不是只看长度，并在容量使用率 70% 时告警。

一页纸速查

关键词 一句话
add / offer / put 满了：抛异常 / 返回 false / 阻塞
remove / poll / take 空了：抛异常 / 返回 null / 阻塞
element / peek 只看队头：抛异常 / 返回 null
ArrayDeque 单线程队列与栈首选，禁 null，非线程安全
PriorityQueue 默认最小堆，迭代器不排序，remove O(n)
ArrayBlockingQueue 有界、单锁、预分配，线程池推荐
LinkedBlockingQueue 双锁吞吐高，但默认无界要自己设容量
SynchronousQueue 容量 0，交接；CachedThreadPool 用它
DelayQueue Delayed + take() 到期才返回，内存态
ConcurrentLinkedQueue 无锁非阻塞，size() O(n)，弱一致
drainTo 批量取，减少锁操作，适合批处理
毒丸 优雅关闭，不能用 null 做哨兵
弱一致迭代器 不抛 CME，但视图可能不完整
容量公式 峰值速率 × 可接受排队时间

最后记住三句话：

  1. 方法层面：先想清楚”满了怎么办、空了怎么办”，再决定用 add/offer/put 还是 remove/poll/take。
  2. 选型层面：单线程用 ArrayDeque，线程池用有界 BlockingQueue，优先级用堆，延时分清”可丢/不可丢”，高并发投递才用无锁队列。
  3. 运维层面：容量必须有界、拒绝必须有策略、排队时长必须有监控、消费者异常必须被捕获——这四条做到，队列基本不会出事。
