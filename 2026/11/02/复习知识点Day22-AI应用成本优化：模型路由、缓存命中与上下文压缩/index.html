一句话记住今天：账单 = Token 数 × 单价 × 调用次数，三个因子各对应一招——模型路由把 token 换到便宜的模型上、缓存命中让重复的 token 只付零头、上下文压缩把没必要发的 token 直接删掉。三招可以叠加，但每一步都必须用评测集守住质量，否则省下的钱会以”返工率”的形式还回去。Day17 里这些是面试答题点，这篇讲怎么真正落地。

先说结论

手段 压的是哪个因子 典型收益量级 前置条件 最大风险
模型路由 / 级联 单价 60%~90% 任务可分类、有评测集 路由错误把难任务送小模型
提示词缓存 输入单价 输入侧 30%~80% 前缀内容稳定 布局写乱导致命中率≈0
语义缓存（结果缓存） 调用次数 重复问题 50%~90% 只读、可容忍陈旧 错误命中、串租户、缓存投毒
上下文压缩 输入 token 20%~60% 有质量回归 丢掉硬约束和数字
输出控制 输出 token 10%~40% 明确输出契约 被截断、字段缺失
减少轮次 / 并行工具 调用次数 30%~60% Agent 流程可重排 早停漏步骤
Batch API 单价 常见约五折 任务离线 不实时
蒸馏 / 微调小模型 单价 + 延迟 长期显著 有数据、任务稳定 前期投入与维护

一句方法论：先归因，再优化。不知道钱花在哪个环节，所有优化都是猜；很多团队一上来换小模型，结果发现 60% 成本是同一份固定前缀没命中缓存。

01 先算清钱花在哪：成本归因

1.1 四类要计费的 token

类型 说明 常见误区
输入 prompt system、工具定义、few-shot、历史、RAG 片段、本轮输入 以为”只有用户输入算钱”
输出 completion 生成的 token 单价通常远高于输入
推理 / reasoning token 思考型模型内部推理也计费 完全忽略，账单超预期数倍
缓存 token 命中价与写入价分开计 只看总 token，不看命中字段

两个必须记住的单价事实：

  1. 输出比输入贵一个数量级方向（常见 3~5 倍）：SELECT 式的长复述是隐形成本；
  2. 推理 token 按输出价计：数学、代码、复杂规划任务里，它可能比正文长好几倍。

1.2 调用次数是怎么放大的

多轮对话最烧钱的地方不是”每轮说了什么”，而是每轮都要把历史重新发一遍：

所以：10 轮会话的累计输入可能是”单轮平均”的 5 倍以上。其他放大器：Agent 循环（每轮带全量上下文）、工具结果原样回填、格式失败重试、LLM-as-Judge 全量评审、路由判定自身。

1.3 归因表（没有这个就没法优化）

看板至少五个指标：

指标 用途
每千次请求成本（按 feature 分组） 找真正的成本大头
缓存命中率（读 token / 总输入 token） 判断前缀布局是否有效
平均输入 / 输出 / 推理 token 判断压缩空间
路由升级率、错分代价 判断路由是否省钱不省质量
重试率、Agent 平均轮次 判断流程浪费

1.4 一笔示例账（数字为假设，用于说明算法）

固定前缀 system 1200 + 工具 600 + RAG 1800 = 3600/轮，每轮新增历史 400，输出 300/轮，三轮会话；输入 $1/百万、输出 $4/百万、缓存读 $0.1/百万：

方案 输入构成 成本
无缓存 12000 输入 + 900 输出 $0.0156
前缀缓存命中 2 轮 缓存读 7200 + 未缓存 4800 + 输出 900 $0.0091（省 42%）
再叠加语义缓存命中 FAQ 22% 请求零调用 约 $0.007（再省 ~20%）

02 模型路由：送到”够用且最便宜”的那一档

2.1 三种路由形态

形态 做法 优点 缺点
静态规则 按 feature 硬编码档位（意图=小模型，报告=大模型） 简单、零额外延迟 粒度粗，边界任务浪费或翻车
分类器路由 规则 + 轻量模型判定难度/风险，再选档 精细、省钱 判定本身有延迟与成本
级联（cascade） 先小模型，低置信或校验失败再升级 质量兜底强 两次调用，长尾延迟上升

生产常见组合：静态规则打底 + 级联兜底，分类器只在高流量、任务混合的场景引入。

2.2 七个路由信号

  1. 任务类型：抽取 / 分类 / 改写 / 推理 / 代码 / 规划；
  2. 输入长度：超长的检索问答直接给中档以上；
  3. 是否需要工具调用或严格结构化输出：小模型 schema 遵循能力弱；
  4. 领域与语言：方言、专业术语、多语混合；
  5. 风险等级：涉钱、涉法务、对外发布 → 直接高档 + 人工；
  6. 历史成功率：同一 feature 在不同模型上的回归表现；
  7. 置信度 / 校验结果：级联升级的触发条件（自评分低、schema 校验失败、检索无依据）。

2.3 代码骨架

配套三件事：供应商故障切换（同档位备选模型）、超时与降级、路由决策落库（离线复盘错分）。

2.4 路由器本身不能贵

  • 规则优先：80% 分流能靠 feature + 长度 + 风险 三元组解决；
  • 用轻量模型判难度时，判定延迟要压到几十毫秒级，否则不如固定档位；
  • 同会话粘住档位：中途换模型会导致语气、格式、引用风格突变，用户能感觉到”换了个人”；
  • 路由结果缓存（同 session、同类问题不重复判定）。

2.5 怎么证明路由没伤质量

手段 做法
分任务回归 每个 feature 单独测准确率，不看总体平均分
双跑抽样 同请求同时跑大小模型，比对差异，估算”升级真实收益”
混淆矩阵定价 “简单判成难”= 浪费钱；”难判成简单”= 事故，给两类错误不同代价
灰度放量 按 user bucket 放量 5% → 20% → 100%，盯转人工率、投诉率
一键回退 路由开关配置化，出问题切回全量大模型

2.6 坑

  1. 模型 ID 写死也要精确匹配：供应商静默更新会让回归结果失效；
  2. 小模型不支持严格 JSON：要么降级为”文本 + 解析”，要么该类任务不路由；
  3. 只看单价不看总成本：小模型重试率、人工复核率上升会把节省吃掉；
  4. 成本按单次调用算：应按”完成一次业务任务”算总账（含重试、工具、升级）。

03 缓存命中：重复的 token 只付一次钱

3.1 提示词缓存的机制

服务端把前缀的 KV 状态留住，下次请求前缀完全一致就复用，命中部分按折扣价计费，同时首 token 延迟（TTFT）显著下降。工程上要盯四个约束：

约束 实际含义
前缀必须逐 token 相同 一个字符差异（时间戳、空格、字段顺序）就整块不命中
分块匹配 一般按块（block）对齐，前缀长度不足门槛时不缓存
最小长度门槛 几百 token 的短前缀不值得缓存，常见门槛在千级 token 量级
TTL 分钟级 命中可续期；间隔久了要重新写入，写入可能加价

具体门槛、TTL、折扣比例各供应商不同，务必查当前价目与文档，别把”缓存一定省钱”当默认前提。

3.2 布局决定命中率（最容易踩的一节）

正确的排布是”稳定 → 半稳定 → 易变”：

命中率杀手清单：

  1. 在 system 里塞 当前时间：2026-11-02 17:20 → 每请求都不同，整块不命中；
  2. 工具/字段用未排序的字典序列化，JSON key 顺序抖动；
  3. few-shot 每次随机抽样（RAG 式动态示例很贵，先测再上）；
  4. 多租户内容拼进同一个”公共前缀”，导致前缀互不相同；
  5. 改写早期历史（摘要替换原文）→ 之后的前缀全部失效；
  6. 换模型或换 prompt 版本没同步缓存 key（不同模型不共享缓存）。

3.3 命中率怎么算、目标定多少

两个实操判断：

  • 稳定前缀本身要够长（例如 ≥ 数千 token），否则省下的钱抵不上写入加价和复杂度；
  • 命中率要看 P50 也要看分布：只有长会话命中、短请求全不命中的系统，收益远低于看板平均值。

3.4 语义缓存：整次调用都不用发

风险与缓解：

风险 场景 缓解
错误命中 “退货几天” 与 “换货几天” 向量很近但答案不同 阈值分档 + 关键槽位（实体、时间）精确校验
时效性 价格、库存、政策变化 按内容类型设 TTL；写数据时主动失效
越权串租 A 租户问题命中 B 租户答案 key 必含 tenant/ACL 哈希
缓存投毒 一次错误答案被缓存放大 只缓存有依据的回答；抽检 + 快速下线
反馈污染 用户骂”答错了”但缓存还在 负反馈触发失效与告警

适用面：只读、幂等、高频重复（FAQ、术语解释、状态查询）；推理型、个性化型任务别上。

3.5 别只盯着模型调用：链路上其他可缓存点

缓存对象 收益 注意
Embedding 同一 chunk 不重复嵌入（重嵌入很贵） 按模型版本 + chunk 策略作 key
RAG 检索结果（query → chunks） 省检索与重排算力 权限过滤必须在缓存之后仍生效
工具 / 外部 API 结果 直接省调用费 幂等接口才可缓存，注意 TTL
会话摘要 避免每轮重算全量历史 增量摘要，别频繁重写早期消息
短回答（FAQ） 零模型调用 见 3.4 风险

3.6 Agent 场景的省钱要点

  1. 只追加历史，别在每轮重写系统提示（否则前缀缓存全废）；
  2. 工具结果进上下文前先裁剪（见第 4 节），这是 Agent 最大的 token 浪费源；
  3. 并行独立工具调用，减少轮次 = 减少历史重复发送；
  4. 早停与 max_iterations，防止无效循环把成本推到几十倍；
  5. 子任务结果落盘复用，而不是重新推理一遍。

3.7 打点必须区分字段

供应商返回里 cached_input_tokens、cache_write_input_tokens、reasoning_output_tokens 是不同字段。只统计总 token 的看板，会让你以为命中率 80% 实际 0%。

04 上下文压缩：少发 token，但不少给信息

4.1 先做预算表，再谈压缩

超预算时的裁剪优先级（写进配置，别让工程师现场拍脑袋）：

4.2 结构化裁剪：零模型成本，收益最大

手段 例子 收益
工具结果字段白名单 API 返回 40 字段，只留 6 个 常见 −60%~−90% 工具 token
截断 + 分页 limit=50、max_chars=1500，超长给”取更多”的工具 防止单次调用炸上下文
去重合并 同文档相邻 chunk 合并 −10%~−30% 检索 token
只给 ID 不给正文 模型返回订单号，前端自己渲染 输出 token 大幅下降
结构化格式 表格/CSV/JSON 比自然语言更省字 −30% 左右
文档预处理 OCR/解析后只留正文，去掉页眉页脚、HTML 标签 检索与输入同时降
别塞 base64 图片转文字/摘要，或用视觉模型直传 避免离谱的 token 消耗

4.3 摘要与滚动记忆

三条原则：

  1. 结构化摘要 > 散文摘要：数字、ID、硬约束、承诺必须逐项保留，散文最容易把”不超过 3 天”写成”尽快”；
  2. 增量摘要：旧摘要 + 新增轮次 → 新摘要，别每轮重算全量历史；
  3. 只在历史超阈值时触发：短会话压缩省的 token 抵不上摘要调用的成本。

失效模式：早期约束被摘要掉 → 模型反复给已被拒绝的方案。缓解：把”不可协商约束”单独拎出来放进稳定层（每轮固定发送，且能命中缓存），普通对话才走摘要。

4.4 检索侧压缩（RAG 最容易省）

  • top-k 收紧：塞 20 段远不如 rerank 后给 3~5 段，多数场景准确率反而更高（噪声少了）；
  • 抽取式压缩：只保留命中问题的句子；
  • 父子文档：小块命中、传相关段落而不是整篇长文；
  • 多样性去冗：MMR 或按文档去重，避免五段几乎一样的内容；
  • 不要传全文给模型再问”哪段相关”：这是最贵的写法。

4.5 Prompt 本体瘦身

要点：形容词不改变行为，约束和输出契约才改变行为。few-shot 示例是最贵的 token——从 5 个减到 2 个往往只掉 1~2 个点准确率，但省 40%+ 前缀；减与不减，用评测集说话。

4.6 输出侧压缩

手段 做法
max_tokens 按历史 P95 输出长度设上限，别留无限空间
结构化返回 JSON schema，字段替代自然语言长段落
禁止复述 明确”不要重复用户问题，直接给结论”
简洁档位 同一能力用 style: concise/detail 双档，默认简洁
不生成不需要的字段 摘要+解释+建议三件套，多数场景只要摘要

4.7 “上下文窗口又大又便宜，还要压缩吗”

要，原因不是钱：

  1. 延迟：长输入意味着 prefill 计算量随长度显著上升，P95 会被拉长；
  2. 有效注意力：长上下文里”中间信息丢失”，塞 200 段不会让模型更准，只会更慢更贵；
  3. 成本仍然随 token 线性：单价低不等于免费；
  4. 缓存与内存：长会话的 KV 复用效率更差。

结论：便宜 ≠ 免费 ≠ 有效。压缩既是成本手段，也是质量手段。

4.8 怎么确认压缩没掉质量

  • 每次改压缩策略都跑固定回归集（≥200 条），并记录”最坏案例”而不是只看均值；
  • 高风险链路保留直通通道：金额、法务、事故处理走”不压缩 + 大模型 + 人工复核”。

05 其它高 ROI 手段

手段 说明 注意
Batch API 离线任务批量提交，常见约五折 非实时，要处理部分失败与对账
蒸馏 / 微调小模型 高频固定任务长期降本 + 降延迟 需要数据、评测和维护成本
传统算法前置 分类用向量/BM25/正则，抽取用规则 + schema 能用确定性方案就别问模型
LLM-as-Judge 抽样 全量评审成本极高，改成 5%~10% 抽检 与人工标注校准一致性
预算护栏 per-tenant / per-user 预算、单请求 token 上限、异常熔断 防止循环调用把账单打爆
重试策略 只在格式错误时重试，最多 1~2 次 + 指数退避 5xx/限流不等于可盲目重试
多供应商同能力 价格、限流、故障切换 前缀缓存不跨供应商共享
流式输出 不影响账单，改善感知延迟 别为了流式重复请求一次

06 组合案例：客服问答的成本从 $0.0156 → $0.0042

步骤 动作 账单影响 质量影响 验证方式
0 归因 建 llm_call_log，按 feature 拆成本 — — 发现 60% 输入是固定前缀且 0 命中
1 前缀重排 时间戳/请求 ID 移出 system，工具定义排序固定 −42% 无 缓存读 token 从 0 → 72%
2 模型路由 意图与抽取走小模型，投诉走大模型 −35% −0.4pt（可接受） 分任务回归 + 5% 灰度
3 RAG 收紧 top20 → top5 + rerank −28% 输入 +1.8pt 同评测集前后对比
4 历史压缩 超过 6 轮转结构化滚动摘要，硬约束常驻稳定层 长会话输入 −45% 持平 关键点回归（数字/ID 保留率）
5 语义缓存 FAQ 类只读问题缓存，含 tenant/ACL key 22% 请求零调用 抽检一致 命中答案抽检 + 负反馈失效
6 输出契约 JSON schema + max_tokens + 禁止复述 输出 −18% 格式合规率 ↑ 合规率与截断率监控

结果：单次会话成本 −73%，P95 延迟 2.4s → 1.1s，答案正确率 87.2% → 88.1%（示例数字）。

顺序很关键：先重排前缀（几乎零风险），再收紧检索（通常还能涨质量），最后才动路由（质量风险最高）。

07 落地节奏与验收

阶段 内容 产出 回滚
0 归因（约 1 周） 调用日志、成本看板、评测集 成本分布 + 基线指标 —
1 缓存布局（约 1 周） 前缀重排、命中率打点 命中率与节省曲线 布局可配置回退
2 路由（约 2 周） 静态规则 + 级联，灰度放量 分任务回归报告 一键切回大模型
3 压缩（约 2 周） RAG top-k、结构化摘要、输出契约 token/质量对照表 直通通道保留
4 结构优化 语义缓存、批处理、蒸馏小模型 长期成本基线 逐 feature 灰度

08 高频面试题

Q1：如何系统性地降低大模型应用成本？
A：先归因（调用日志拆到 feature 级，区分输入/输出/推理/缓存 token），再按三个因子下手：模型路由降单价、缓存降重复成本、上下文压缩降 token 数；配套手段是减少轮次、批处理、蒸馏小模型。顺序上先做零风险的前缀重排和检索收紧，最后才动路由，每步都用评测集和灰度验证。

Q2：提示词缓存为什么没命中？
A：最常见是前缀不稳定——把时间戳/请求 ID 写进 system、工具或 JSON 字段顺序抖动、few-shot 动态洗牌、改写早期历史、把租户差异混进公共前缀、换模型或 prompt 版本没对齐。另外前缀长度不足门槛或超出 TTL 也不会命中。

Q3：模型路由会不会伤质量？怎么保证？
A：会，所以要做三件事：分任务回归（不用总体平均分）、给两类错分定价（简单判难是浪费钱，难判简单是事故）、灰度加一键回退。高风险任务直接固定大模型不路由，同时保留级联兜底：小模型低置信或校验失败就升级。

Q4：语义缓存的风险和 key 怎么设计？
A：风险是错误命中、时效、越权和缓存投毒。key 必须包含租户与权限范围哈希、prompt 版本、模型 ID，并按内容类型设 TTL；写入时校验有依据，负反馈触发失效。只对只读幂等的高频重复问题开。

Q5：上下文压缩会不会丢关键信息？
A：会，所以用结构化摘要（目标、事实、约束、待办、ID 分字段）而不是散文摘要，并把不可协商的硬约束放在每轮固定发送的稳定层。每次改压缩都跑固定回归集，看关键点保留率，而不是只看平均分。

Q6：输出比输入贵，怎么压输出？
A：max_tokens 按 P95 设限、JSON schema 代替长段落、明确禁止复述问题、只返回渲染需要的字段（ID 而非全文）、默认简洁档。同时注意推理型模型的思考 token 也按输出计费，要单列监控。

Q7：Agent 成本失控一般是什么原因？
A：工具结果原样塞回上下文、轮次无上限、每轮重写系统提示导致缓存全废、重试风暴。解法：工具输出裁剪白名单、max_iterations 与早停、并行独立工具调用减少轮次、前缀冻结、重试只针对格式失败且限次。

Q8：长上下文很便宜了，还需要 RAG 和压缩吗？
A：需要。便宜不等于免费，也不等于有效：长输入 prefill 延迟上升，且”中间信息丢失”让塞更多文档不一定更准；RAG 还解决权限过滤与来源可溯。正确做法是检索精排给 3~5 段，长上下文用于少量整篇分析类任务。

Q9：怎么控推理 token？
A：任务分级（能不走思考模型就不走）、限制思考预算（若供应商支持）、拆分步骤避免一次复杂推理膨胀、把确定性逻辑交给代码而不是模型、监控思考 token/输出 token 比值作为路由信号。

Q10：缓存 TTL 怎么定？
A：按内容变化频率而不是拍脑袋：静态知识小时级甚至不失效，库存价格秒级或干脆不缓存，FAQ 分钟到小时级；配合”数据写入即失效”的事件驱动，比单纯缩短 TTL 更省。同时要盯 TTL 与提示词缓存续期机制的关系，间隔太长命中率会掉。

Q11：成本、延迟、质量能同时优化吗？
A：常能，因为它们大多来自同一个源头——多余的 token。前缀重排、检索收紧、工具结果裁剪、减少轮次，通常三者一起改善；冲突点是”用更贵的模型换更高准确率”和”语义缓存省成本但可能陈旧”，这些要用评测集和 SLA 明确取舍。

Q12：你怎么证明优化真的有效？
A：四件套：固定评测集离线前后对比、灰度 A/B 看线上业务指标（转人工率、投诉率、任务成功率）、成本看板看 token 结构（输入/输出/推理/缓存读）而不是只总额、以及 P95 延迟与错误率不劣化。任何只看”账单变小”的结论都不算数。

09 一页纸速查

关键词 一句话
成本公式 Token 数 × 单价 × 调用次数，三个因子三招
归因先行 分 feature 记输入/输出/推理/缓存四类 token

10 60 秒面试话术

问题：”你们的 AI 功能成本太高，你会怎么优化？”

参考回答：

我先把成本拆开，而不是直接换模型。第一步建调用归因表，按业务功能记录输入、输出、推理和缓存读取四类 token，因为多轮会话每轮重发历史，累计输入接近平方级增长，很多团队的钱其实浪费在这里。第二步做提示词缓存：把 system、工具定义、固定示例和长期知识放在稳定层并按固定顺序序列化，会话历史只追加，时间戳和请求 ID 挪到最后，这一步几乎零风险，我们那次命中率从 0 提到 70% 多，输入侧成本降了四成。第三步压上下文：RAG 从 top20 收紧成 rerank 后取 3~5 段，工具结果做字段白名单和分页，长会话用结构化滚动摘要并把硬约束常驻稳定层，输出侧用 schema 加 max_tokens 禁止复述——这三步通常成本降了质量还略升，因为噪声少了。第四步才是模型路由：静态规则加级联兜底，简单抽取走小模型，涉钱和对外内容固定大模型加人工，灰度放量并用分任务回归证明质量不掉，配置化一键回退。最后对高频重复的只读问题做语义缓存（key 含租户和权限哈希）、离线任务走批处理、稳定任务再考虑蒸馏小模型。验收标准是三条同时满足：每千次成本下降、质量指标不降、P95 延迟不升。

最后记住三句话：

  1. 优化顺序是”布局 → 裁剪 → 路由 → 缓存结果”：风险从低到高，收益从确定到需要权衡，反过来做多半要回滚。
  2. 省钱的本质是少发 token，而少发 token 通常同时降延迟、升质量：真正需要取舍的是”更便宜的模型”和”可能陈旧的缓存”。
  3. 没有归因表和回归集的降本都是玄学：账单下降不等于成功，”成本降、质量不降、延迟不升”三条同时成立才算数。
