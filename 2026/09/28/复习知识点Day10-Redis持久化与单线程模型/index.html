复习知识点Day10：Redis持久化与单线程模型

一句话记住今天：Redis = 内存里的单线程执行引擎 + 持久化兜底。本篇抓三条主线：① 持久化（RDB 快照 / AOF 日志 / 混合持久化，各有丢数据窗口与恢复速度的取舍）；② 线程模型（命令执行永远是单线程，6.0 起网络 IO 可多线程，还有后台 bio/lazy free 线程）；③ 面试高频考点（选型、触发方式、恢复优先级、fork + COW、为什么单线程还快）。

1. Redis 是什么：先 5 分钟找回记忆

  • 定位：基于内存的高性能 Key-Value 数据库，数据主要在内存，所以快（单机轻松 10 万+ QPS）。
  • 常见用途：缓存、分布式锁、计数器/排行榜、限流、消息队列（Stream/PubSub）、分布式会话。
  • 为什么面试爱考 Redis：绝大部分 Java 后端天天在用，但 90% 的人说不清”数据怎么落盘””到底几个线程”，这两点正是本文主线。

2. Redis 内存持久化方案（重点一：背对比表）

Redis 数据在内存，进程一退出就全没了，所以要有持久化。方案有三类：RDB（快照）、AOF（追加日志）、混合持久化（4.0+）。

2.1 RDB：内存快照（二进制）

  • 过程：把某个时间点的全量内存数据序列化写成 dump.rdb（二进制，体积小）。
  • 触发方式（面试必背）：
    • SAVE：同步阻塞主线程生成，生产别用；
    • BGSAVE：fork 子进程异步生成，主线程继续服务（推荐）；
    • 自动触发：满足 save 条件（如 save 900 1 300 10 60 10000，即 900 秒内有 1 次写 / 300 秒 10 次 / 60 秒 1 万次）；
    • 优雅关闭且允许保存时；主从复制全量同步时 master 也会 bgsave 生成 RDB 发给从机。
  • 原理图（必会画）：
  • 优点：文件小、恢复快（一次加载全量）、方便做定期备份/异地灾备。
  • 缺点：两个快照之间写的数据会丢（丢数据窗口大）；fork() 瞬间可能阻塞主线程（大实例明显）；快照期间写多时 COW 会让内存临时上涨。

2.2 AOF：追加写日志

  • 过程：把每一条写命令追加到 appendonly.aof（文本，可读可审计），启动时重放命令恢复数据。
  • 配置开关 appendonly yes；写回策略三档（背熟）：
策略 配置值 fsync 时机 丢数据风险 速度
每改必刷 always 每条写命令都 fsync 几乎不丢（最多宕机瞬间那一条） 最慢
每秒刷一次（推荐） everysec 每秒 fsync 一次 最多丢 1 秒左右的数据 快
交给系统 no 由操作系统决定何时落盘 不可控 最快
  • 文件内容示例（注意是 RESP 协议文本）：
  • AOF 文件会越来越大，所以要自动重写 bgrewriteaof：
    • 触发：auto-aof-rewrite-percentage 100（较上次重写增长 100%）且 auto-aof-rewrite-min-size 64mb（超过 64 MB）；
    • 重写 = 基于当前内存生成最小命令集（比如 100 次 incr 合并成一次 set），不是简单清旧文件；
    • 重写期间新命令先进 aof_rewrite_buf 缓冲，子进程完成后合并，保证不丢。
  • 优点：丢数据少（everysec 最多 ~1 秒）；可读、可修复。
  • 缺点：文件比 RDB 大；恢复重放慢；fsync 频繁影响写性能。

抢答点：”AOF 重写时主进程还能继续服务吗？”能。它和 BGSAVE 一样走 fork + COW，重写期间新写命令先进缓冲区，两阶段合并。

2.3 混合持久化（Redis 4.0+，生产首选）

  • 配置：aof-use-rdb-preamble yes。
  • 形态：AOF 文件头部是RDB 全量快照，尾部追加AOF 增量命令。
  • 收益：加载快（RDB 头）+ 丢数据少（增量尾巴），两者优点兼得。Redis 7.0 还升级成”多分区 AOF”（manifest + base + incr），重写更稳。

2.4 数据恢复优先级（面试高频）

  • AOF 文件损坏 → redis-check-aof --fix 修复；RDB 损坏 → redis-check-rdb 校验兜底。
  • 生产必须定期把 RDB 文件备份到异地：AOF/RDB 文件都丢，数据救不回。

2.5 选型建议（面试答题模板）

使用场景 推荐方案
纯缓存，丢数据无痛 关持久化（省 IO 和 fork）
缓存 + 数据，可容忍丢几秒 RDB + AOF everysec + 混合持久化（生产标配）
严格不丢数据 AOF always（性能代价大，一般不用）
灾备/离线恢复 RDB 定期全量 + AOF 增量，异地备份

3. 单线程还是多线程（重点二）：别再答错了

3.1 一句话结论

命令执行 + 主事件循环 = 单线程；网络 IO（6.0+）= 多线程；后台脏活（bio / lazy free）= 多线程。

所以面试答”Redis 是单线程”不完整，答”Redis 6.0 是多线程”更不对：核心命令执行始终由一个主线程串行完成。

3.2 版本时间轴（背时间点）

版本 变化 说明
2.x ~ 5.x 全单线程 命令执行、网络 IO 都单线程（IO 多路复用）
4.0 引入 Lazy Free UNLINK/FLUSHDB ASYNC 等大 key 删除放后台线程（bio）异步释放
6.0 网络 IO 多线程 io-threads 只分担读写解析，命令执行仍是主线程单线程（默认关）
7.0 多分区 AOF 让 AOF 重写/加载更稳，不改变单线程执行模型

3.3 为什么单线程还能这么快（背这 5 条）

  1. 纯内存：读写不落盘（持久化除外），随机 IO 都在 RAM；
  2. 数据结构高效：跳表、哈希、quicklist/压缩列表等专用结构，读写复杂度低；
  3. IO 多路复用（epoll/kqueue）：单线程同时监听大量 socket，事件驱动；
  4. 免锁免切换：单线程执行命令 → 无竞争、无锁、无上下文切换（性能最大来源）；
  5. 命令本身快：单命令 O(1)/O(logN)，没有复杂 SQL 计算灾难。

事件循环简图：

6.0 的网络 IO 多线程只是把”读请求、写响应”分工给 io-threads 个线程，第 2 步命令执行依然由主事件线程串行跑。

3.4 为什么命令执行不搞多线程（进阶加分）

  • CPU 不是瓶颈：Redis 瓶颈主要是内存容量和网络带宽，多线程救不了这些瓶颈；
  • 多线程引入锁竞争、缓存一致性问题，Redis 的并发优势恰好是”无锁”；
  • 要吃掉多核：主流是多实例分片/集群（每实例仍是单线程核心），而非给单实例加命令线程。

3.5 “线程”细节追问（高级）

追问 答案
bgsave 期间还能写吗 能。fork 后父子共享内存，写触发 COW 复制页，快照干净
fork 为什么会阻塞 复制页表耗时；内存越大、fork 越慢，大实例可能阻塞几百 ms 到秒级
删除大 key 会卡吗 会。同步 DEL 大集合阻塞；用 UNLINK 走后台 lazy free
后台还有哪些线程 bio 线程：文件/关闭、AOF fsync、lazy free；bgsave/rewrite 还有子进程
COW 内存翻倍吗 写多少页翻多少页，写越猛涨越多，需监控内存占用

4. 面试高频考点清单（重点三）：背题表来了

4.1 持久化方向

常问考法 答题要点
几种持久化方案 RDB、AOF、混合（4.0+）
RDB 触发方式 save / bgsave / 自动条件 / 主从全量复制
AOF 写回策略 always / everysec / no，区别丢几秒
AOF 文件膨胀 bgrewriteaof（重写 + 缓冲合并）
恢复优先级 AOF 优先，无 AOF 用 RDB
混合持久化 快照 + 增量双保
Fork 阻塞 复制页表耗时 + COW 内存放大
丢数据结论 RDB 窗口大；AOF everysec ≤1 秒；always 几乎不丢

4.2 单/多线程方向

常考考法 答题要点
Redis 是单线程吗 执行命令单线程；6.0 网络 IO 多线程；后台 bio/lazy free 线程
为什么快 内存 + IO 复用 + 单线程无竞争 + 数据结构
6.0 多线程做什么 分担 socket 读出写回，不碰数据执行
懒删除 unlink / flushdb async，释放大 key 不阻塞
阻塞命令 keys、大集合全量、save、fork、同步 DEL 大 key
