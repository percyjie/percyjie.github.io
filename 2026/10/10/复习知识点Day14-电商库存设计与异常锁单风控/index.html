复习知识点Day14：电商库存设计与异常锁单风控

一句话记住今天：可售库存 = 实际库存 − 锁定库存；下单锁库存、支付扣库存、超时释放库存。而异常锁单风控要解决的正是”某个用户短时间把库存锁光，正常用户下不了单”——本质是用规则和限流，把异常流量挡在”锁库存”这个动作之前。面试抓四块：① 三种库存口径与扣减时机；② 防超卖（原子扣减 + 幂等）；③ 锁定库存的释放（延迟消息 + 状态机）；④ 异常锁单的成因与分层风控。

先说结论：库存是一台状态机

先记住这三个口径和一条流转公式：

口径 典型字段 含义 主要用途
实际库存 total_stock 仓库里真实还有多少件 财务、盘点、上架
锁定库存 locked_stock 已下单未支付、被”占住”的数量 释放、对账、风控
可售库存 total - locked 还能卖给用户的数量 前端展示、下单校验

面试开场白：”我们的库存不是单一数字，而是’实际库存 + 锁定库存’两个字段，可售库存实时相减得到。下单只锁不扣，支付成功才真正扣减，未支付超时再释放——这样才能在防超卖和用户体验之间取平衡。”

一、库存模型设计

1.1 表结构

库存不落”可售”这个冗余字段，而是用实际 + 锁定两个字段实时计算，避免三处数据不一致：

如果 QPS 很高，可以在 Redis 里放一份”可售库存”做预扣减，DB 作为最终账本，但任何时刻以 DB 为准，Redis 只是加速层。

1.2 库存扣减的三个时机

时机 做法 优点 缺点
下单减库存（锁库存） 下单即锁 防超卖最稳 恶意锁单会占库存
支付减库存 支付成功才扣 用户体验好 高并发下极易超卖
预占 + 支付确认（两阶段） 下单预占、支付确认 兼顾 实现复杂、要处理悬挂

结论：绝大多数电商用“下单锁库存”，代价就是要配套超时释放 + 异常锁单风控——这正是本文重点。

1.3 防超卖：必须原子扣减

错误写法（先查后改，并发下必超卖）：

两个请求同时读到”库存 1”，都判断通过，最后锁了 2 件 → 超卖。

正确写法一：SQL 原子更新 + 判断影响行数

正确写法二：Redis Lua 原子扣减（秒杀等高并发场景）

再配合订单号唯一索引做幂等，重复请求不会重复扣库存。

二、锁定库存与释放

2.1 锁定 → 支付 → 释放的完整链路

2.2 释放的三种触发

触发 场景 实现
支付超时 用户下单不付款 延迟消息到期检查，未支付则释放
主动取消 用户点”取消订单” 立即释放
支付失败 / 退款 支付失败、售后退款 释放或回补实际库存

2.3 为什么用延迟消息，而不是定时任务

  • 定时任务扫表：实现简单，但延迟大（取决于扫描周期）、表大时扫表压力大；
  • 延迟消息（RocketMQ 延迟消息 / RabbitMQ TTL + 死信队列 / Redis ZSet 延时队列）：下单时投递一条 15 分钟延迟消息，到点消费，实时、精准、对 DB 无扫描压力；
  • 工程上常见做法：延迟消息为主 + 定时任务兜底（消息丢了还有兜底扫描）。

释放必须幂等：用订单状态机 + UPDATE ... WHERE status = WAIT_PAY 的 CAS 判断，避免延迟消息重复消费导致库存被多次回补。

三、异常锁单：一个用户短时间大量下单，别人下不了单

这是本文的核心场景，值得单独拆开讲。

3.1 现象还原

某用户（或脚本）在 3 秒内对同一 SKU 下单 200 单，把 locked_stock 顶到 total_stock：

结果就是库存饥饿（starvation）：货没卖出去，钱没收到，正常用户却买不到。

3.2 危害

  • 库存饥饿：正常用户全程买不到，体验崩坏；
  • 黄牛囤货：低价抢购后转卖，平台和用户双输；
  • 大促被打乱：秒杀 / 限购活动的库存被脚本吃掉；
  • 真实损失：免支付 / 货到付款场景，恶意下单可能直接造成资损。

3.3 为什么”限购”不够

很多系统只做”每个用户限购 N 件”，但只统计已支付订单。恶意用户可以不付款：每次下单只锁库存、不支付，等超时后再下——限购形同虚设。

关键认知：要限制的是”未支付的锁定量”，而不是”已购买量”。

3.4 分层防御（从便宜到重，面试重点）

层次 手段 说明
1 限购（用户 × SKU） 校验口径 = 已支付 + 待支付 + 购物车，而不只是已支付
2 锁定量上限 单用户对单 SKU 未支付锁定量 ≤ X 件（直击占用问题）
3 下单频率限制 令牌桶 / 滑动窗口，如 10 秒最多 1 单、1 分钟最多 5 单
4 用户维度限流 单用户整体 QPS 限流，防脚本高频刷
5 设备 / IP 维度 设备指纹 + IP 归属，识别多账号同设备
6 名单体系 黑名单拒绝、灰名单挑战、白名单放行
7 人机校验 异常时弹验证码 / 滑块，提高脚本成本
8 排队削峰 大促用 MQ + 令牌，只放行”库存数量”的请求
9 加速释放 缩短支付超时（15 分钟 → 5 分钟）、风控命中主动释放

3.5 核心设计：把”锁库存”变成有门槛的动作

风控必须在锁库存之前，任何一步不通过都不进入锁库存，这样异常流量零成本被挡掉：

如果风控是异步的（事后复查），一旦判定订单异常，要主动取消订单并立即释放锁定库存，不能干等超时。

四、风控技术设计（简单版）

4.1 接入点：前置 + 后置

  • 前置（同步）：下单前实时判定，只跑”快而准”的规则，拦截明显异常（高频、超限、黑名单）；
  • 后置（异步）：事后审计、补充名单、人工复核，复杂分析不拖慢下单主链路。

原则：前置做拦截，后置做发现，不要在下单链路上跑重模型。

4.2 规则引擎（最简可用版）

把风控抽象成”维度 + 时间窗 + 阈值 + 动作”的规则表：

维度 时间窗 阈值示例 动作
用户 × SKU 下单次数 1 分钟 > 5 拒绝 / 验证码
用户 × SKU 未支付锁定量 — > 3 件 拒绝
用户 下单次数 1 分钟 > 20 拒绝
同 IP 下单次数 1 分钟 > 100 限流
同设备下单次数 1 分钟 > 10 验证码
新账号 + 高频下单 5 分钟 命中组合 人工 / 挑战

用 Redis 滑动窗口做计数，一条 Lua 完成”清理过期 + 判断 + 计数”：

4.3 名单体系

名单 动作 典型来源
黑名单 直接拒绝 历史恶意下单、刷单、欺诈
灰名单 强制验证码 / 人工审核 疑似黄牛、异常设备
白名单 放行 内部账号、VIP、合作方

4.5 风控与库存联动

  • 风控拒绝 → 不锁库存（零成本）；
  • 风控异步判定异常 → 主动取消订单 + 立即释放锁定库存；
  • 监控风控命中率与误杀率，用白名单和申诉通道兜住误伤。

五、兜底与对账

风险 兜底方案
少量超卖 原子扣减防住绝大多数；残余用补货 / 退款 / 协商处理
锁定量与未支付订单对不上 定时对账：locked_stock vs SUM(未支付订单数量)
Redis 与 DB 库存不一致 以 DB 为准，定时用 DB 重建 / 校准 Redis
释放消息丢失 定时任务扫超时订单兜底
风控误杀 白名单 + 申诉通道 + 阈值灰度调整

必看监控指标：可售库存、锁定率（locked / total）、锁单失败率、释放延迟、异常用户数、风控拦截率。

六、常见面试题（背这组）

面试题 一句话答案
库存有哪几种口径？ 实际库存、锁定库存、可售库存，可售 = 实际 − 锁定
下单减库存还是支付减库存？ 一般下单锁库存、支付才扣减，防超卖
怎么防超卖？ SQL 原子更新 WHERE total-locked>=n 判断影响行数；或 Redis Lua 原子扣减
为什么不能”先查再改”？ 检查与修改之间有并发间隙，两个请求会同时通过 → 超卖
锁定库存怎么释放？ 延迟消息到期检查，未支付则释放；定时任务兜底；状态机 CAS 保证幂等
释放用定时任务还是延迟消息？ 延迟消息实时性好、无扫表压力；定时任务做兜底
一个用户大量下单导致别人买不到？ 限购（含未支付）+ 锁定量上限 + 用户/设备/IP 限流 + 名单 + 验证码 + 排队
为什么只做”限购”不够？ 恶意用户不付款、只锁库存，所以要限制”未支付锁定量”而非”已购量”
风控放在哪一层？ 下单前置同步拦截 + 异步事后复查，前置不跑重模型
风控规则怎么落地？ Redis 滑动窗口 / 令牌桶计数 + 规则表 + 加权评分
库存与订单怎么保证一致？ 订单号幂等 + 状态机 CAS + 定时对账
秒杀怎么削峰？ MQ 排队 + 令牌放行 + Redis 预扣 + 多层限流

7. 自测三问

  1. 画出”下单 → 支付 → 超时释放”的库存字段变化时间线，并说明每一步如何保证幂等（重复请求、重复消息都不出错）。
  2. 某用户 3 秒内对同一 SKU 下单 200 单把库存锁满，正常用户下不了单。给出至少 5 层防御方案，并说明每层分别拦住什么。
  3. 设计”单用户对单 SKU 未支付锁定量不超过 3 件”的校验：数据从哪来、并发下怎么保证不超限、和限购如何配合？

下一篇预告：可以复习「秒杀系统全链路设计（Redis 预扣 + MQ 削峰 + 防刷）」或「订单状态机与分布式事务」，把库存、订单、支付这条线彻底串起来。
