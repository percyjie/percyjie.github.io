一句话记住今天：冷热接口分离解决”资源别互相拖累”，热点 Key 治理解决”单点别被打爆”，分库分表解决”单机存不下、写不动”。这三件事有严格的先后顺序：先用冷热分离和缓存削掉无效流量，再治理热点 Key，最后才动分库分表。上来就分库分表，往往是把一个缓存能解决的问题，做成分布式问题。

先说结论：三层问题，三套手段

问题 本质 第一手段 什么时候才升级
冷热接口互相影响 线程、连接、CPU 等资源竞争 接口拆分 + 线程池/连接池隔离 + 超时降级 单机资源仍被打满 → 独立集群/单元化
热点 Key 流量集中到单个 Key/单行/单分片 本地缓存 + Key 拆分 + 限流 + 单写者 单分片仍扛不住 → 热点探测系统/专用集群
单表太大、写入瓶颈 单机容量与吞吐上限 索引、缓存、读写分离、归档 上述都做完仍不够 → 分库分表/NewSQL

三句话概括：

  1. 冷热分离是”隔离”：让核心链路和非核心链路不共享瓶颈资源。
  2. 热点 Key 是”打散”：把对单点的访问分散到本地缓存、多个 Key、多个副本。
  3. 分库分表是”拆分”：把数据和写压力拆到多个库表，代价是分布式复杂度。

01 冷热接口分离：先把”热”和”冷”分清楚

1.1 三个容易混的概念

概念 分离对象 解决的问题 典型做法
冷热接口 按 QPS、重要性划分的 API 低频重接口拖垮高频核心接口 接口拆分、独立线程池、独立集群、异步化
冷热数据 按访问频率、时间划分的数据 热数据占内存、冷数据占存储 Redis/本地缓存、归档到 HBase/ClickHouse/OSS
读写分离 读请求与写请求 读多写少时读流量压垮主库 主从复制、读从库、强制走主库

“接口冷热”不是”数据冷热”。 一个接口可能访问的是热数据，但它本身是低频的（比如后台导出）；也可能接口 QPS 很高，但数据是只读的（比如商品详情）。先按”接口”分资源，再按”数据”分存储。

1.2 怎么判断哪些接口是热的

别凭感觉，看指标。至少采集这几类：

指标 看什么 用途
QPS / 峰值 QPS 接口调用量级 判断资源需求
P95 / P99 RT 尾部延迟 判断 SLA 和超时设置
CPU / GC / 线程池队列 单机资源消耗 判断是否需要隔离
连接池占用 DB/Redis/下游连接 判断是否共享瓶颈
缓存命中率 本地/Redis 判断缓存是否有效
下游 RT / 错误率 依赖服务健康度 判断降级边界
业务重要性 是否影响下单/支付 判断优先级

一个典型的电商接口分层：

接口 QPS 量级 目标 RT 分类 策略
商品详情核心字段（标题、价格、库存） 5 万+ P99 < 50ms 热/核心 本地缓存 + Redis，独立线程池
评价列表、推荐、广告 几千 P99 < 300ms 温/非核心 并行调用，超时降级为空
历史订单查询 几十 1s 内 冷 独立服务/冷库，分页限制
报表导出 个位数 分钟级 冷/重 异步任务，完成通知

经验法则：满足”二八定律”的少数接口就是热接口，但还要叠加”业务重要性”——QPS 不高但影响支付的接口，也必须按核心链路对待。

1.3 四种分离手段

手段 做什么 解决什么 代价
接口拆分 核心/非核心、读/写、同步/异步拆开 避免一个慢接口拖垮整个页面 调用链变长、聚合逻辑变复杂
资源隔离 独立线程池、连接池、Redis 集群、DB 防止故障和流量互相传染 资源利用率下降、运维成本上升
数据分层 热数据缓存、温数据 MySQL/ES、冷数据归档 降低热存储成本和查询压力 跨源查询、数据一致性
部署隔离 独立集群、单元化、租户隔离 隔离故障域和发布影响 机器成本、发布复杂度

最重要的原则：只拆接口不隔离资源，等于白拆。 两个接口还共用同一个 Tomcat 线程池、同一个 DB 连接池，慢接口照样能把连接占满。

1.4 代码：线程池隔离 + 超时降级

  • 核心链路不要用 CallerRunsPolicy：队列满时让 Web 线程自己执行，会把入口线程也拖住；核心链路更适合快速失败 + 降级。

1.5 案例：商品详情页怎么拆

拆分后的收益：

变化 拆分前 拆分后
非核心推荐服务抖动 整个详情页超时 核心字段正常返回，推荐位为空
大促流量上涨 所有接口抢同一线程池 核心链路资源有保障
冷数据查询 抢占 DB 连接 走 CDN/冷库/异步导出

前端配合很关键：核心接口先渲染，非核心接口后填充。不要让非核心数据阻塞首屏。

1.6 冷热接口分离的坑

  1. 只做接口拆分，不做资源隔离：仍然共享线程池/连接池，故障照样传染。
  2. 拆得太细：一个页面调十几个服务，网络开销和失败概率反而上升；按”业务能力”拆，不按”字段”拆。
  3. 冷接口同步调用：导出、报表这类分钟级任务必须异步化，否则会占满线程。
  4. 跨库跨服务事务：拆分后还要求强一致，会把架构复杂度推向分布式事务；优先按业务边界保证最终一致。
  5. 冷数据归档后不可查：归档方案必须包含查询入口、恢复流程和保留周期。

02 热点 Key：从发现到治理

2.1 热点 Key 和大 Key 不是一回事

类型 判定 主要危害 典型场景
热点 Key 单个 Key 的 QPS 远高于平均值 Redis 单线程被打满、Cluster 槽位倾斜、DB 被击穿 秒杀库存、明星微博、热搜、爆款商品
大 Key Value 过大或集合元素过多 网络阻塞、命令耗时、删除卡顿、内存不均 巨型 Hash、全量用户列表、大 JSON
热点大 Key 两者叠加 最危险，可能直接拖垮实例 爆款商品的超大详情缓存

经验阈值（不是硬标准）：

  • String 类型 Value 超过 10KB，就要关注；
  • Hash/List/Set/ZSet 元素超过 5000，就要考虑拆分；
  • 单 Key 的 QPS 占实例总 QPS 超过 10%，基本可以判定为热点。

2.2 怎么发现热点 Key

方法 命令/工具 优点 局限
热点分析 redis-cli --hotkeys 直接列出访问频率高的 Key 需要 LFU 淘汰策略，采样可能漏
大 Key 扫描 redis-cli --bigkeys 快速找大 Value 只扫类型和大小，不反映访问频率
单 Key 内存 MEMORY USAGE key 精确看内存占用 只能逐个查
慢日志 SLOWLOG GET 找耗时命令 热点 Key 不一定慢
实时命令 MONITOR 能看到全部命令 性能开销大，禁止生产长期开启
代理/云监控 代理层指标、云厂商监控 有现成的 Key 级 QPS 依赖基础设施
客户端采样 本地计数 + 定时上报 能结合业务维度 有采样误差和内存成本

客户端采样的简单实现：

生产环境不要对每个 Key 都计数，按业务前缀或采样率统计即可；已知的大促商品、秒杀 SKU 应该提前加入”重点观察名单”，不能等监控发现。

2.3 六种治理手段

手段 适用 效果 代价
本地缓存 读多写少、可容忍短暂不一致 把热点挡在 Redis 之前 多节点一致性、内存占用
Key 拆分 读热点、计数、库存 把单 Key 压力分散到 N 个 Key 写放大、聚合逻辑复杂
多副本读 读多写少 利用从库分担读 主库写仍是瓶颈、复制延迟
热点探测系统 热点变化快、规模大 自动发现并推送到本地缓存 建设成本高
限流/降级 突发流量、恶意请求 保护系统不被压垮 会损失部分请求
单写者队列 热点行更新、库存扣减 串行化写，避免行锁冲突 增加延迟、需要幂等

3）多副本读

Redis Cluster 支持从副本读（客户端开启 READONLY），可以把读流量分摊到多个副本。但要清楚：

  • 副本只能分担读，主库的写和过期删除仍然集中；
  • 主从复制有延迟，强一致读必须走主库；
  • 热点 Key 仍然只属于一个槽位，副本解决的是”读吞吐”，不是”槽位倾斜”。

4）热点探测系统

大规模系统会自建热点探测：客户端上报 Key 访问量 → 聚合节点滑动窗口统计 → 判定为热点后推送到各应用本地缓存。京东 Hotkey、有赞 TMC 都是这个思路。核心价值是自动发现 + 自动推送，减少人工配置。

5）限流与降级

对单 Key 做令牌桶限流，超过阈值直接返回缓存旧值或默认值：

秒杀场景可以配合”排队/答题/验证码”把无效流量挡在 Redis 之前。

6）单写者队列

数据库热点行更新（比如库存扣减）不要多线程直接抢行锁，而是按 Key 哈希到同一个队列/分区，由单线程串行处理：

这样能把随机的行锁竞争变成顺序写，吞吐更高；代价是增加延迟，需要做好幂等和积压监控。

2.4 案例：秒杀库存 Key 怎么拆

假设单个 SKU 有 1 万件库存，峰值 10 万 QPS 都打在一个 stock:sku:1001 上。方案：

  1. 把库存拆成 16 个桶，每个桶 625 件；
  2. 请求随机选一个桶，用 Lua 原子扣减；
  3. 当前桶不足时，再尝试其他桶；
  4. 展示库存时累加 16 个桶。

优点：单 Key 压力被分散到 16 个槽位，Redis 单线程和网卡压力都下降。

代价：

  • 读总库存要聚合 16 次，接口要做缓存；
  • 某个桶空了但其他桶还有货，需要重试逻辑；
  • 桶数量变更时要重新分配库存，必须停机或做双写迁移。

如果业务要求”绝对不超卖”，分桶扣减是可以做到的（总量等于各桶之和）；如果业务要求”严格 FIFO”，分桶反而不合适，应该用单写者队列。

2.5 热点 Key 的坑

  1. 本地缓存不一致：更新后广播丢失，读到旧值；用短 TTL + 版本号兜底。
  2. 随机后缀写放大：N 个分片都要写，写 QPS 乘 N；只适合读热点。
  3. 拆分后仍同槽：Cluster 模式下乱加 hash tag，等于没拆。
  4. 缓存击穿：热点 Key 过期瞬间大量请求打到 DB；用互斥锁/单飞（singleflight）或逻辑过期。
  5. 大 Key 删除阻塞：用 UNLINK 异步删除，不要用 DEL。
  6. 只治缓存不治 DB：Redis 挡住了，但缓存失效时 DB 仍会被打穿；DB 侧也要有限流和队列。

03 分库分表：先判断要不要做

3.1 什么时候才需要分库分表

先看经验阈值（不同业务差异很大，仅作判断参考）：

信号 参考阈值 说明
单表行数 1000 万~5000 万 索引深度增加、DDL 变慢、查询抖动
单表数据量 50~100GB 备份恢复、迁移成本急剧上升
单库 QPS 5000~10000+ 单实例 CPU/连接成为瓶颈
连接数 单实例 70% 以上 连接池频繁等待
DDL 时长 分钟级以上 影响发布和在线稳定性
备份/恢复 超出维护窗口 故障恢复不可接受

但先别急着分，按顺序问自己：

一句话：分库分表是最后一张牌，不是第一张牌。 它能解决容量和写入扩展，但会引入分布式 ID、跨库查询、分布式事务、扩容迁移等一整套复杂度。

3.2 垂直拆分与水平拆分

类型 怎么拆 解决 例子
垂直分库 按业务拆到不同数据库 业务耦合、单库压力 用户库、订单库、商品库
垂直分表 宽表按字段冷热拆开 单表列多、大字段拖慢查询 商品基础表 + 商品详情表
水平分表 同一张表按行拆成多张 单表数据量过大 t_order_0..63
水平分库 同一张表拆到多个库 单库写入/连接瓶颈 ds_0..3.t_order_0..15

通常的顺序是：先垂直分库（业务边界清晰）→ 再水平分库分表（单表仍然太大）。

3.3 分片键怎么选（最关键的一步）

分片键选错，后面全是补丁。选型看五条：

  1. 基数高：status、gender 这种只有几个值的字段不能做分片键。
  2. 分布均匀：避免大客户/大租户把某个分片打爆。
  3. 查询能命中：绝大多数查询都要带分片键，否则会广播到所有分片。
  4. 稳定不变：分片键一旦变更，意味着跨分片迁移数据。
  5. 业务相关性：同一业务聚合的数据尽量落在同一分片，避免跨分片事务和 Join。
业务 推荐分片键 理由 风险
用户 user_id 按用户查、基数高、分布均匀 按手机号查需要额外索引
订单（用户视角） user_id “我的订单”天然按用户查 按 order_id 查详情需要基因/映射
订单（商家视角） merchant_id 商家后台按商家查 用户视角查询会跨分片
聊天消息 session_id 同一会话有序、查询集中 按用户查所有会话需要额外表
多租户 SaaS tenant_id 租户隔离、便于计费 大租户会倾斜，需要二次拆分
日志 tenant_id + 时间分区 按租户和时间查 只按时间查会广播

订单表最经典的难题：按 user_id 分片后，用户查自己的订单很快；但订单详情页只给了一个 order_id，怎么路由？

常见解法：

方案 做法 优点 缺点
基因法 把 user_id % N 编进 order_id 低位 无需额外存储，直接路由 分片数变化后基因失效
映射表 order_id → user_id 存 Redis/DB 灵活 多一次查询，映射表也会大
广播查询 所有分片查一遍 实现简单 分片多时不可接受
搜索引擎 订单数据同步到 ES 支持多维度查询 数据同步和一致性成本

基因法示意：

前提是分片数固定为 1024（或能整除的规模）；未来扩容时，基因法需要重新设计，所以很多团队会预分片，一开始就规划足够的逻辑分片。

3.4 分多少片：用数字算，不要拍脑袋

假设订单表现有 2 亿行，每天新增 50 万行，规划 3 年：

方案 库数 每库表数 总表数 3 年后每表行数
64 片 4 16 64 约 1170 万
128 片 4 32 128 约 586 万
256 片 8 32 256 约 293 万

建议：

  • 分片数取 2 的幂，方便取模和后续翻倍扩容；
  • 单表控制在 500 万~1000 万行，单库表数不要过多（否则连接和 DDL 管理复杂）；
  • 预留 2 倍以上增长空间，但不要一开始就分 1024 片，造成大量小表和管理负担；
  • 分片数一旦确定，扩容成本很高，宁可前期多规划一点。

ShardingSphere-Proxy 独立代理 语言无关、统一入口 多一跳网络、代理运维 多语言、统一治理
MyCat 代理 社区方案、SQL 兼容 社区活跃度和生态较弱 存量系统
TiDB / OceanBase / PolarDB-X NewSQL 透明扩缩容、强一致、支持分布式事务 成本高、运维复杂、学习曲线 预算充足、强一致要求
MySQL 分区表 单实例分区 改造成本最低 不解决单机瓶颈 按时间归档、单机内管理

面试时别只说”用 ShardingSphere”，要能说清楚：为什么选客户端还是代理、分片键是什么、跨分片查询怎么解决。

3.6 分库分表后的六个硬问题

问题 现象 解法
分布式 ID 自增 ID 在各分片重复 Snowflake、Leaf、号段模式；避免 UUID 做主键
非分片键查询 不知道去哪个分片 基因法、映射表、ES、广播（最后手段）
跨分片分页/排序 每片都要查，内存聚合 各片取 Top N 归并；深分页用游标/ES
分布式事务 跨库写入无法本地事务 同分片绑定、本地事务 + MQ 最终一致、Saga/TCC
全局唯一约束 各分片唯一索引不跨库 分布式 ID、独立唯一索引表、业务幂等
扩容迁移 取模变化导致大量数据搬迁 预分片、双写迁移、一致性哈希

1）分布式 ID

Snowflake 结构：

注意点：

  • 机器 ID 要统一分配，避免重复；
  • 时钟回拨要处理（等待、抛错或切换备用 worker）；
  • 单机每毫秒 4096 个序列，普通业务足够；
  • UUID 虽然简单，但无序、占空间、影响 B+ 树插入性能，不适合做主键。

2）跨分片分页

假设按 user_id 分成 256 片，要查”全站最新 100 条订单”：

深分页更糟：LIMIT 100000, 20 需要每片取 100020 条再归并，内存和网络都会爆炸。解法：

  • 限制最大页数（如最多 100 页）；
  • 用游标：WHERE create_time < last_time ORDER BY create_time DESC LIMIT 20；
  • 复杂搜索/排序交给 ES/ClickHouse，MySQL 只负责按 ID 取详情。

3）分布式事务

优先级从高到低：

  1. 避免跨分片：分片键设计时把关联数据放同一片（同一用户的订单和订单明细都按 user_id）。
  2. 本地事务 + MQ：核心写本地库，发消息让下游最终一致；用 Outbox 表保证消息一定发出。
  3. Saga/TCC：跨服务长事务，要设计补偿和幂等。
  4. XA/Seata AT：强一致但性能和运维成本高，谨慎使用。

面试金句：能用分片键避免的分布式事务，就不要用分布式事务框架解决。

4）扩容迁移

三种路线：

路线 做法 优点 缺点
预分片 一开始建 1024 张逻辑表，映射到少量物理库 扩容只需搬逻辑表 前期表多、管理复杂
双写迁移 新旧集群同时写，迁移存量后切读切写 可控、可回滚 双写一致性、周期长
一致性哈希 节点增减只影响相邻数据 迁移量小 实现复杂、仍有数据倾斜

3.8 迁移落地方案（重点）

分库分表真正的难点不是写配置，而是怎么把存量数据安全迁过去，并且能回滚。推荐七步：

阶段 动作 关键产出 回滚策略
0 评估设计 容量测算、分片键、分片数、SLA 设计文档、容量表 —
1 建新集群 新库表、中间件、监控、告警 可运行的新集群 保留旧集群
2 双写/CDC 应用双写或 Canal 订阅 binlog 增量同步链路 关闭双写，回到旧库
3 全量迁移 DataX/DTS 分批导数，限速 存量数据迁移完成 重跑迁移任务
4 增量追平 binlog 持续同步，监控延迟 新旧数据追平 暂停切流
5 数据校验 行数、checksum、抽样、业务对账 一致性报告 修复后重跑
6 灰度读 按用户/流量比例读新库，双读比对 灰度报告 切回旧库
7 切写收尾 停旧写、切新写、观察、下线旧库 新集群全量运行 保留回滚窗口

每一步的细节：

阶段 0：评估

  • 算清楚 3 年数据量、峰值 QPS、单分片目标；
  • 确定分片键和分片数，评估跨分片查询比例；
  • 明确迁移窗口、可接受停机时间、回滚 SLA。

阶段 1~2：双写还是 CDC？

方式 做法 优点 缺点
应用双写 业务代码同时写新旧库 实时、可控 侵入业务、一致性难保证
CDC/binlog Canal 订阅旧库 binlog 写新库 业务无侵入 有延迟、需处理 DDL

双写要保证幂等（唯一键/版本号），并监控双写失败；CDC 要监控同步延迟和位点。

阶段 3：全量迁移

  • 用 DataX/DTS 分批导出，控制批次大小和速率，避免打满旧库；
  • 迁移顺序：先字典/配置，再业务主表，最后关联表；
  • 记录每批的位点，失败可续传。

阶段 4：增量追平

  • 全量迁移期间旧库仍在写，必须靠 binlog 增量追平；
  • 监控 seconds_behind_master 和自定义延迟指标；
  • 延迟稳定在秒级以内才进入校验。

阶段 5：数据校验

校验层次：

  1. 行数：总量是否一致；
  2. checksum：关键字段汇总是否一致；
  3. 抽样：随机抽 1000 条逐字段比对；
  4. 业务对账：订单金额、库存、账务等关键指标对账。

阶段 6：灰度读

  • 按 user_id % 100 选择 1% 用户读新库；
  • 双读比对新旧结果，记录差异；
  • 逐步放量到 10%、50%、100%；
  • 发现差异立即切回旧库，不影响用户。

阶段 7：切写

  • 停旧库写入前，确认增量延迟为 0、校验通过；
  • 切写后保留双写/回滚开关至少一个观察周期；
  • 监控 P99、错误率、慢 SQL、分片倾斜；
  • 稳定后再下线旧库和同步链路。

迁移的核心原则：每一步都可回滚、每一个差异都可定位、每一笔数据都可对账。

3.9 面试怎么答：2 亿订单表怎么分

问题：”订单表 2 亿行，日增 50 万，怎么分库分表？”

参考回答：

  1. 容量：3 年后约 7.5 亿行，按单表 500 万规划需要 150 片，取 256 片（8 库 × 32 表），每片约 293 万行。
  2. 分片键：按 user_id 分片，满足”我的订单”查询；order_id 用 Snowflake 并把 user_id % 1024 编入低位，支持订单详情直接路由。
  3. ID：Snowflake，机器 ID 统一分配，处理时钟回拨。
  4. 查询：用户维度走 user_id；订单详情走基因 order_id；商家/运营维度同步到 ES，避免广播。
  5. 事务：同一用户的订单和订单明细都按 user_id 分片，保证同库本地事务；跨服务用本地消息表 + MQ 最终一致。
  6. 迁移：双写 + 全量 DataX + 增量 Canal + 行数/checksum 校验 + 灰度读 + 切写 + 回滚窗口。
  7. 观测：分片倾斜、P99、慢 SQL、同步延迟、双写失败率。

04 三者怎么组合：一个完整案例

以”商品详情 + 订单查询”为例，三层手段各司其职：

流量/问题 对应手段
商品详情 QPS 高 本地缓存 + Redis + 核心/非核心接口拆分
秒杀库存单 Key 热点 库存分桶 + Lua + 限流
评价/推荐拖慢首屏 独立线程池 + 超时降级
历史订单查询慢 冷热数据分离 + ES/冷库 + 异步导出
订单表 7 亿行 按 user_id 分库分表 + Snowflake + 基因路由
跨分片查询 ES/宽表/映射表，禁止无脑广播

05 一页纸速查

关键词 一句话记忆
冷热接口 按 QPS + 业务重要性分，核心/非核心拆开
资源隔离 独立线程池、连接池、集群，避免故障传染
冷热数据 热数据缓存、温数据 MySQL/ES、冷数据归档
读写分离 读走从库，强一致读走主库
热点 Key 单 Key QPS 远超平均，易打满单线程/单槽位
大 Key String > 10KB 或集合 > 5000 元素，考虑拆分
热点发现 --hotkeys、--bigkeys、慢日志、客户端采样
本地缓存 Caffeine + 短 TTL + Pub/Sub 失效
Key 拆分 随机后缀/分桶；Cluster 下别加相同 hash tag
热点行 单写者队列 + MQ 按 Key 分区 + 批量合并
分片阈值 单表千万级/50GB+、单库 QPS 到瓶颈再考虑
分片键 基数高、分布匀、查询带、稳定、业务相关
基因法 把 user_id 编进 order_id，支持订单详情路由
分片数 取 2 的幂，按 3 年容量算，留 2 倍余量
分布式 ID Snowflake/Leaf，避免 UUID 做主键
跨分片分页 各片 Top N 归并；深分页用游标/ES
分布式事务 优先同分片本地事务，其次 MQ 最终一致
迁移七步 评估→建集群→双写/CDC→全量→增量→校验→灰度切流

06 60 秒面试话术

问题：”一个高并发交易系统，怎么解决冷热接口、热点 Key 和分库分表？”

参考回答：

我会分三层处理。第一层是接入和接口层：按 QPS 和业务重要性把接口分成核心、非核心和冷接口，核心接口独立线程池和连接池，非核心设置超时降级，冷接口异步化，避免慢接口拖垮下单链路。第二层是缓存层：对读热点做本地缓存 + Redis，热点 Key 用分桶或随机后缀打散，库存这类写热点用单写者队列或 Redis 分桶 + Lua，配合限流保护 Redis 和 DB。第三层是存储层：先做索引、缓存、读写分离和冷数据归档，确实到单机瓶颈再分库分表；订单按 user_id 分片，order_id 用 Snowflake + 基因法支持详情查询，同用户订单和明细同分片保证本地事务，跨服务用 MQ 最终一致。迁移按双写、全量、增量、校验、灰度读、切写、回滚窗口七步走。最后用 P99、分片倾斜、缓存命中率、同步延迟和一致性差异来验证效果。

最后记住三句话：

  1. 冷热分离的核心不是”拆接口”，而是”隔离资源”：线程池、连接池、集群不隔离，拆了也白拆。
  2. 热点 Key 的核心不是”加缓存”，而是”打散单点”：本地缓存、分桶、多副本、限流，按读写类型选组合。
  3. 分库分表的核心不是”配置中间件”，而是”分片键 + 迁移方案”：分片键决定查询和事务复杂度，迁移方案决定能不能安全上线。
