复习知识点Day3：JVM 垃圾回收调优与线上排查

一句话记住今天的内容：JVM 调优不是调参数，是”先用工具定位问题，再改最少的东西”。线上九成的”调优”其实是排查：CPU 飙高先找线程栈，内存上涨先看 GC 与堆 dump；参数永远是最后一步。

1. 调优前提：先定指标，再动手

没有指标的调优都是玄学。默认盯四组数：

指标 含义 正常参考
吞吐量 用户代码运行时间占比（1 - GC 时间/总时间） 追求越高越好，一般 99% 量级
暂停时间（STW） 每次 GC 的 Stop-The-World 时长 G1 目标默认 200ms，ZGC 毫秒级
GC 频率 Young GC 每秒几次、Full GC 多久一次 Young 频繁但短可接受，Full GC 越少越好
堆占用曲线 堆使用率是否长期平稳 持续上涨说明可能有泄漏

推荐流程：开 GC 日志/监控采集基线 → 定位 GC 阶段与代际 → 判断是”参数不合适”还是”代码有问题” → 一次只改 1 个参数 → 灰度对比 → 观察一周 → 再动下一个。

2. 常用调优参数速查

参数 作用 建议
-Xms / -Xmx 初始/最大堆 生产建议两者相等，避免运行期扩容抖动
-Xmn / -XX:NewRatio 新生代大小/比例（默认 1:2） 对象 n 代、可用吞吐场景可适当加大新生代
-XX:SurvivorRatio Eden 与 Survivor 比例（默认 8） G1 会自适应，一般不用手调
-XX:MaxGCPauseMillis G1 的停顿目标 默认 200ms，调太小反而导致频繁调整
-XX:MaxMetaspaceSize 元空间上限 必须设，防动态代理/热部署泄漏
-XX:MaxRAMPercentage 容器内 JVM 可用内存比例 容器场景用 75 左右，别写死固定 -Xmx
-XX:+HeapDumpOnOutOfMemoryError + -XX:HeapDumpPath OOM 自动导出堆 dump 线上必须开
-Xlog:gc* GC 日志（JDK 9+ 语法） 排查第一步，先开起来

3. 调优与排查工具清单（必记）

工具 一句话用法 常用示例
jps 列出本机 Java 进程 jps -l
jstat 看 GC 频率、堆占比 jstat -gcutil <pid> 1000
jinfo 看/改 JVM 参数 jinfo -flags <pid>
jstack 看线程栈（CPU 高/死锁） jstack <pid>
jmap 堆信息/导出 dump（会 STW，谨慎） jmap -dump:format=b,file=a.hprof <pid>
jcmd JVM 通用诊断命令 jcmd <pid> GC.heap_dump /tmp/a.hprof
jfr / java -XX:StartFlightRecording JFR 飞行记录 低开销长期记录
Arthas 线上热诊断：thread / dashboard / vm thread -n 3 找最忙线程
MAT 分析 hprof：Leak Suspect、Dominator、GC Roots 泄漏排查主力
VisualVM / GC Easy 图形查看堆、分析 GC 日志 调参前后对比

小坑：jmap 或 jcmd 的堆导出都会暂停 JVM，生产最好在低峰/压测环境做，别在线上高峰直接 jmap -dump。

4. 线上 CPU 飙高排查（四步法，背下来）

现象：top 里 JAVA 进程 CPU 100%+，接口 RT 变长。

  1. 锁定进程：top 找到高 CPU 的 Java PID。
  2. 锁定线程：top -Hp <pid> 找到 CPU 最高的线程 TID。
  3. TID 转 nid：printf '%x\n' <tid> 转 16 进制，线程栈里对应 nid=0x…。
  4. 看线程栈分类：jstack <pid> > /tmp/jstack.txt（等价 jcmd <pid> Thread.print），搜 nid=0x… 所在的栈，判断：业务线程异常，还是 GC 线程风暴。

根因快速分类表：

线程情况 常见根因 处理方向
栈里循环/序列化/正则 死循环、正则回溯、JSON 序列化、日志刷屏 排查代码，加超时/限流
GC 线程（GC/GC Thread） Young GC 或 Full GC 频繁：堆太小、大对象、泄漏 jstat -gcutil 看 GC 频率，再 GC 日志/dump
synchronized 阻塞/自旋 锁竞争、死锁、资源排队 看线程状态 BLOCKED/WAITING，优化锁粒度
内核态高（st/系统调用多） 磁盘 IO、网络重试、Native 调用 看系统指标：IO、网络、FD 数

口诀：top → top -Hp → nid → jstack，先排除”GC 风暴”，再看业务代码。

5. 线上内存泄漏排查

前提判断：堆使用率持续上涨、GC 后不回落、Full GC 越来越频繁且回收量很少，基本都是泄漏；偶尔一两次 GC 后回落则可能是”突发流量/缓存”。

四步法：

  1. 确认趋势：jstat -gcutil <pid> 1000 观察 O（老年代）持续上升；配合 GC 日志看 Full GC 频率。
  2. 导出堆 dump：jcmd <pid> GC.heap_dump /tmp/app.hprof（低峰期）。
  3. MAT 分析：Leak Suspects → Dominator Tree 找”吃内存最大的对象” → Path to GC Roots 看是谁一直在引用它。
  4. 定位代码：按引用的调用栈回到业务代码，找异常持有者（静态集合、线程、监听器）。

最高频的泄漏模式表：

模式 表现 修复
静态/集合类只增不减 堆上涨且按业务量单调递增 换成有界缓存/定时清理
ThreadLocal 未 remove 线程池下”脏数据串线”+ 泄漏 finally 里 remove
监听器/回调未注销 对象被注册表强引用 组件销毁时注销
ClassLoader 泄漏 热部署、动态加载类，老年代暴涨 控制加载路径、复用一个 ClassLoader
连接/流/池未关闭 堆外/堆内资源同时泄漏 try-with-resources 关闭
缓存无上限/不过期 堆缓慢上涨 换 Caffeine/Guava 带过期策略

别忘了非堆内存：

  • Metaspace：动态代理/CGLIB/反射类太多，-XX:MaxMetaspaceSize 兜底，超了先查类加载器数量（jcmd <pid> VM.class_histogram）。
  • 直接内存（DirectBuffer/Netty）：-XX:NativeMemoryTracking=summary 开启后，用 jcmd <pid> VM.native_memory summary 看进程占用。

6. 调优的红线（踩坑清单）

  1. 参数不是越多越好：生产上常见过度调参（比如堆/GC 参数堆砌），效果不如先修 bug。
  2. 一次只动一个变量：否则无法判断归因。
  3. 别把”调优”当决策：Full GC 频繁先查泄漏/大对象，再来调参数；调优掩盖不了”代码 GG”。
  4. 先有数据再有结论：监控、GC 日志、dump 三者先于任何 YAML。

7. 常见面试题（背这组）

问题 一句话答案
JVM 调优从哪一步开始？ 先看 GC 指标与日志，再决定参数；一次改一个
CPU 飙高排查命令序列？ top → top -Hp → printf %x → jstack 看线程栈
Full GC 频繁的常见根因？ 堆太小、内存泄漏、大对象、Metaspace 满、G1 参数不适
内存泄漏怎么定位？ GC 日志+jstat 确定趋势 → dump → MAT 找 GC Roots 持有者
jmap -dump 为什么线上慎用？ 会 STW（暂停），高峰可能放大故障
你有用哪些 JVM 工具？ jstat/jcmd/jstack + Arthas + MAT（按场景说）
OOM 有哪些类？ 堆、栈、Metaspace、直接内存，异常名和排查方法不同
G1 调优主要动哪几个参数？ -Xms/-Xmx/-XX:MaxGCPauseMillis/-XX:MaxMetaspaceSize

8. 自测三问

  1. 线上 CPU 100%，写出完整命令链条（含 TID 转 nid 那一步）。
  2. 堆持续上涨但没 OOM，怎么区分是”活对象太多”还是”内存泄漏”？
  3. 调优时为什么强调”一次只改一个参数”？
