一句话记住今天：这八道题看似分散，考的其实是同一种能力——把”组件怎么工作”讲到”线上会出什么问题、你怎么兜底”。Redis 的渐进式 rehash 与大 key、MySQL 的 B+ 树查找与 WAL 落盘、RabbitMQ 的推拉与背压、线程池参数的推导、Redisson 看门狗的续期边界、热 Key 的定位与打散、非自增主键的代价。每题的答法都是四段：结论 → 机制 → 边界/坑 → 项目里怎么做。

先说结论：八题速览

# 问题 一句话答案 追问高发点
1 Redis rehash 流程，大 key 会卡吗 渐进式分步迁移，不整体卡；卡的是大 key 的 O(N) 命令 rehash 期间读写怎么找 key、SCAN 怎么遍历
2 MySQL 索引查 age=30 二级索引定位到首个 30，沿叶子链表扫完，再回表取整行 为什么可能不走索引、覆盖索引
3 MySQL 写盘是顺序还是随机 日志顺序写、数据页随机写，WAL 把随机写异步化 两阶段提交、组提交、脏页刷盘
4 RabbitMQ 推还是拉，要轮询吗 默认推（basic.consume），靠 prefetch 背压；basic.get 才需轮询 堆积、流控、和 Kafka 拉模式的区别
5 为什么 IO 密集 2N、CPU 密集 N+1 CPU 加一是留余量；IO 线程多数时间在等，用 N×(1+W/C) 下游容量上限、利特尔法则、虚拟线程
6 看门狗续期时间怎么定，一直续期有问题吗 默认 30s 租期、每 1/3 续一次；一直续期会掩盖 hang 和分区双持有 leaseTime、fencing token、长 GC
7 Redis 热 Key 怎么定位、怎么解决 --hotkeys/埋点定位；本地缓存 + Key 拆分 + 限流 Cluster 槽位倾斜、hash tag 陷阱
8 主键不自增有什么问题 破坏聚簇索引插入局部性，页分裂、碎片、随机 IO 全局唯一 ID、二级索引变大

记忆锚点：Redis 怕”单点大”，MySQL 怕”随机写”，MQ 怕”消费者慢”，线程池怕”无界队列”，锁怕”忘记释放”，主键怕”随机插入”。

01 Redis rehash：大 key 会不会卡住

1.1 为什么需要两张表

Redis 的字典（dict）内部维护 ht[0] 和 ht[1] 两张哈希表。平时只有 ht[0] 在工作，触发扩容/缩容时给 ht[1] 分配新表，然后把元素逐步迁过去。

状态 ht[0] ht[1] rehashidx
正常 使用中 空 -1
rehash 中 只减不增 只增 当前迁移到的桶下标
完成 释放 成为新 ht[0] -1

1.2 什么时候扩容、扩到多大

1.3 渐进式 rehash 五步

  1. 给 ht[1] 分配空间，rehashidx = 0；
  2. 每次增删改查顺带迁移一个非空桶（不是一次性搬完）；
  3. 空闲时 serverCron 每次最多迁 100 个桶、限时 1ms，避免长时间占用事件循环；
  4. 迁移期间：读先查 ht[0] 再查 ht[1]；写只写 ht[1]；删除两边都查；
  5. 全部迁完：释放 ht[0]，交换两张表，rehashidx = -1。

1.4 大 key 到底会不会卡

结论：rehash 本身不会因为大 key 卡住，因为迁移的是”键值对条目”（指针），不是把 value 整体复制一遍。真正卡住的是大 key 上的 O(N) 命令。

操作 复杂度 影响
DEL 百万元素的 Hash/List/Set/ZSet O(N) 同步释放，阻塞事件循环
HGETALL / SMEMBERS / LRANGE 0 -1 O(N) 大结果集、网络与内存双杀
KEYS * O(N) 全库扫描，生产禁用
SORT、FLUSHDB、MIGRATE O(N)/O(全库) 明显抖动
大 key 过期 同步删除 过期瞬间卡顿
RDB/AOF 重写、主从全量同步 O(数据量) fork + COW、带宽压力

1.5 生产处置

手段 说明
UNLINK 代替 DEL 后台线程异步释放（lazy free）
HSCAN + 分批 HDEL 大 Hash 分段清理，控制单次耗时
拆 key 按时间/ID 分段，单 key 元素控制在几千以内
SCAN 代替 KEYS 游标遍历，不阻塞
开 lazyfree-lazy-user-del 用户删除也走异步释放
监控 redis-cli --bigkeys、MEMORY USAGE、SLOWLOG、LATENCY DOCTOR

1.6 面试怎么答

“Redis 的 rehash 是渐进式的：扩容时给 ht[1] 分配两倍空间，每次命令顺带迁移一个桶，空闲时 serverCron 每轮最多 100 个桶、限时 1ms，所以不会整体卡住。迁移期间读先查 ht[0] 再查 ht[1]，写只写 ht[1]。大 key 不会因为 rehash 被整体搬动，因为迁移的是指针；但大 key 上的 DEL、HGETALL、KEYS 是 O(N)，会阻塞单线程，所以生产用 UNLINK、HSCAN 分批删，并把大 key 拆小。”

可能追问：”rehash 期间 SCAN 会不会漏 key？”——SCAN 用反向二进制迭代，能容忍 rehash 期间表大小变化，但允许重复返回；保证”遍历期间一直在的 key 至少返回一次”，业务侧要去重。

02 MySQL 索引查找：WHERE age = 30 到底怎么查

2.1 先看 B+ 树长什么样

  • 非叶子节点只存索引键 + 页指针，不存整行；
  • 二级索引叶子存 (age, 主键)；
  • 聚簇索引（主键）叶子存整行数据；
  • 叶子节点之间有序链表，天然支持范围扫描。

2.2 五步查找过程

  1. 从根页开始，页内二分查找，定位到 30 可能所在的子页；
  2. 逐层向下，直到叶子页；
  3. 找到第一个 age = 30 的记录（非唯一索引不保证唯一）；
  4. 顺着叶子链表继续向右扫，直到 age > 30 为止；
  5. 每条记录拿主键，去聚簇索引回表取整行。

如果索引是 (age, name) 且只查这两列：

2.3 为什么优化器可能”有索引也不用”

原因 说明
匹配行太多、区分度低 回表是随机 IO，扫 30% 的行可能不如全表顺序扫
SELECT * 列多 回表成本高，覆盖索引又覆盖不了
统计信息过期 估算行数失真，选错计划；ANALYZE TABLE 修正
隐式转换 age 是 varchar 却写 age = 30，列被转成数字，索引失效
列上有函数/运算 WHERE age + 1 = 31 用不上索引

2.4 面试怎么答

“二级索引的叶子节点存的是 age 和主键，非叶子只存 age 和页指针。查 age=30 时从根页二分定位到叶子，找到第一个 30，因为不是唯一索引，要沿叶子链表继续扫到大于 30 为止；然后拿每条记录的主键回聚簇索引取整行。如果查询列都在索引里就是覆盖索引，不用回表。优化器也可能因为匹配行太多、回表随机 IO 太贵而选择全表扫描，所以要结合 EXPLAIN 的 rows、filtered 和实际数据分布判断。”

可能追问：”为什么二级索引不直接存整行？”——省空间、减少写放大；代价是回表，所以才有覆盖索引这个优化方向。

03 MySQL 写磁盘：顺序写还是随机写

3.1 一条 update 的完整链路

关键结论：事务提交成功 ≠ 数据页已落盘。 持久性靠 redo log，数据页是异步刷的。

3.2 哪些顺序、哪些随机

组件 写入方式 说明
redo log 顺序 循环文件追加写，checkpoint 推进后覆盖
binlog 顺序 追加写，文件切换时 rotate
doublewrite 顺序 先顺序写双写区，再写数据页，防页损坏
数据页 随机 16KB 一页，按页号定位，位置分散
undo 页 随机 undo tablespace 页式存储
二级索引 随机 非唯一索引可用 change buffer 缓冲合并
聚簇索引插入 近似顺序 自增主键追加；随机主键触发页分裂

一句话：日志顺序写，数据随机写；WAL 让”等日志”代替”等数据页”。

3.3 为什么这样设计还快

机制 作用
WAL 提交只等顺序日志，随机数据页写延后
组提交（group commit） 多个事务合并一次 fsync
异步刷脏 多个 page cleaner 并发刷，不阻塞提交
change buffer 非唯一二级索引写先缓冲，后续 merge，减少随机读改写
自增主键 聚簇索引追加，减少页分裂
O_DIRECT 绕过 OS page cache，避免双缓冲
SSD 随机写差距缩小，但顺序仍更优

3.4 关键参数与坑

参数 建议 代价
innodb_flush_log_at_trx_commit 金融用 1；普通业务可压测后放宽 0/2 崩溃可能丢 1 秒事务
sync_binlog 与上者配合用 1 降低提交吞吐
innodb_flush_method 常用 O_DIRECT 依赖文件系统行为
innodb_io_capacity(_max) 按磁盘能力设置 太低刷不动，太高打满 IO
innodb_max_dirty_pages_pct 控制脏页上限 太高导致突发刷脏抖动

大事务的代价：redo/undo 膨胀、脏页集中刷导致抖动、锁持有时间长、回滚慢。批量操作要分批提交（比如每 500~1000 行一次）。

3.5 面试怎么答

“不是二选一。redo log 和 binlog 是顺序追加写，数据页是随机写。InnoDB 用 WAL：事务提交只保证 redo 和 binlog 落盘，数据页还在 Buffer Pool 里是脏页，由后台 page cleaner 异步刷，checkpoint 推进后 redo 才能复用。所以提交快，但’提交成功’不等于’数据页已写盘’，崩溃恢复靠 redo。写入性能还依赖组提交、change buffer、doublewrite 和自增主键减少页分裂。”

可能追问：”redo 和 binlog 区别？”——redo 是 InnoDB 物理日志、循环写、崩溃恢复；binlog 是 Server 层逻辑日志、追加写、主从复制与按时间点恢复；两阶段提交保证两者一致。

04 RabbitMQ：推还是拉，拉消息要一直轮询吗

4.1 默认是推模式

  • broker 把消息主动推到消费者 socket，消费者库内部有分发线程；
  • 业务代码不需要轮询；
  • 消费能力靠 basic.qos(prefetchCount) 控制：未 ack 的消息达到上限，broker 就停止推送，这就是 RabbitMQ 的背压。

4.2 拉模式 basic.get 的问题

问题 说明
需要循环调用 取不到就返回 null，持续消费只能自己轮询
空转开销 短 sleep 浪费延迟，长 sleep 浪费吞吐
每次一条 批量场景效率低
经典队列不支持长轮询 不像 Kafka 的 poll(timeout) 能挂起等待
公平性差 多个消费者各自抢，难以精确控制节奏

结论：RabbitMQ 里说”拉”，通常是”推模式 + prefetch + 手动 ack”实现可控消费，而不是 basic.get 轮询。 需要按 offset 回放/拉取的场景用 RabbitMQ Streams。

4.3 推模式的流控与可靠性

机制 作用
prefetch 控制单消费者未 ack 在途数，防止被压垮
手动 ack 处理成功才确认，失败可 nack/requeue
publisher confirm 确认消息已到 broker，防生产端丢
mandatory / return 路由失败回退给生产者
死信队列 重试超限、过期、被拒绝的消息隔离
连接/通道流控 broker 内存/磁盘告警时阻塞发布端

4.4 和 Kafka 的区别

维度 RabbitMQ Kafka
消费模型 推（broker 推给消费者） 拉（消费者 poll）
节奏控制 broker 按 prefetch 推 消费者自己控制拉取量
长轮询 经典队列无 poll(timeout) 天然长轮询
消息语义 队列入队出队、灵活路由 分区日志、按 offset 回放
堆积能力 堆积到内存/磁盘，性能下降明显 顺序日志，天然适合大量堆积

4.5 面试怎么答

“RabbitMQ 默认是推模式，消费者 basic.consume 之后 broker 主动推，不需要业务轮询；用 basic.qos 设置 prefetch，控制未 ack 的在途消息数形成背压，配合手动 ack 保证可靠性。basic.get 才是拉模式，每次取一条，取不到返回空，要持续消费就得循环，空转和延迟都不划算，经典队列也没有长轮询。所以生产不用 get 轮询，堆积时应该扩消费者、调 prefetch、批量 ack、死信隔离，而不是加轮询。”

可能追问：”prefetch 调大是不是吞吐更高？”——单消费者处理快时可以提高，但下游慢时只会把消息堆在客户端内存里，延迟和 OOM 风险都上升；要按处理能力和下游容量定。

05 线程池：为什么 IO 密集 2N、CPU 密集 N+1

5.1 两个公式的来由

  • CPU 密集 N+1：N 个核跑 N 个线程已经打满；+1 是为了某个线程发生缺页、GC、锁等待时还有线程能用上 CPU。再多只会增加上下文切换和缓存失效。
  • IO 密集 2N：线程大部分时间在等 DB、RPC、磁盘，不占 CPU，要多开线程把 CPU 填满。等待时间和计算时间大致相当时，N × (1+1) = 2N。等待是计算的 9 倍，就是 10N——2N 只是经验值，不是定律。

5.2 还有三个上限，别只套公式

上限 说明
下游容量 DB 连接池、第三方 QPS、LLM 并发配额；线程再多也只会排队
内存 每线程栈 512KB~1MB，几百线程就是几百 MB
竞争与切换 锁竞争、上下文切换、缓存失效，可能越加越慢

5.3 配置只是第一步，配套更重要

配套 做法
业务隔离 LLM、PDF、通知、导出各一个池，避免互相拖垮
有界队列 无界队列 = 把 OOM 延后，还会让拒绝策略失效
拒绝策略 核心链路 CallerRuns 降速；非核心丢弃 + 告警；不能默认 Abort 抛给用户
上下文传递 TaskDecorator 传 traceId/租户，finally 清理
监控 active、queueSize、rejected、任务等待时长；队列 80% 或拒绝 > 0 告警
关键任务持久化 先落任务表/MQ，进程重启可补偿

5.4 虚拟线程能替代吗

  • JDK 21 起可用，IO 密集场景收益明显；
  • JDK 21 时代 synchronized 会 pinning 载体线程，JDK 24（JEP 491）已改善；
  • 但瓶颈会转移到连接池和下游限流，线程不再是瓶颈时，加线程没有意义；
  • 不要无脑替换，先看下游容量和阻塞点。

5.5 面试怎么答

“CPU 密集按核数加一，留一点余量应对缺页和 GC；IO 密集用 N×(1+等待/计算)，等待和计算差不多就是 2N，但它只是经验值。实际还要受下游容量、内存和锁竞争约束，比如 LLM 单次 2 秒、下游只允许 10 QPS，并发上限就是 20，超了只能排队或降级。队列必须有界，按可接受等待时间乘处理速率估长度；拒绝策略按业务分级，核心降速、非核心丢弃告警，并且不同下游用独立线程池隔离。”

06 Redisson 看门狗：续期时间怎么定，一直续期有问题吗

6.1 机制

项 默认值/行为
lockWatchdogTimeout 30 秒（锁的初始租期）
续期间隔 租期的 1/3，即 10 秒
生效条件 只有在没有显式指定 leaseTime 时才启用
显式 leaseTime 看门狗不生效，到期自动释放

6.2 为什么是 1/3

留出两次续期失败的容忍窗口：如果每 1/3 续一次，即使连续两次网络抖动导致续期失败，租期还剩约 10 秒，不会立刻丢锁；同时续期频率不会高到给 Redis 造成额外压力。

6.3 一直续期会有什么问题

问题 场景 后果
业务 hang 住/忘记 unlock 死循环、线程阻塞、异常路径漏 unlock 锁被无限续期，别人永远拿不到
网络分区 客户端以为持锁，Redis 侧已过期，另一客户端拿到 两个持有者同时写
长 GC STW 超过租期，业务还在跑但锁已过期 并发写入、数据错乱
定时器开销 锁数量很大 大量续期任务和 timer 压力
无限等待 业务没有超时控制 请求堆积、线程池耗尽

6.4 生产实践

  1. 能预估时长就传 leaseTime，不要让看门狗兜底一切；
  2. tryLock(waitTime, leaseTime, unit) 设置获取等待，避免无限阻塞；
  3. finally 里 unlock，并校验持有者（Redisson 已用唯一 value 校验）；
  4. 关键业务加幂等 + 版本号/fencing token，防止分区下的双持有写坏数据；
  5. 监控锁持有时间，超过阈值告警；
  6. 锁内不要做长 RPC、等用户输入、批量大任务。

6.5 面试怎么答

“Redisson 默认租期 30 秒，看门狗每 1/3 也就是 10 秒续一次，取 1/3 是为了容忍两次续期失败还有余量。它只在没有显式 leaseTime 时生效。一直续期的风险是：业务 hang 或忘记 unlock 时锁永不过期，别人永远拿不到；网络分区时可能出现两个客户端都以为自己持锁，必须靠业务幂等和 fencing token 兜底；长 GC 也可能让锁在业务执行中过期。所以能估时长就传 leaseTime，tryLock 设等待时间，finally 释放，关键写操作加幂等。”

07 Redis 热 Key：怎么定位、怎么解决

7.1 定位手段

方法 说明 局限
redis-cli --hotkeys 基于 LFU 计数排序 需要 LFU 淘汰策略，采样统计
OBJECT FREQ key 查单 key 的 LFU 频率 需逐个查
MONITOR 实时看命令 开销大，只能短时应急
代理层指标 Codis/Twemproxy/云代理的 key 级 QPS 依赖基础设施
客户端埋点 本地计数 + 定时上报 有采样误差
平台探针 京东 Hotkey、有赞 TMC 等 建设成本高

补充：--bigkeys、MEMORY USAGE 找的是大 key，不是热 key；热 key 和大 key 经常同时出现，但要分开治理。

7.2 解决手段

手段 做法 注意
本地缓存 Caffeine + 短 TTL（1~5s）挡住绝大多数读 多节点一致性：Pub/Sub 失效 + 短 TTL 兜底
Key 拆分 key:0 ~ key:N-1，读随机、写全量 写放大；计数类可本地聚合
多副本读 从副本分担读 热 key 仍属一个槽位，只解决读吞吐
限流/降级 单 key 令牌桶，超限返回旧值/默认值 会损失部分请求
预热 活动前把热点数据加载到本地/Redis 要防同时失效
逻辑过期 不设物理 TTL，异步重建 实现复杂
计数聚合 本地累加后批量写，或分片计数再汇总 精度与实时性权衡

Cluster 关键点：热 key 只落一个槽位，加节点并不能分摊；拆 key 时不要加相同的 {hash tag}，否则所有分片仍落同一个槽位。细节在 Day18 展开过，这里记结论。

7.3 面试怎么答

“定位上，LFU 策略下用 --hotkeys 或 OBJECT FREQ，线上更常见的是代理层指标和客户端埋点，MONITOR 只能短时抓。解决分三层：读热点先上本地缓存，短 TTL 加广播失效；再不行把 key 拆成 N 份，读随机、写全量，Cluster 下注意别加相同 hash tag，否则白拆；同时做限流降级和活动前预热。写热点或计数型热 key 用本地聚合批量写或分片计数。”

08 MySQL 主键不自增会有什么问题

8.1 聚簇索引的插入局部性

InnoDB 的表按主键组织成聚簇索引，数据页里的行按主键有序排列：

主键类型 插入位置 结果
自增 BIGINT 永远追加到最后一页 页填充率高、顺序 IO、缓存友好
随机 UUID v4 随机插入中间页 页分裂、碎片、随机 IO、写放大
趋势递增（雪花/ULID） 大致追加 接近自增，兼顾全局唯一

页分裂的连锁反应：新页分配、旧页搬数据、索引碎片、Buffer Pool 命中率下降，最终插入变慢；碎片多了还要 OPTIMIZE TABLE 重建（大表要用 gh-ost/pt-osc，避免锁表）。

8.2 二级索引会被主键拖累

二级索引叶子存的是主键值：

一张表有几个二级索引，每个索引的每条记录都要存主键——主键大一倍，所有二级索引都跟着变大，内存、IO、比较成本全部上升。

8.3 分库分表下的全局唯一

自增主键在单库单表没问题，但分库分表后各分片会重复。正确做法不是退回随机 UUID，而是：

方案 特点
Snowflake 时间有序、64 位、需处理机器 ID 与时钟回拨
号段模式（Leaf） 批量取号、DB 压力小、ID 趋势递增
ULID 时间有序 + 随机后缀，字符串/二进制都可
数据库自增步长 简单但扩容不灵活，不推荐大规模使用

业务唯一键（订单号、案件编号）建唯一索引即可，不要直接当聚簇主键。

8.4 面试怎么答

“InnoDB 是聚簇索引，数据按主键有序存。自增主键是追加写，页填充率高；随机主键比如 UUID 会插到中间，触发页分裂、产生碎片和随机 IO，Buffer Pool 命中率也会下降。二级索引叶子存主键，UUID 36 字节对比 BIGINT 8 字节，所有二级索引都会变大。所以单库优先自增 BIGINT；需要全局唯一就用雪花、号段或 ULID 这种趋势递增的 ID，别用随机 UUID；业务唯一键单独建唯一索引。MySQL 8 还可以用 innodb_autoinc_lock_mode=2 提升并发插入，但自增值会有空洞。”

09 八道题的共同答题框架

面试里最加分的不是背出机制，而是让人相信你在线上处理过。统一用五段：

三条纪律：

  1. 数字口径要分清：入口 QPS ≠ 核心写 TPS；日均处理量 ≠ QPS；峰值是生产值还是压测值；
  2. 没做过的说”评估过方案”，不要硬编；追问三层一定穿帮；
  3. 每题收尾带一句项目细节，比如”我们按案件 ID 分段加锁””缓存 key 带法院维度”，可信度立刻不一样。

10 一页纸速查

关键词 一句话
rehash 触发 负载因子 ≥1 扩容（有子进程 ≥5），<0.1 缩容
渐进式 rehash 每次命令迁一个桶，serverCron 100 桶/1ms
rehash 读写 读 ht0→ht1，写只写 ht1，删两边查
大 key 卡顿 不是 rehash，是 DEL/HGETALL/KEYS 等 O(N) 命令
大 key 处置 UNLINK、HSCAN 分批、拆 key、禁用 KEYS
二级索引查找 根→叶→首个匹配→扫到不匹配→回表

写盘方式 日志顺序写，数据页随机写

RabbitMQ 模型 默认推，prefetch 控在途，手动 ack
basic.get 拉模式需轮询，生产不用

11 60 秒复盘话术

问题：”挑一道你今天印象最深的题讲讲。”

“我讲 Redis 的 rehash 和大 key 吧。rehash 是渐进式的：扩容时分配两倍空间，每次命令顺带迁一个桶，空闲时每轮 100 个桶且限时 1 毫秒，迁移期间读先查旧表再查新表、写只写新表。所以 rehash 不会整体卡住，大 key 也不会因为 rehash 被整体搬动，因为搬的是指针。真正会卡的是大 key 上的 O(N) 命令，比如 DEL 一个百万元素的 Hash、HGETALL、KEYS，Redis 单线程会被阻塞。线上我们用 UNLINK 异步删、HSCAN 分批清，把大 key 按时间或 ID 拆小，同时用 –bigkeys 和 SLOWLOG 做巡检。放到项目里，法院案件缓存我们也做了类似约束：单 key 控制在几千元素以内，缓存只存非敏感摘要。”

最后记住三句话：

  1. 组件题都要落到”边界”：rehash 不卡但 O(N) 命令卡；WAL 快但数据页是异步刷；推模式省轮询但依赖 prefetch 背压。
  2. 参数题都要落到”约束”：线程数受下游容量、内存和竞争限制；看门狗受租期、GC 和分区限制；队列长度受可接受等待时间限制。
  3. 面试的可信度来自项目细节：同样一句原理，加上”我们按案件 ID 分段加锁 / 缓存 key 带法院维度 / 3 台服务器按峰值评估”，就是做过和背过的区别。
