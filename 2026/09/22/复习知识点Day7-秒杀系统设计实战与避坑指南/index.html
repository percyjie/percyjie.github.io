一句话记住今天：秒杀 = 「漏斗削峰」+「Redis 原子扣库存」+「MQ 异步下单」+「DB 兜底对账」。面试抓三条主线：① 分层架构（前端静态化 → 网关限流 → 应用防重 → Redis 原子扣库存 → MQ 异步落库 → DB 兜底）；② 防超卖核心代码（Lua 脚本原子扣减库存，禁止「先查后扣」）；③ 一致性兜底（消息可靠投递 + 超时回补 + 定时对账）。

1. 秒杀系统是什么：核心矛盾与设计目标

秒杀 = 极短时间内、大量用户抢购有限库存（双 11 抢购、抢票、限量发售）。它本质上是「瞬时洪峰 + 强一致性」的极端场景。

维度 特征
流量形态 读多写少、瞬时爆发（平时 100 QPS，秒杀 10w QPS）
库存 有限且公开透明，卖完即止
硬性约束 不能超卖（卖 100 件不能出 101 单）
体验要求 请求不超时、不重复扣款、结果可查

三大设计目标：

  1. 高性能：绝大多数请求在缓存/网关层就被快速响应，不让流量全部打到 DB；
  2. 高可用：峰值不拖垮整个链路，能”快速失败”而不是”慢慢挂掉”；
  3. 一致性：库存与订单最终一致，靠对账兜底。

一句话记住：把流量挡在外围，把扣减收敛到内层，把写入转为异步。

2. 分层架构总览（5 层防线）

每一层只做一件事：

层 职责 关键手段
前端 挡住大部分人 静态化、CDN、按钮置灰、验证码/答题
网关 挡住突发流量 限流、防刷、黑白名单
应用层 防重 + 并发控制 幂等标记、Redis Lua 原子扣减
消息队列 削峰填谷 异步下单、失败重试、死信告警
数据库 最终落库 唯一索引、条件更新、对账任务

3. 第一道防线：前端与网关

原则：能不进来就不进来。 查库存、查倒计时等流量都应被静态化/缓存扛住，业务接口只在真正抢购时被调用。

3.1 前端

  • 页面静态化 + CDN：抢购页纯静态，进入后零请求；
  • 按钮置灰 + 倒计时：未开始 / 已售罄直接禁点，避免大量无效请求；
  • 验证码 / 答题：天然限速防刷（人类答题约 3 秒一次，把瞬时峰值拉平）；
  • 抢购结果显示用「轮询结果接口」替代「轮询库存接口」，避免把缓存/DB 打到死角。

5. MQ 异步下单与最终一致性

扣减成功 ≠ 下单成功。两者通过 MQ 解耦成「最终一致」：

为什么必须拆异步？

  • 同步创建订单会让 MySQL 变成新的热点（瞬时 10w 条 INSERT），把整库拖死；
  • 秒杀场景用户只需知道自己”抢到了”，实际订单可以出结果；体感可接受。

5.1 消费幂等（防重复建单）

建议在订单表加唯一索引：UNIQUE KEY uk_user_sku (user_id, sku_id, biz_id)，双保险。

5.2 超时未支付与对账回补

  • 抢到未支付会占库存：订单超过 N 分钟未支付 → 关闭订单 + 回补库存（回补同样走 Lua 原子增加，并记录流水供审计/对账）；
  • 定时对账任务对比「Redis 扣减成功量 vs DB 有效订单量」，发现差异告警并自动/人工修复。

6. 常见坑与最优实践汇总（一张表）

坑 现象 最佳实践
超卖 抢到人数 > 库存 Lua / DB 条件更新原子扣减，禁止「先查后扣」
重复下单 同一人多单 幂等 key + DB 唯一索引
库存与订单不一致 扣了库存，订单没建成 MQ 重试 + 消费幂等 + 定时对账回补
缓存雪崩 同刻大量 key 失效 过期时间加随机值、多级缓存
缓存击穿 热点 key 失效瞬间 DB 被打爆 互斥锁重建、热点 key 永不过期+异步更新
接口被刷 爬虫/脚本不停轮询 验证码、用户限流、接口脱敏
DB 连接打满 每个请求都查库 读写全走缓存，真正落库的只有异步创建订单
Redis 单点挂掉 库存不可用 集群 + 限流保护 + 优雅降级为”排队”

7. 面试常见问题速答（表格速查）

面试题 一句话要点
秒杀系统核心难点是什么？ 瞬时高并发 + 不能超卖 + 不能打挂 DB
如何保证不超卖？ Redis Lua 原子扣减为主，DB 条件 UPDATE 兜底
为什么库存放 Redis 而不是 MySQL？ 扛住高并发热点写，又不让 DB 成为全局瓶颈
库存扣减成功但订单创建失败怎么办？ MQ 重试 + 幂等消费 + 失败进入死信/告警 + 对账补偿
用户抢到但 15 分钟未支付怎么办？ 关单 + Lua 回补库存 + 记录流水对账
什么情况下会发 MQ？ 只有 Redis 扣减成功才发，失败不发
从点击到下单经过哪几步？ 前端 → 网关限流 → 应用防重 → Lua 扣库存 → MQ → 异步建单
